The frontier scheduler: watching the ladder think

2026-06-26 22:27 · milestone architecture rendering ladder

Watch this log output for a moment.

[14:00:43]   juggernaut_van_s11_00001_.png -> masters/juggernaut_van_s11_t29s_00042_.webp
[14:00:43]    queued localimagegen/juggernaut_van_s13 seed=42

[14:00:59]   juggernaut_van_s13_00001_.png -> masters/juggernaut_van_s13_t15s_02026_.webp
[14:00:59]    queued localimagegen/juggernaut_van_s15 seed=2026

[14:01:14]   juggernaut_dragon_s13_00001_.png -> masters/juggernaut_dragon_s13_t15s_00042_.webp
[14:01:14]    queued localimagegen/juggernaut_dragon_s15 seed=42

Each line is the dynamic ladder planner doing its job on measured reality, in real time, per rung.

The flaw we fixed

Until today, run computed the entire desired rung set for every ladder upfront — one big disk scan, one planLadder call per ladder, and then every resulting cell enqueued to ComfyUI in a single batch. Juggernaut's kingdom scene: 46 items in the queue at once.

The problem: planLadder uses render durations to decide how finely to space rungs. Faster renders → tighter spacing; slower renders → wider gaps. But those durations were read from already-rendered masters. If a ladder was new — nothing rendered yet — the planner had no timing and fell back to floor+ceiling only. And even with some data, the entire batch was committed on timing measured in a previous pass, sometimes minutes or hours ago. The ladder was frozen at plan-time, not adjusted at measurement-time.

The planner was designed for per-rung feedback. The scheduler was ignoring that.

What changes

One frontier rung per ladder in the queue at any moment. A ladder is a (model × scene × seed) triple — juggernaut with 6 scenes and 2 seeds has 12 ladders. So the queue holds 12 items: not 46, not 1, exactly 12.

When a rung completes:

  1. Stamp it immediately — move raw PNG to master WebP, record the _t<dur>s_ duration in the filename.
  2. Fold the measured duration into that ladder's in-memory rendered map.
  3. Re-run planLadder(floor, pins, ceiling, rendered) — pure function, same algorithm, now with one more real data point.
  4. Call frontierRung(planned, renderedSet) — the lowest desired rung not yet on disk.
  5. Enqueue it. The slot refills instantly.

The queue depth doesn't drop as work completes — it stays at the number of active ladders until they're all finished. Breadth keeps the GPU busy; depth is earned by measurement.

Watching it in the log

s11 stamped, t=29s → gapForDur(29) = 2 → next frontier: s13
s13 stamped, t=15s → gapForDur(15) = 2 → next frontier: s15
s13 stamped, t=15s → gapForDur(15) = 2 → next frontier: s15

The gapForDur function maps render duration to a step-count gap on a square-root curve (1 at ≤9s, 4 at ≥217s). At 15–29s — juggernaut is fast — the gap is 2. If a render came back at 100s the gap would widen to 3; at 217s+ it's 4. Each ladder climbs at its own pace, calibrated to its own timing.

That's the design working. The plan isn't written once at the start and frozen. It's rewritten after every measurement, ladder by ladder, rung by rung.

Crash safety

Nothing changed about where state lives: masters on disk. Kill the process mid-flight, re-run, and it re-scans masters/, seeds each ladder's rendered map from whatever's there, and picks up from the correct frontier. Rungs that were in-flight but never stamped simply stay missing. No run-state file, no partial state to reconcile.

The tail rule

When only one ladder is left — the sole source of in-flight work — strict depth-1 means the GPU sits idle for the poll interval (~5s) plus stamp time while we wait to re-plan. For short renders that's non-trivial. The scheduler checks: if that idle gap is ≥25% of the last measured render duration, it pre-queues one extra rung (depth 2). Otherwise it accepts the brief idle. Most of the time, with 12 ladders running in parallel, this never triggers — breadth handles it. It's only the tail of the very last ladder where it matters.

The number that tells you it's working

Queue depth: 12. Constant. One per ladder, the whole time. Not 46 (the old "everything at once"), not 1 (fully serialised). Twelve parallel measurements, twelve independent climbs, zero wasted timing guesses.

That's the frontier scheduler.
