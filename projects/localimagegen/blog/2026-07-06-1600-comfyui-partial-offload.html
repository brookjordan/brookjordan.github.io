How ComfyUI decides to partially load a model

2026-07-06 16:00 · lesson comfyui memory apple-silicon

ComfyUI has a feature that's easy to miss: when available RAM is tight, it doesn't refuse to load a model — it loads what it can into GPU memory and streams the rest from CPU RAM on demand. The log tells you which happened: "loaded completely" or "loaded partially".

The decision point

Before loading a model, ComfyUI calls get_free_memory(device) to check headroom. On MPS this returns psutil.virtual_memory().available — system free RAM. If that's larger than the model's weight size plus some buffer, it loads completely. If not, it loads partially: the UNET weights stay on CPU and get copied to GPU a layer at a time during each denoising step.

# Simplified from ComfyUI's model_management.py
if model.model_size() > get_free_memory(device):
    load_model_gpu_partial(model)   # keep weights on CPU, DMA per step
else:
    load_model_gpu(model)           # full weights onto GPU

What partial loading costs

A full load holds all UNET weights in GPU memory throughout the render. A partial load moves weights from CPU to GPU on every denoising step — typically 20–50 per render — then frees them. The peak GPU allocation is lower (only a fraction of the weights are resident at once), but the render is much slower: each step incurs a DMA transfer of potentially gigabytes of weights, throttled by memory bandwidth.

On an M3 Max, a full SDXL render takes ~12 seconds. A partial load of the same model, with 30 denoising steps, takes ~90 seconds — 7.5× slower.

The trap: it's decided at load time, not render time

ComfyUI calls get_free_memory() once, when the model loads. If the page cache happened to be warm at load time (less apparent free RAM), it might choose partial load even though plenty of physical memory is available. If the cache was cold (more apparent free RAM), it might choose full load.

This is exactly why we suspected pony's bimodal distribution was real — the log was reporting "complete" every time, but we were worried the free-RAM check might have been noisily triggering partial loads for some runs. The log reporting was correct: pony loaded completely every time. The bimodal was purely measurement noise.

Parsing the logs

The intensive sweep parser watches for these lines in ComfyUI's stdout:

loaded completely 10.795 GB, time: 5.04s
loaded partially, current loaded 6.532 GB

Each measurement captures loadMode: 'complete' | 'partial' | null. When a model genuinely does split modes across runs — which can happen if available RAM changes between measurements, or if another process took memory in the background — the reconciliation step uses the log-reported mode as the primary axis for the bimodal split, rather than inferring it statistically from the peak distribution.

The reserve-vram flag

ComfyUI takes a --reserve-vram N flag that reduces the apparent free memory by N GB for the purposes of the get_free_memory() check. Set it to 5 and ComfyUI will behave as if 5 GB less RAM is available, triggering partial loads earlier. Our sweep passes --reserve-vram 5 in the ComfyUI startup command, which means models that are borderline (UNET ~6–8 GB on a 36 GB machine) should always load completely.

On a smaller machine — or with more processes running — the partial-load mode becomes more relevant, and the reconciliation logic for handling the bimodal split becomes important.
