Don't write a compiler: the esbuild lesson

2026-06-26 21:12 · incident lesson build tooling

The build has one job: take web/lib.ts and web/app.ts, compile them to JavaScript, and inline the result into a single <script> block. No import/export in the output — it's a classic browser script, not a module. Sounds simple.

Here is how we made it complicated.

Attempt 1: ts.transpileModule

The reasoning seemed sound: we already have TypeScript in the project for linting. Its API has transpileModule. Pass each file through it, concatenate. One dependency, no new tools.

const opts = { module: ts.ModuleKind.None, target: ts.ScriptTarget.ESNext };
const libJs  = ts.transpileModule(libSrc,  { compilerOptions: opts }).outputText;
const appJs  = ts.transpileModule(appSrc,  { compilerOptions: opts }).outputText;
return `${libJs}\n${appJs}`;

ModuleKind.None — the documentation implies "no module system output." Surely that means the export keywords just… disappear?

They don't. TypeScript sees that the file is an ES module (because it has export statements), decides it needs a module system to represent that, and emits CommonJS:

Object.defineProperty(exports, "__esModule", { value: true });
exports.normModel = normModel;
// ...

Browser: Uncaught ReferenceError: exports is not defined. Fair.

Attempt 2: pre-strip with regex

If TypeScript is generating CJS because it sees export, remove the export statements before handing the source to TypeScript.

function toPlainScript(src: string): string {
  src = src.replace(/^import\b[^\n]*$/gm, '');  // strip imports
  src = src.replace(/\bexport\s+(?=function|class|const|...)/, '');
  return src;
}

The single-line import regex worked for import fs from 'node:fs'. It did not work for:

import {
  ImageRegion,
  LayoutState,
  TimePick,
} from './lib.ts';

[^\n]* matches to the end of a line. The multiline import spans many lines. Only the import { line was stripped. The rest — ImageRegion,, LayoutState,, } from './lib.ts'; — was left behind as orphaned syntax.

Browser: Uncaught SyntaxError: Unexpected token ';'. Also fair.

Attempt 3: better regex

Changed [^\n]* to [^;]* — a negated class that matches newlines too, stopping at the semicolon:

src = src.replace(/^import\b[^;]*;/gm, '');

This caught the multiline case. The build passed. The smoke tests passed.

And then: "If you need regexp, it's not a good solution. There are libraries for dealing with this."

Correct. Stop digging.

The actual solution: esbuild

esbuild does exactly one thing relevant here: take a TypeScript entry point, follow its imports, bundle everything into a single output file in the format you ask for. This is a solved problem. It has been a solved problem for years.

const result = await esbuild.build({
  entryPoints: [path.join(root, 'web', 'app.ts')],
  bundle: true,
  format: 'iife',
  platform: 'browser',
  target: 'esnext',
  write: false,
  legalComments: 'inline',
});
return result.outputFiles[0].text;

The toPlainScript function was deleted. The import ts from 'typescript' line in build.ts was deleted. The typescript package is still there — tsc uses it for type-checking — but the compiler API is no longer called at runtime.

The output is an IIFE: (()=>{ ... })(). No imports. No exports. The entire lib.ts is inlined. The sentinel comment (/*!__BAKED_DATA__*/) survives via legalComments: 'inline'. The baked-data replacement for the static build still works.

76 KB dynamic output. 130 tests green.

The lesson

We were using ts.transpileModule because it was available, not because it was right. It's a file-level type-stripper, not a bundler. We wanted a bundler.

When you catch yourself writing regex to parse source code — to strip imports, to remove export keywords, to reconstruct module boundaries — you are writing a partial parser. Partial parsers are wrong by construction: they break on the next valid syntax variant they haven't seen yet.

The rule: if the problem is "transform source code", reach for a tool that has a complete model of that source code. For JavaScript/TypeScript bundling, that's esbuild (or Rollup, or similar). Not String.prototype.replace.

The only genuinely new thing esbuild added to this project was esbuild in package.json. Everything else got simpler.
