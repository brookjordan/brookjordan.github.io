Testing the gallery: lib.ts/app.ts split + Vitest

2026-06-26 20:21 · testing refactoring web vitest typescript

The gallery frontend — web/app.ts — had been untestable since day one. Here is why, how I fixed it, and what the tests cover.

The problem: a classic browser script

web/app.ts was written as a single-file script with no exports. Every function lived at script scope, top-level DOM bootstrap fired immediately on load (setupDragDrop(...), void refresh('auto')), and the build inlined it directly into a <script> tag. This was the right call for an offline static page that needed to work on a plain file server — no bundler, no module graph, no runtime imports.

But it meant you could not import the file in a test. The moment Node.js tried to evaluate it, document.getElementById(...)! would crash. The pure logic (naming grammar, colour math, time-budget picking) was completely trapped inside a browser-only artifact.

The fix: lib.ts / app.ts split

I extracted the DOM-free logic into web/lib.ts — a proper ES module with export statements — and kept everything touching the DOM in web/app.ts. app.ts now imports from lib.ts.

What went to lib.ts:

  • All interfaces and type aliases (Catalog, CellMeta, PromptCatalog, TimePick, etc.)
  • Naming / identity: normModel, isImageFile, catalogPrefix, makeCellKey, parseFilename
  • Catalog access: pickEntry, entryMeta, samplesForModel, isOvershoot
  • Prompt resolution: promptSizeOfModel, promptForSize, promptFor
  • Time-budget picking: timeCellPick, slideShownSample
  • Formatting: formatDuration (also upgraded to emit 1m30s style), formatMetaTooltip
  • All colour math: linearizeSrgb, rgbToLab, relativeLuminance, contrastRatio, rgbToHex, haloFromSample, textColorForHalo, analyzeImageData, captionStyleFromSample
  • Layout math — now pure functions that take aspect ratios as parameters instead of a DOM index: heightFromWidth, widthFromHeight, minHeightForWidths, layoutFromAnchor

What stayed in app.ts:

Everything that touches the DOM: state variables, event listeners, ingestFilename (mutates catalog), all render/update functions, the image loader stack, drag-and-drop setup, the notes lightbox, and resize-bar drag handling. App.ts keeps thin wrappers for the functions that used to read globals directly — e.g. pickEntry(model, subject, sample) calls pickEntryPure(catalog, currentSeed, model, subject, sample).

The key discipline: functions that previously read from module globals were refactored into pure forms that take the state as parameters. The global-reading call sites become one-liner wrappers in app.ts.

Keeping the build bundler-free

The shipped output is still a single self-contained <script> — no runtime imports, no bundler. The trick is ts.ModuleKind.None in src/build.ts:

const opts: ts.CompilerOptions = {
  target: ts.ScriptTarget.ESNext,
  module: ts.ModuleKind.None,
  strict: true,
};
const libJs = ts.transpileModule(libSrc, { compilerOptions: opts }).outputText;
const appJs = ts.transpileModule(appSrc, { compilerOptions: opts }).outputText;
return `${libJs}\n${appJs}`;

ModuleKind.None tells the TypeScript transpiler there is no module system: export function foo() becomes function foo(), and import { foo } from './lib.ts' is stripped entirely. Concatenate lib first, app second, and you get a plain script where normModel, pickEntry, etc. are just global functions — exactly as before. No bundler involved, offline static page unchanged, serve --fixed still works with no net access.

Choosing Vitest

I wanted yarn test to just work without adding a bundler to the pipeline. Vitest handles TypeScript natively via OXC/esbuild, runs in Node, and uses the same import syntax as the test files. No config gymnastics needed — vitest.config.ts is 6 lines.

The test files live in test/ and import from ../web/lib.ts with the .ts extension. A new tsconfig.test.json extends the root config, adds "lib": ["esnext", "DOM"] (for Uint8ClampedArray in analyzeImageData), and includes both test/**/*.ts and web/lib.ts.

What the suite covers (128 tests)

  • lib.naming.test.ts: normModel, isImageFile, catalogPrefix, makeCellKey, parseFilename — round-trips, zero-padding, model-with-underscore parsing, parity against src/naming.ts's parse for the same filenames.
  • lib.formatting.test.ts: formatDuration edge cases (negative, zero, sub-minute, 1m30s), formatMetaTooltip field coverage, prompt inclusion, prompt truncation.
  • lib.catalog.test.ts: pickEntry seed fallback ladder, isOvershoot ceiling boundaries, samplesForModel overshoot filtering, closestSample nearest-or-below logic.
  • lib.prompts.test.ts: promptSizeOfModel normalised lookup, promptForSize fallback chain, promptFor end-to-end.
  • lib.time.test.ts: timeCellPick budget fits / over-budget / no-timing-data cases, slideShownSample per-mode dispatch.
  • lib.color.test.ts: linearizeSrgb at 0/128/255, relativeLuminance black/white/grey, contrastRatio black-on-white = 21, textColorForHalo light/dark flip, analyzeImageData on synthetic pixel buffers.
  • lib.layout.test.ts: heightFromWidth/widthFromHeight inverse relationship, minHeightForWidths monotonicity, layoutFromAnchor height consistency invariant.

What is deferred

  • jsdom for DOM helpers: sampleImageRegion, applyCaptionStyle, bindSlideCaptions and the rest of the DOM layer stay untested for now. Adding jsdom as a vitest environment would cover them.
  • Playwright on the built files: a smoke test that loads build/flexible/index.html in a headless browser and checks for console errors. The right trigger is "first time a build regression breaks the rendered gallery and we don't catch it immediately."

Neither of these is the right next step today — 128 tests already catch the logic layer where bugs actually live.
