Phase tracking: hooking into ComfyUI's execution lifecycle via WebSocket

2026-07-06 15:00 · tooling comfyui memory websocket

The allocator peak tells you the most RAM ever used in a render. It doesn't tell you when that peak happened — was it during model loading, text encoding, denoising, or VAE decode? Breaking the render into phases turns a single number into a story.

ComfyUI's WebSocket protocol

ComfyUI exposes a WebSocket at /ws?clientId=<uuid>. Once connected, it streams JSON events as the queue runs:

{"type": "execution_start",  "data": {"prompt_id": "...", "timestamp": 1234567890}}
{"type": "executing",        "data": {"node": "1",       "prompt_id": "..."}}
{"type": "executing",        "data": {"node": "6",       "prompt_id": "..."}}
{"type": "executing",        "data": {"node": null,      "prompt_id": "..."}}
{"type": "execution_success","data": {"prompt_id": "...", "timestamp": 1234567891}}

The executing event fires when a node starts. The node field is the node ID from the workflow JSON. When node is null, the queue item is done.

From node IDs to phases

A node ID alone isn't useful — "6" could be a KSampler in one workflow and a VAEDecode in another. We also need the class. The workflow JSON we submit includes class_type for every node, so we can build a lookup before enqueueing:

const PHASE_LOADERS  = new Set(['CheckpointLoaderSimple', 'UNETLoader', 'UnetLoaderGGUF',
                                 'CLIPLoader', 'DualCLIPLoader', 'VAELoader', 'LoraLoader']);
const PHASE_ENCODERS = new Set(['CLIPTextEncode', 'CLIPTextEncodeSDXL']);
const PHASE_SAMPLERS = new Set(['KSampler', 'KSamplerAdvanced', 'SamplerCustomAdvanced']);
const PHASE_DECODERS = new Set(['VAEDecode', 'VAEDecodeTiled']);

When an executing event arrives, we look up the node's class and assign a phase name: 'load', 'encode', 'sample', or 'decode'. Each phase transition gets a timestamp and a fresh snapshot of the allocator state.

What the phase timeline reveals

For an SDXL model like pony, the timeline looks like:

t=0ms    load   driver: 0.0 GB  (baseline — fresh restart)
t=4200ms load   driver: 3.4 GB  (UNET loaded)
t=4800ms load   driver: 4.7 GB  (CLIP × 2 loaded)
t=5100ms encode driver: 5.1 GB  (CLIPTextEncode runs, CLIP still hot)
t=5200ms sample driver: 5.3 GB  (KSampler starts — all weights resident)
         ...denoising steps, driver climbs to 11.0 GB peak...
t=18000ms load  driver: 5.1 GB  (VAE loaded, activations freed)
t=19500ms done  driver: 5.1 GB

The sample boundary — the moment KSampler begins — is the cleanest snapshot of "weights only, no activations yet." That's the value we call driverPostLoadGB: 5.3 GB, versus the 11.0 GB peak. The 5.7 GB difference is activation memory during denoising.

Why this matters for SDXL

5.3 GB weights + 5.7 GB activations = 11.0 GB. The activations are 52% of the peak. If you're sizing a machine for inference, the weights alone are a poor proxy for headroom — you need room for the denoising activations too, and they're roughly as large as the weights.

The phase timeline also shows where a model's memory "profile" differs from the norm. A quantized GGUF model loads much faster and produces smaller activation tensors. A video model might hold large intermediate latents across frames. The phases make those differences visible in a way a single peak number doesn't.
