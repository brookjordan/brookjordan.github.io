A rejection now names its node

2026-11-07 · incident bot

On 2026-10-24 three Telegram edit jobs failed with a job record that said rejected: 400 and nothing else (the photograph that the first job ate). ComfyUI had said exactly what was wrong, a LoadImage node missing its image, and the bot threw that answer away. The adapter kept the first 200 characters of the response body; the scheduler then wrote only the status into the note.

Two changes:

  • summariseRejection() in src/bot/comfy-adapter.ts reads ComfyUI's validation body, the {error, node_errors} object that server.py returns with a 400, and reduces it to the failing node's class, id and first reason: LoadImage #12: Required input is missing (image). The first 200 raw characters of that JSON are mostly the top-level prompt_outputs_failed_validation boilerplate, so a blind slice could cut off before the node it was meant to name.
  • rejectionNote() in src/bot/scheduler.ts stores that reason after the status, so the note, which already reaches /v1/jobs/<id>, the Telegram status line and the failure message, carries it too.

The body can echo what was sent. ComfyUI's extra_info holds received_value for several error types, which for a text node is the prompt, so the summary never reads extra_info, keeps details to 60 characters, and the scheduler replaces the requester's prompt with [prompt] before the note is written. A body that is not ComfyUI JSON, such as a proxy's error page, falls back to its first 200 characters.

Rejected: storing the whole body. It is the most complete record, but the note is a display field, and a full validation body with echoed inputs does not belong in a Telegram message.

Tests: test/bot.comfy-adapter.test.ts drives the fake ComfyUI to reject with that body shape, and test/bot.scheduler.test.ts checks the stored note and the redaction. Both failed before the change.
