The seed was a hash of the prompt

2026-10-24 · incident lesson

Brook, in the Telegram bot: "the seeds seem to be repeating a lot." They were! Oh, they were. The bot's seed was not random at all. It was a deterministic hash of the prompt text. Every prompt carried its own little fixed seed, like a name tag. Ask for the same picture twice and you got the same picture twice, forever, with the bot cheerfully calling that randomness.

function stableSeed(prompt: string): number {
  let h = 2166136261 >>> 0;
  for (const byte of Buffer.from(prompt, 'utf8')) {
    h = Math.imul(h ^ byte, 16777619) >>> 0;
  }
  return (h & 0x7fff_ffff) + 1;
}

and the job record carried seed: stableSeed(job.originalPrompt).

The intent was right there in the comment: "Deterministic per prompt: Krea comparison commands can share a seed." And that is a genuinely lovely property! Compare five Krea variants with the seed held constant and the comparison is fair. Someone wanted that, and they were right to. The trouble is the property got applied to every job, so the comparison affordance escaped into the product and started eating novelty. Worse, the gallery's own cell identity is <model>_<scene>_sNN_<seed>, which means a re-used seed is not "similar output". It is the same cell. The bot was re-printing the same trading card and calling it a new draw.

Counted, not guessed

Not a theory from reading the code. Counted from the live job store in data/telegram-bot/jobs/ on 2026-10-24:

quantity value
jobs carrying a seed 82
distinct seeds 36
distinct prompts 25
prompts locked to exactly one seed 17 of 25

One seed appeared in 11 separate jobs. Two prompts accounted for 12 and 11 jobs respectively. Eighty-two rolls of the dice, thirty-six numbers. Those dice were loaded, rigged, and hand-polished.

The fix

randomInt(1, 0x7fff_ffff + 1): a properly random positive 31-bit seed, drawn once at creation and then durable. A retry or a restart re-uses the recorded value, so idempotency is preserved and a job never re-rolls under a retry. That was the property worth keeping all along: the seed is stable for a job, not stable for a prompt. Comparison commands keep their fairness; everyone else gets fresh dice.

The regression test draws 40 jobs from the identical prompt and asserts 40 distinct seeds. Against the old code it fails spectacularly, which is the point. Against the new code it passes. Both directions were run, not assumed.

What this was not

Two other seed sources look like repetition and are not, and both get to live:

  • scripts/replay-edit.ts defaults to --seed 4242. Deliberate! A certificate is only comparable to another certificate if the seed is pinned. The replay harness is a scientific instrument, not a user-facing render. Next!
  • config/gallery.ts pins seeds: [42, 2026]. The gallery matrix is a controlled comparison, the same scene at fixed seeds across models. Randomising it would destroy the very thing it exists to measure. Absolutely not. Next!

So the change is scoped to the Telegram bot's job store: the one surface where a human asks for an image and expects a new one.

What still hurts

The test that shipped alongside the original code was named "assigns a durable seed", and it documented exactly the wrong half of the contract. It asserted the seed did not change between reads. It never asserted the seed differed between requests. So it sat there passing, green and proud, while every repeat re-rendered the same picture. The bug had a bodyguard the whole time. A test named for one property cannot catch the loss of the property you forgot to name, and that is the part worth losing sleep over.
