Pony Goes Native: Dropping the Lightning LoRA

2026-07-07 · pony illustrious workflow research decision

Pony's renders have always looked washed-out and watercolour-hazy — the exact "dull colours" complaint that opened this research thread. After a systematic side-by-side test, the cause is clear and the fix is unambiguous.

What was wrong

Pony Diffusion V6 XL was running on the same sdxl Lightning LoRA builder as sdxlbase / realvisxl / juggernaut: 4-step or 8-step SDXL-Lightning LoRA, cfg 1, euler / sgm_uniform, baked VAE. This was a mistake of convenience — Pony is an SDXL checkpoint so the LoRA loads, but SDXL-Lightning is distilled from the base model, not from Pony's fine-tune. At cfg 1 the negative prompt is inert (ByteDance's own docs say Lightning "already used CFG during training, so using it again reduces quality"), and at full strength_model: 1.0 the distillation fully overwrites Pony's aesthetic. The result is exactly what we saw: flat, grey, low-contrast watercolour noise.

The Pony V6 model card is explicit: CLIP skip 2, external sdxl_vae.safetensors, score-tag prefix, Euler a, 25 steps, CFG 7. We were hitting maybe two of those five requirements.

The test

We rendered all 8 scenes × {pony_old, pony_new, ill_old, ill_new} at seed 1234567, saving to recipe-test/ in the ComfyUI output dir. The Pony comparison was unambiguous:

Scene Old (Lightning, cfg 1, 8st) New (bare, cfg 7, 25st, ext VAE)
van muddy grey street saturated magenta/cyan neon night scene
dragon flat brown blob vivid blue-scaled dragon in crystal cave
doll hazy pastel fog crisp pink-dress BJD with depth of field
kingdom washed cityscape punchy mountain kingdom at golden hour

Every scene improved substantially. The Illustrious comparison (cfg 5 vs cfg 6) was subtle — both already vibrant at step 26 — so cfg 6 is a modest polish, not a fix.

Changes made

workflows/pony.t2i.json and pony.t2i.high.json — both rewritten:

  • Removed LoraLoaderModelOnly (Lightning LoRA)
  • Added VAELoader loading sdxl_vae.safetensors (already installed)
  • KSampler: cfg 1 → 7, sampler euler → euler_ancestral, scheduler sgm_uniform → karras
  • Model input: from LoRA output → directly from checkpoint

config/gallery.ts (pony entry):

  • ceiling: 8 → ceiling: 25
  • Removed steps: { add: [1] } (step 1 only made sense for Lightning's 4-step LoRA)
  • Removed workflow_high (no longer need a 4-step vs 8-step split)
  • Updated comment

src/graphs.ts:

  • Removed PONY_BUILDER constant (now unused)
  • Removed Pony from the isHighSDXL check (no LoRA split to route)
  • Rewrote the pony fallback builder to match the new recipe

workflows/illustrious.t2i.json: cfg 5 → 6 (modest contrast/saturation bump)

Deprecation: lig deprecate model=pony queued 21 remaining non-deprecated cells; combined with cells already deprecated from previous sessions, all Pony and Illustrious cells will be replaced on the next lig run.

What it means for the sweep

Pony leaves the "SDXL-Lightning speed cohort" (sdxlbase/realvisxl/juggernaut/krea2/qwen2512) and joins the "native anime cohort" (illustrious/noobai/noobaivpred). Each cell now takes ~55s instead of ~12s on M3. The step ladder grows from 5 rungs (1/2/4/6/8) to ~10+ rungs (2/4/6/…/25). This changes what the Pony row measures — native quality vs. distilled speed — which is the right comparison for an anime fine-tune with this level of curation.

The invariant in CLAUDE.md ("builders carry only the functional Lightning step-distill LoRAs") still holds: Pony's new builder carries no LoRA at all. Lightning on an incompatible fine-tune wasn't "functional" — it was actively harmful.
