Decision: pick banner workflows by tagged strengths, not per-banner comments

2026-07-06 18:00 · decision tooling content

scripts/banners/gen-banners.ts generates the little illustration that heads each devlog post. Every BannerDef used to hardcode model / steps / cfg / sampler / scheduler directly, justified by a one-off comment:

// Model fit: Juggernaut excels at cinematic atmospheric concept art and landscape scenes.
model: 'Juggernaut-XI-v11.safetensors',
steps: 35, cfg: 6, sampler: 'dpmpp_2m_sde', scheduler: 'karras',

That knowledge — "Juggernaut is good at cinematic/landscape/industrial scenes", "NoobAI wants Danbooru-tag prompts", "IllustriousXL handles painterly fantasy environments" — already existed as prose in the file's top-of-file comment block and was correct. It just wasn't usable: to add a ninth banner you had to re-read six checkpoints' worth of scattered comments and manually decide, then re-type the settings again.

What we did instead

config/workflows.ts (the main gallery's model catalog) already has exactly the right shape for this: a good_at: string[] tag list per workflow, seeded empty pending real usage data (see its comment: "grows from the image-notes corpus (Phase 2)"). Banners don't have a notes corpus, but they do have hand-authored community consensus already sitting in prose — so we formalized that prose into the same shape:

const WORKFLOWS: Record<string, WorkflowPreset> = {
  noobai:      { model: 'NoobAI-XL-v1.1.safetensors', good_at: ['danbooru-tags', 'anime', 'character', 'chibi'], ... },
  illustrious: { model: 'illustriousXL_v2.safetensors', good_at: ['danbooru-tags', 'illustration', 'painterly', 'fantasy', 'colorful'], ... },
  juggernaut:  { model: 'Juggernaut-XI-v11.safetensors', good_at: ['natural-language', 'cinematic', 'photoreal', 'concept-art', 'industrial', 'landscape', 'architecture'], ... },
  realvisxl:   { model: 'RealVisXL_V5.0_fp16.safetensors', good_at: ['natural-language', 'photoreal', 'technical', 'electronics', 'closeup'], ... },
  // ...
};

Each BannerDef now states the job, not the machinery: goodFor: ['cinematic', 'industrial', 'concept-art']. A pickWorkflow() scores every preset's good_at against a banner's goodFor by tag overlap and returns the best match — steps/cfg/sampler/scheduler/negative-prompt all come along for free from the winning preset.

The tag vocabulary quietly captures a second axis worth noticing: danbooru-tags vs. natural-language isn't about subject matter at all, it's about which prompt dialect the checkpoint was fine-tuned against. race-condition and actual-numbers's prompts both open with "very awa, masterpiece, best quality, newest, absurdres, highres" — pure Danbooru quality-tag boilerplate — even though the subject (a race condition timing diagram, a bar chart) has nothing to do with anime. Tagging by prompt-dialect fit, not just content, is what correctly routes both to NoobAI instead of to whichever checkpoint's subject-matter tags happen to overlap most.

Verifying it before trusting it

Re-derived every existing banner's original hand-picked model from its goodFor tags by hand before touching the array, then ran the real script — the log line makes the reasoning legible at generation time instead of buried in a comment:

[mem-lies] goodFor=[danbooru-tags, anime, character, chibi] -> NoobAI-XL-v1.1.safetensors @ 1536×640...

All eight banners' picks matched their original hand-authored choice exactly.

A small bonus: keep

Two banners carried a // KEEP comment meaning "this render turned out well, don't regenerate it" — but nothing enforced that; yarn gen:banners with no filter re-rolled everything, comment or not. Turned the comment into a real keep: true field: a bare yarn gen:banners now skips kept banners (and says so), while yarn gen:banners <slug> still regenerates a specific one on request. Same shape as the main gallery's deprecate-don't-delete posture — a note that only a human reads is not a guarantee.

Why not wait for a real notes corpus

config/workflows.ts's good_at is deliberately seeded empty until Phase 2's image-notes corpus exists — inventing tags there ahead of real usage data would just be guessing. Banners are a different situation: the "which checkpoint is good at what" knowledge already existed, hand-verified, in the file's comments. Formalizing existing verified knowledge into a matchable shape isn't the same risk as fabricating good_at data for the main catalog — there was no need to wait.
