Incident: a plain build silently un-deprecated 216 Pony cells

2026-07-07 00:46 · incident resilience gallery

Last night's overnight run was supposed to re-render Pony with its corrected booru-tag prompts. This morning the gallery said Pony was fully done. It wasn't — not one Pony master had a modified timestamp since the fix landed. The run had nothing to do, because something had already told it Pony didn't need doing.

What actually happened

Auto-deprecation works by comparing each master's recorded promptHash (written the moment it was rendered) against the hash the current config would produce for that cell. Mismatch means the prompt changed since the render — deprecated, needs a rerun.

refreshData rebuilds data/meta.json from scratch on every call — run, watch, build, refresh-data all call it — by merging three layers: scanMasters() (whatever meta.json doesn't have a fresher record for, reconstructed straight from each master's filename), histMeta (from ComfyUI's own /history, which only remembers a rolling window of recent jobs), and liveMetaMap (this run's own in-flight renders). The bug was in the base layer: scanMasters doesn't know what prompt a master was actually rendered with, so for the promptHash field it just computed the hash of what the prompt would be under the current config — a tautology. Any master old enough to have rotated out of ComfyUI's history (i.e. almost all of them) got its recorded hash silently replaced with one that, by construction, always matches the live config. Deprecated-by-prompt-change cells look freshly rendered the instant a build runs, render or no render.

Timeline: fixed Pony's prompt_size, config auto-deprecated 216 cells, confirmed via status. Ran yarn build a few minutes later (routine — build before commit, per house rules) — that alone flipped Pony back to "done" with zero renders. The overnight run started after that and, correctly following what the data told it, skipped Pony entirely. Illustrious's sub-21-step deprecation survived the same build untouched, because it's a manual selector in config/deprecations.yaml — a completely different, hash-independent mechanism that this bug can't touch. That's what made it visible at all: two cells deprecated in the same breath, one silently reverted a few minutes later, one not.

The fix

refreshData now reads whatever promptHash is already on record before layering scanMasters underneath it, and keeps the recorded value when one exists. scanMasters's guess only wins for a cell with no prior record at all — i.e. the first time it's ever seen, when there's nothing to drift from yet. Only a real observed render (ComfyUI history, or this run's own live capture) is trusted to overwrite a promptHash going forward.

Recorded the true historical hash was already gone by the time this was caught, so there was no way to "restore" it — re-added Pony's 216 cells to the deprecation list by hand (lig deprecate model=pony) to recover the intended state.

The lesson

This is exactly the "completion must be provable from disk" rule from CLAUDE.md, missed in a subtle place: the disk record itself wasn't append-only or fact-preserving — a read-modify-write over the very field that encodes "did this actually change" let a no-op rebuild indistinguishable from a real one. Any state that's supposed to prove something happened has to be written once, at the moment it's true, and never recomputed from a source that doesn't know the answer.
