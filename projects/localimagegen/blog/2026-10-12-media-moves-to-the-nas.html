The gallery's images move to the NAS

2026-10-12 · architecture decision ops

Every deploy of this gallery was shipping 8,974 image files. projects/localimagegen in the site repo was 550 MB, of which img/ was 445 MB, and Netlify served those images with cache-control: public, max-age=0, must-revalidate — so each one revalidated against the origin on every visit. The repo and the CDN were both carrying weight that neither needed to.

Meanwhile /Volumes/assets/localimagegen/masters on the NAS already held all 10,591 masters, including every one of the 8,974 the live gallery references.

So the media left git.

What moved, and what did not

lig publish-assets sends build/img and the devlog's img, banners and audio to the NAS asset service, and the pages load them from https://assets.brook.dev/localimagegen/…. The site repo keeps the HTML, the baked data and the manifest, and lig deploy now prunes any img/ it finds rather than writing one.

Every published path carries a content version, so a re-render lands on a new URL rather than overwriting an old one. lig version-assets was the one-time move of the 8,974 already-published files into that layout; it took three seconds and is idempotent.

The two halves are independent commands on purpose. deploy mirrors HTML and data into the Netlify-served folder; publish-assets sends media to the NAS. Publication is idempotent — a file goes only when the remote copy is missing or a different size — so an interrupted run resumes by re-running it, the same convergent model as everything else here. verify-assets reads the remote tree back and checks every file, because a successful copy is not proof of publication.

Result: 8,974 images (474 MB) and 184 blog media files (88 MB) published in about fifty seconds, and the site repo project folder went from 550 MB to 11 MB.

The cache question, which turned out to be measurable

The assets host serves media with Cache-Control: public, max-age=31536000, immutable, and its own guidance is never to overwrite a published media filename. That is awkward here, because lig compress deliberately re-encodes over an output older than its master.

The obvious question is whether the same filename ever really comes back. The site repo's history answers it: 361 image files were rewritten under the same filename across four commits.

The reason is in the naming. A master is <model>_<scene>_s<NN>_t<dur>s_<seed>_, and dur is the render duration in whole seconds, so a re-render collides with the old name whenever it takes the same number of seconds again. That is much more likely than it sounds at the short end:

files at t≤3s share
all deployed images (8,974) 857 9.6%
rewritten in place (361) 211 58.4%

A six-fold over-representation, with 127 of them at t1s. Collision is not the only cause — one t36s file was rewritten too, so a re-encode of an unchanged master (mtime skew after a restore, or a changed SSIM target) also reuses a name — but the pipeline reuses filenames far more often than "we don't re-render the same cell" implies.

First decision, since reversed: keep the filenames and give the /localimagegen/ subtree a one-day cache instead of the host's one-year immutable. That was a compromise, and Brook called it: a day of caching gives up most of what a static asset host is for.

Decision: version the published path instead. Every file lands at <dir>/<version>/<name>, where <version> is a hash of the bytes, and the subtree takes the same one-year immutable cache as the rest of the host. A re-render publishes a new URL; an unchanged file keeps its URL, so caches still stay warm across re-publishes. The table above is exactly the case that forced it.

Why hash the bytes rather than count renders: the master's filename is the cell identity, so the engine cannot distinguish a re-render from the same render, and a version counter would need new per-cell state while invalidating URLs even when nothing changed. Hashing costs nothing, and 15 of the 8,974 images turned out to share a version with another file, which means those two images now share one cached URL rather than two.

The version goes in a directory rather than into the filename so the grammar in src/naming.ts stays untouched. The engine and the gallery both parse that grammar, and it is what the whole matrix is keyed on, so it is the last thing to bend.

The nginx rule lives in the docker-assets stack (config/default.conf). ^~ lets one block cover the whole subtree: without it, .webp would match the host's media regex while .avif fell through to the bare location / and served with no cache header at all.

Two things that were not working

SMB was read-only. Every write to /Volumes/assets and /Volumes/docker was denied, and fresh mount_smbfs attempts failed outright, while SSH to the same account wrote to the same paths happily. Publication therefore goes over SSH, which is also what the migration report recommended after SMB's hard-link, Aux-renaming and 0700 defects. It is faster here too, by an order of magnitude. The read-only mount is still unexplained and is worth a look separately.

rsync does not work against this NAS. Every path — absolute, relative, home, /tmp — came back invalid path from the remote rsync 3.4.1, with both Homebrew's rsync 3.5.1 and macOS's openrsync. Forcing --protocol=32 and --old-args changed nothing. The publisher streams a tar of each batch over ssh instead, which works and gives the same resumability at batch granularity.

A migration gap this surfaced

The working copy had no .git: the machine-swap backup archived the worktree as a tar that deliberately excluded it, on the reasoning that git was "already bundled and pushed" — but no bundle for this repo exists in payload/git/bundles/, so GitHub was the only copy of the history.

The same tar excluded masters/, which means the local folder holds only the 711 untracked renders. 8,266 masters the live gallery references were missing locally, though the NAS has all of them. That is why lig build --bake-only exists: re-bake the HTML from the build/data and build/img already on disk without recompressing, because a full compress would rewrite the manifest from an incomplete masters set and quietly shrink the published gallery from 8,974 images to about 700.

Restoring .git is in progress and will bring the committed masters back. Until then, do not run a plain lig build in this checkout.
