Two machines, one inventory

2026-10-20 00:20 · ops architecture

Somewhere past midnight, the question arrived that nobody wanted to answer out loud: if this laptop dies tonight, what exactly do we lose? And the honest answer was: nobody knew! Not without a session of archaeology. In fact, three questions had each already eaten a whole session: which models does the matrix need, is the NAS actually holding them, and what happens if this laptop dies. All three were answered by looking, which is the same as not being answered. This pass made them answerable by command.

The inventory is generated, not remembered

docs/models-and-nodes.md lists all 51 model files the workflows reference and all 3 custom node packs they require, with a laptop column and a NAS column. It's produced by scripts/generate-model-manifest.ts, which asks three witnesses and interrogates none of them:

  • the workflows, for what is needed (check-model-inventory.ts, reading the live server's loader enums rather than a guessed directory);
  • the filesystem, for what the laptop has;
  • one ssh listing, for what the store has.

A hand-written table of 51 rows is wrong within a week. This one is wrong only until you re-run it, which is the closest thing to honesty a table can offer.

The NAS was missing 13 files and every node pack

The audit came back with its collar unbuttoned. The store held most weights but had no copy of custom_nodes at all, and 13 files lived only on the laptop: the SD1.5 and SD2.1 vintage, the Flux 2 weights, Krea 2, PixArt Sigma, SDXL base and RealVis. That's the failure mode where a rebuilt machine has every weight and still cannot load a single workflow: a pantry full of ingredients and no plates.

Two scripts close it. upload-models-to-nas.py streams each file as file.part and renames only after the byte count checks out, because a dropped connection must never leave a truncated model sitting under a real name, wearing its good clothes. publish-nodes-to-nas.py tars the packs (source only: no .git, no __pycache__), uploads them beside the model categories, and writes a MANIFEST.md carrying each archive's SHA-256.

The store now holds 18 checkpoints, 24 diffusion models, 16 text encoders, 11 VAEs, 21 LoRAs and 3 node packs. Laptop and NAS both report 51/51. That number used to be a guess. Now it's a receipt.

The audit nearly lied to us

The tool built to catch lies nearly told one itself. Finding which packs are required meant mapping every class_type in 32 workflows to the pack that registers it. The first version searched pack sources for the class name and reported six packs, including ones for KSampler and VAELoader, both core. Packs mention core classes constantly; mentioning is not providing. Six suspects, four of them invented by gossip.

Matching only real registrations (the class name used as a dict key) gave two: ComfyUI-GGUF for UnetLoaderGGUF, and ComfyUI_ExtraModels for PixArtCheckpointLoader. A third had to be added by hand, because krea2 doesn't need a node from a pack; it needs a CLIP type, an enum value, which no class scan can see. That distinction is now written into the script rather than into somebody's head, where distinctions go to die.

Why bother

Because the alternative is what just happened: six days of a project quietly producing nothing, and nobody able to say which machine was short of what without a session of archaeology. The next laptop to die gets a shrug and a re-provision, not a séance.

What still hurts

The CLIP-type gap means the pack list is not fully derivable: one dependency lives in a hand edit, and if a new model needs an enum from a pack, the script will stay serenely silent about it. The audit trusts the live server's enums too, so a workflow added but never loaded anywhere is invisible to the whole apparatus. And those 13 missing files sat there for as long as they did because nothing ever compared the two columns until tonight. The checker exists now, but it only helps if somebody actually runs it, which is the oldest catch in the book.
