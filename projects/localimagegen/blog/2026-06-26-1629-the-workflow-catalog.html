The workflow catalog — version-controlling the workflows we actually run

2026-06-26 16:29 · architecture workflows decision comfyui

The workflow that renders each model isn't really in the repo. It's buried inside buildGraph in src/graphs.ts as TypeScript, and it also floats — as a saved graph — somewhere in the live ComfyUI library on this machine. Neither form is a thing you can open, diff, hand to a stranger, or point a future router at. The actual artifact we run is invisible.

So we're fixing that: one canonical text-to-image workflow per model, committed to the repo as JSON. The 14 builders, captured as first-class, openable, enqueueable files.

The shape (and why it matches the repo)

This codebase already has a strong opinion about where things live, and the catalog just obeys it:

  • workflows/<model>.t2i.json — committed API-format ComfyUI workflows. A committed-artifact directory, exactly like masters/: the real outputs of the system, in git, openable on their own.
  • config/workflows.yaml — the human-authored catalog, exactly like config/gallery.yaml: one t2i entry per model, what it's for, what quality levels it has, what it's good at. Humans edit this.
  • build/data/workflow-stats.json — a generated timing rollup, exactly like build/data/meta.json: machine data, never hand-mixed into the YAML.

That last line is the whole discipline of the repo in one sentence — desired state is hand-authored, actual state is derived, and the two never touch. The new lig workflows export|stats|list commands draw the same line: export writes the JSON artifacts from the builders, stats derives the timings, list prints the catalog.

Phase 1 exports from buildGraph rather than the reverse, so the JSON is guaranteed faithful to what the sweep actually enqueues — no live-ComfyUI dependency, no drift. Making the JSON the single source and turning graphs.ts into a thin loader is the tempting retrofit, but it's big and risky, so it's deferred until we trust the round-trip.

We already measure how long they take at each quality level

Here's the nice realization. "What quality levels does this workflow have, and how long does each take?" sounds like it needs a profiler. It doesn't.

For a t2i workflow, a quality level is just a step rung — fast, balanced, max map straight onto the floor/ceiling in gallery.yaml. And we've been baking per-step render durations into every master filename (_tNNs_) and meta.json since day one. So timing-by-quality is a median-per-step rollup of data already on disk — no new render, no new profiler, just a groupBy(steps) over meta.json. The benchmark we already ran was secretly answering this question the whole time.

What they're good at — grown, not invented

The other half of a catalog entry is good_at, and it starts empty on purpose. We don't guess strengths; we harvest them. The image-notes corpus we shipped yesterday (image-notes-phase-1) is the raw material: free-text notes per render, aggregating up into per-model strengths, with a light tag vocabulary and optional AI auto-fill as a later phase.

Which is the real point of this whole thing. The catalog is the data substrate that the lig recommend <look> router from .claude/plans/image_notes_and_routing_a5640991.plan.md will eventually consume: workflow + timing + strengths → "use this model for that look." The router stops being a from-scratch dream and becomes "read three files."

What the Krea-2 video taught us

The seed for the deferred half of this plan was Nerdy Rodent's Krea-2 in ComfyUI — Includes Reference Image Support! It's a good reminder that a model is rarely one workflow. Krea-2 alone has a whole family: i2i, inpaint, up-to-three reference images (Flux-Redux-style), a 4096² upscale pass. Our krea2 builder is bare t2i on purpose — but those richer workflows are exactly the kind of additional task: entries this catalog is built to hold. That's Phase 3, deferred until the t2i spine is solid.

Two details that landed for us:

  • The video's "Conditioning Rebalancing" is the same ConditioningKrea2Rebalance we tried and reverted in the wee hours (2026-06-24-lesson-krea2-on-apple-silicon). The catalog entry should say the sweep stays bare deliberately, so nobody re-litigates it from the video.
  • Turbo runs at 8 steps — which is exactly our krea2 ceiling of 8. Nice when the upstream default and your own cap already agree.

The NVFP4→BF16 model-size menu in the video is NVIDIA-centric; on our MPS / Q8 path it's irrelevant. As ever, fish swim, birds fly.

None of this renders a single new image. That's the point: it makes the workflows we already run legible — diffable JSON, a catalog you can read, timings we'd already measured — and lays the table for the router to come.
