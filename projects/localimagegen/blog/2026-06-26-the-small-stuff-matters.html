Three small fixes that make the engine actually nice to use

2026-06-26 16:02 · fix feature lesson quality-of-life

The backlog has been cleared. Not just the big plans — the three little ones nobody writes blog posts about but that make daily work noticeably less annoying.

The spurious recompress (or: stop blaming the mtime)

Every time a new render was imported, compress would re-compress every single master on the next lig build. All ~1,000 of them. Minutes of libvips toiling over files it had already processed.

The bug: when stamp.ts transcodes a raw PNG to a lossless WebP master, the new WebP gets a mtime of right now. The freshness check in compress.ts is simple mtime comparison — compressed.mtime >= master.mtime. A freshly-written WebP is always newer than a previously-compressed AVIF, so the whole corpus looks stale.

The fix is one line in importAsWebp: stat the source PNG before transcoding, then utimesSync the new WebP to match. The WebP now inherits the PNG's render-time mtime instead of the transcode-time mtime. Compress sees "master same age as source" and skips it correctly. If the utimes call fails for any reason, the worst outcome is a spurious recompress — non-fatal, caught, logged.

Lesson: mtime-based freshness is cheap and usually right. The gotcha is "create a new file from an old one" — the new file inherits the clock, not the source. One utimesSync is all it takes to restore the invariant.

run --by-scene

Default model-first ordering fills one model completely across all scenes before moving on. That's the right default — fewer VRAM reloads, faster net throughput. But when you've just added a new scene (hello, kingdom) and you want to see something from every model for that scene before anything else, it's maddening to wait.

run --by-scene finishes all models' cells for scene A before moving to B. Within each scene, tier priority still applies (missing first, then invalid, then deprecated) and fastest-first model ordering is preserved. The flag is orthogonal to --model, --seed, --verify, and --missing-only.

lig mem

The engine already knows it uses a lot of RAM. It doesn't know how much per model. lig mem measures it empirically:

  1. POST /free to unload everything, wait 2s to settle
  2. Snapshot vram_free from /system_stats → baseline
  3. Enqueue one fast cell (lowest step, first scene, first seed) for that model
  4. Poll vram_free every 500ms while the queue drains → track the trough
  5. POST /free
  6. Footprint = baseline − trough

Output is a sorted table (biggest footprint first) and build/data/mem.json for anything that wants to consume it programmatically later.

The MPS caveat: unified memory, so vram_free == system RAM free — the number is "contribution to memory pressure", not dedicated VRAM. Run with watch paused and a quiet machine (no browser, no Slack) for clean deltas. Even with that caveat the relative ordering across models is meaningful, and that's the main thing we care about for scheduling.

All three are in master. None is headline-worthy on its own. Together they mean: imports don't kick off a twenty-minute recompress, you can focus a render run on a new scene, and there's finally a number to put against each model's memory cost. The engine's a bit more of a real tool today than it was this morning.
