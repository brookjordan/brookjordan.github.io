A new machine, and a list that came from the code

2026-10-23 18:54 · ops decision

New laptop, blank disk, one job: get the Telegram rendering bot working again. Step one, "which models?", and step one fell straight through the floor. Because the answer lived in two places that each knew half of it. docs/models-and-nodes.md lists the gallery matrix's 51 files. The bot serves a subset of 7 base models, but it layers abliterated text encoders and NSFW LoRAs over them, and several of those components appear in no gallery workflow at all. Ask the documentation, get 51 files that are mostly wrong for the question. Wonderful.

Hand-reading 48 commands in config/telegram-bot.ts would have fetched most of it and missed exactly the wrong few, which is the worst possible failure mode for a migration checklist. So the requirement set was derived instead: every botModels[key].base contributes its gallery inventory files, every edits[] entry is scanned for a filename, and the union is the answer. Twenty-nine files across 7 bases, in registry order, which is also the priority order because BOT_MODEL_KEYS puts the seven picks first. The code knew all along. The code always knows.

The audit nearly lied to us

And here is where it gets good. Two comparison LoRAs, snofs_krea_v1.safetensors (/krea5, /krea6) and aidmaNSFWunlock-FLUX-V0.2.safetensors (/schnell2, /schnell4), are named only in config/telegram-comparisons.ts. Neither is in the matrix file registry, so neither carries a source or a checksum. The matrix carries a SHA-256 for 26 of the bot's files and neither of these is among them. They are findable by filename on Hugging Face (canndywt/snofs_krea_v1, Drockdgd/aidmaNSFWunlock-FLUX-V0.2), but a filename match is not provenance. That is a stranger with the same name, not your file.

Then the bigger fish, and it is about the gallery inventory rather than the bot. The 51-file list in models-and-nodes.md was generated against a stopped ComfyUI, and eight of the files it counts as present are duplicates of files whose real names it counts as missing:

The workflow asks for The file on disk
krea2_turbo-Q8_0.gguf krea2-turbo-Q8_0.gguf (same inode)
flux1-schnell-Q4_K_S.gguf flux1-schnell-Q4_K_M.gguf
Flux-2-Klein-9B-KV-Q4_K_M.gguf Flux-2-Klein-9B-KV-SD-Q4_K_M.gguf
qwen-image-2512-Q4_K_M.gguf qwen-image-2512-Q5_K_M.gguf

Each pair counted once as present and once as absent. The inventory confidently reported 51/51 while hiding a real gap in the krea2 base, like a census that counts your twin as you. And the hyphenated krea2 file is a hard link to the other spelling, so a re-download into either name lands in both. The gap came with its own camouflage!

What still hurts

A registry that freezes recipes is a manifest of what to load, not where it came from, and not whether the loader will accept the name it says. Those are three different checks wearing one trench coat. Provenance lives in matrix.json's SHA-256, present for 26 of these components, and needs checking against bytes. Inventory needs checking against a running server, because an offline inventory cannot enumerate loader inputs and reports a name mismatch as a missing file, which is precisely how 51/51 lied to us. On the new machine the first check is now node scripts/preflight.ts with ComfyUI up, before anything downloads. The two LoRAs with filename-only provenance and no checksums are still sitting there, unverified, and they know it.
