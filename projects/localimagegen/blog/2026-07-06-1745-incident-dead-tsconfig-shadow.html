Incident: a dead `[ts-migrate]` tsconfig.json shadowed the real web config

2026-07-06 17:45 · incident lesson tooling

Right after fixing the scripts/ blind spot, web/app.ts produced two flatly contradictory editor errors on the same import line, depending only on whether it had a .ts extension:

// with the extension:
An import path can only end with a '.ts' extension when 'allowImportingTsExtensions'
is enabled.ts(5097)

// without it:
Relative import paths need explicit file extensions in ECMAScript imports when
'--moduleResolution' is 'node16' or 'nodenext'. Did you mean './lib.js'?ts(2835)

Neither error should have been possible: the project's real config for web/**/*.ts was tsconfig.web.json, with moduleResolution: "bundler" and allowImportingTsExtensions: true — under that config, the extension is simply optional, both ways are legal, and yarn lint:tsc --project tsconfig.web.json proved it (clean either way).

The actual culprit: a second file also named tsconfig.json

$ git log --follow --oneline -- web/tsconfig.json
91e2b85 [ts-migrate][web] Init tsconfig.json file

A one-off migration tool had, at some point, run tsc --init inside web/ and committed the untouched boilerplate — nodenext module resolution, no allowImportingTsExtensions, a pile of commented-out options, the literal // Visit https://aka.ms/tsconfig header comment. Nothing in package.json or eslint.config.js ever referenced it. It was dead.

But Cursor's (and VS Code's) built-in TypeScript language server doesn't discover projects by scanning package.json scripts — for an open file, it walks up the directory tree looking for the nearest file literally named tsconfig.json, independent of that file's include array and independent of any other, differently-named config that might logically apply. For web/app.ts, that walk hits web/tsconfig.json immediately and stops — it never reaches the real tsconfig.web.json at the repo root, which the editor has no reason to know exists. Toggling the .ts extension was really toggling between two error branches of the same wrong, dead config, which explains why both were internally consistent but mutually exclusive.

tsc --noEmit from the CLI never saw this because yarn lint:tsc invokes each project file explicitly by name (tsc --noEmit --project tsconfig.web.json) — CLI invocation and editor auto-discovery use entirely different resolution rules, and only one of them was pointed at the config that mattered.

The fix

Make the file the editor actually looks for be the file that's actually correct, instead of maintaining two: moved tsconfig.web.json's real settings into web/tsconfig.json (overwriting the boilerplate), deleted the now-redundant root-level tsconfig.web.json, and updated package.json's lint:tsc + the eslint.config.js comment to point at web/tsconfig.json. Editor and CLI now resolve to the identical file.

The generalizable lesson

A custom-named tsconfig (tsconfig.web.json, tsconfig.test.json, …) is invisible to editor auto-discovery no matter how correct its include is — only a file literally named tsconfig.json, found by walking up from the open file, gets picked up automatically. Per-package subdirectories that need their own compiler options (like web/) should carry their settings in <dir>/tsconfig.json, not a root-level tsconfig.<dir>.json — otherwise you're one stray tsc --init away from a silent, contradictory shadow config. (test/ has the same latent gap today — tsconfig.test.json lives at the root with no test/tsconfig.json to be found by the editor — noted here rather than fixed, since nothing has yet planted a decoy there.)
