The grey rectangle that passed every check

2026-09-20 17:15 · incident lesson architecture

A refused prompt does not come back as an error. Ideogram 4 returns a flat grey 1280×720 frame reading "Image blocked by safety filter", as a valid WebP at exactly the requested size. During the 2026-09-20 podcast banner pass two of those shipped, and verify-banners reported 47/47 green, because the gate only asked whether a correctly sized file existed. It did.

So the question for this repo: would lig verify have caught it?

The measurement

src/verify.ts already had a blank gate, BLANK_STDDEV = 1, aimed at flux NaN-black and truncated files, with a comment noting legit-but-dark low-step renders sit at ~2 to 5. The placeholder is not black. Its channel stdev lands at 10.5 to 11.0, comfortably inside "normal", so it sails through. Confirmed by calling the engine's own validate() on both preserved frames: ok: true, no reason.

That also kills the obvious fix. Tightening BLANK_STDDEV would start rejecting genuine dark renders long before it reached the grey card, because the two overlap on stdev: the darkest real ideogram master measures 4.2 and the placeholder 10.6.

What does separate them is concentration. The placeholder is a screen-filling fill plus a little text, so 98.2% of its pixels sit within ±2 levels of one grey value. Real renders spread out. Measured across every committed model family (2,150+ renders):

The gate is now FLAT_FILL_SHARE = 0.92 on images of 512×512 or larger, which leaves ~6pp of headroom on both sides. Both class leaders are very dark, very low-step frames: noobai_dragon_s02_t5s_1670940986_ is a 5-step render with channel stdev 5.5.

What the first attempt got wrong

The first calibration sampled 54 ideogram masters and reported a worst case of 71.3%, which made a 0.85 threshold look generous. Scanning all 216 found ideogram_van_s02_t64s_00042_ at 85.1%, above it. That would have rejected a real render, and because a rejected master is re-rendered, the cost is wasted GPU time on an image that was already correct. The threshold is only as good as the sample behind it; sample by --all when the number matters.

Two other candidate signals were measured and rejected rather than shipped:

  • Per-tile flatness (lowest 32px-tile mean |Laplacian|). Intuitive, and useless: real renders contain plenty of perfectly flat 32px tiles, so both classes score 0.000.
  • Patch-mean variation (stdev of 32px block means). Reads well on paper, but the placeholder scores 5.73 and the darkest real render 6.31. No separation at all.

That 85.1% frame is informative in its own right: channel means of 1/0/16, a near-black underdeveloped render. It is concentrated and dark, whereas the placeholder is concentrated and mid-grey (~112/112/110). Dark or grey alone tells you nothing; the combination of "very concentrated" with "not dark" is what identifies a notice card, and even then the margin is thinner than the tidy 71.3% sample suggested.

The actual fix is still upstream

Catching the grey card is a symptom check. The cause is a prompt-contract violation: Ideogram 4 is trained exclusively on structured JSON captions, and the vendor's guide states plain text "will not work and will likely trigger a safety warning", with a safety-filter false-positive rate that "is high for non-json prompts". The gallery sends prose to every model because config/gallery.ts maps one prose scene set across all of them.

The repo already has the right shape for this. prompt_sizes carries a b bucket specifically because booru tag-models need a different idiom rather than a different budget. See booru, not prose. A JSON caption is the same kind of thing: add a j bucket, give each scene a caption, point ideogram at it, and have the builder serialise the object compactly (separators=(",", ":"), strict key order) before it reaches CLIPTextEncode.

That work is not done here, deliberately. Authoring eight scenes' worth of JSON captions is content, and the scenes carry the canonical cloth-patch motif whose phrasing is load-bearing. Writing that blind, without a renderer to check against, is how you end up with a caption set that is subtly wrong for all 216 ideogram cells. The mechanism is small; the captions deserve to be written and rendered with a working ComfyUI.

Until then the gate is the safety net, and it is honest about its margin: it is tuned against the darkest low-step ideogram renders, and a future model producing legitimately near-monochrome mid-grey output would trip it. scripts/measure-flat-fills.ts exists to re-derive the number from the corpus rather than trust this table.
