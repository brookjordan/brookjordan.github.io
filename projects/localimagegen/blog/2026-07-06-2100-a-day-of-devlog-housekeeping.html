A day of devlog housekeeping: tsconfig gaps, a full banner refresh, and a way to see the old ones

2026-07-06 21:00 · tooling content decision meta

Today's thread started as a single type error and ended up touching most of the devlog. Writing it down as one narrative, because the individual posts below each capture a piece but not how they chained together.

It started with Cannot find name 'fs'

A tooltip on scripts/banners/gen-banners.ts blamed a missing @types/node, which was already installed. The real cause was scope, not types: scripts/**/*.ts sat outside every tsconfig's include, so the editor fell back to a default project with no Node types at all — lesson: tsc/eslint blind spots. Fixing that immediately surfaced a second, weirder bug in web/app.ts: two contradictory errors depending only on a file extension, traced to a dead, forgotten web/tsconfig.json silently shadowing the real config that only the editor (not the CLI) ever saw — incident: dead tsconfig shadow.

That turned attention to how banners get their model

Looking at gen-banners.ts closely enough to fix its types raised an obvious question: why does every BannerDef hardcode a checkpoint via a one-off comment ("Juggernaut is good at cinematic scenes") instead of something matchable? So the same good_at-tag shape the main gallery's config/workflows.ts uses got applied to banners too — a pickWorkflow() scores each checkpoint's declared strengths against a banner's declared job and picks automatically — decision: good_at tags for banners.

Then: an audit of every banner's provenance

With a real selection system in place, the obvious next move was checking whether the devlog's existing banners actually deserved to stay. A pass through every post sorted banners into three buckets: ComfyUI-generated (fine), hand-picked/pre-pipeline AI art with no generation metadata ("unconfirmed"), and posts with no banner at all. The AI-generated-but-not-ComfyUI banners got rebuilt first and judged one at a time — not against their own prompt, but standalone: does this image, looked at cold, read as the thing the post is actually about? A few needed several rerolls (custom-node, race-condition) before a variant matched; most passed on the first or second try.

Then the big one: 53 banners in one batched pass

That left 44 "unconfirmed" banners and 9 posts with none. Rather than trickle these out, all 53 got drafted at once, and the BannerDef array was reordered — not renumbered, the array order is execution order — into three contiguous runs by resolved checkpoint (Juggernaut ×41, RealVisXL ×9, Illustrious/NoobAI ×3) so ComfyUI only loads a model 3 times instead of 53. Full story, including a near-miss where a throwaway inspection command accidentally re-triggered the whole batch, and the one banner (incident-the-backfill-that-ate-the-dates) that needed two rerolls because its original concept structurally required legible text SDXL can't render: the great banner refresh.

Today's addition: don't just claim the new banner is better — show it

Refreshing 44 banners is a claim ("the new one is more thematically accurate") that nobody reading the post can check without digging through git history. The old images were already kept on disk as img/*.legacy.webp rather than deleted — the same deprecate-don't-delete posture applied to content, not just master renders — so exposing them was just a matter of surfacing what was already there.

Each of the 44 refreshed posts now carries a legacyBanners array in its frontmatter alongside banner. The build stacks every version in the same box — the current one in normal flow, every older one absolutely positioned on top at opacity: 0 — with a small pill in the corner inviting a click. One shared script in the blog shell (web/blog.html) advances an active-slide index on click (or Enter/Space, for keyboard users), cycling current → most-recent-earlier → ... → oldest/original → back to current:

function advance() {
  active = (active + 1) % count;
  slides.forEach(function (s, i) {
    s.style.opacity = i === active ? '1' : '0';
  });
}

No framework, no per-post script, no network request on click — every version is already on the page, so each step is instant. Posts without a legacy banner (new content, or banners that were already ComfyUI-generated) render a plain <img> exactly as before; the compare widget only exists where there's actually something to compare.

Update, same day: this only handled a single prior version. Since a banner can now be regenerated more than once, gen-banners.ts auto-archives the outgoing image as <slug>.legacy-N.png (N auto-incrementing) every time it overwrites an existing one, and the blog build auto-discovers those siblings by globbing banners/<slug>.legacy-*.png — no frontmatter edits needed for the second, third, or Nth refresh. The legacyBanners frontmatter field still carries the one-off pre-pipeline exceptions (different filenames living in img/, from before banners had their own folder); auto-discovered and hand-authored entries are just concatenated, oldest first.

The throughline

None of today's changes were independently planned — each one surfaced the next by making a previously-invisible gap visible: a type error revealed a config blind spot, fixing the blind spot revealed a shadow config, cleaning up the banner script revealed an ad-hoc model-selection scheme, formalizing that revealed how much of the devlog's art wasn't from the pipeline at all, and fixing that revealed that "trust us, it's better" isn't as good as "see for yourself." Same instinct each time: when you notice a gap, look at what's actually behind it before patching the symptom.
