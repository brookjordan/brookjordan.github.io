Why your GPU memory measurements are lying to you

2026-07-06 12:00 · tooling lesson memory apple-silicon

The memory sweep started as a simple question: how much RAM does each model actually use? The answer — baseline − trough, where baseline is free RAM before the render and trough is the low-water mark during it — felt obvious. It was wrong.

The metric

psutil.virtual_memory().available returns the amount of RAM the OS considers immediately usable. On Windows and Linux with discrete GPUs, this is a reasonable proxy: VRAM and system RAM are separate pools, and loading a model pumps up VRAM while system RAM mostly stays put.

On Apple Silicon, there is no VRAM. It's unified memory — one physical pool shared between CPU, GPU, and the neural engine. "Loading a model onto the GPU" means the OS carves off a chunk of that same pool and hands it to the Metal driver. So the free-RAM number does reflect model load — but it also reflects everything else.

The noise

Every restart of ComfyUI stirs the pot. Loading a 10 GB model, then unloading it, leaves 10 GB of reclaimable cache that the OS hasn't yet reclaimed. Load a different model next and some of that cache might be evicted, some might not. How much free RAM you see before the next render depends on what the OS decided to do in the 8 seconds between stopping ComfyUI and starting it again.

On a live run:

krea2 baseline free RAM across three restarts: 22.1 GB, 19.4 GB, 28.7 GB

A 9.3 GB swing in "free RAM" — before a single byte of model data is loaded. The model didn't change. The machine did.

How it breaks the delta

The footprint formula is baseline − trough. If baseline is 22 GB and the model loads 10 GB, trough might be 12 GB and footprint is 10 GB. But if baseline happens to be 19 GB (because the page cache was less warm), trough might be 11 GB and footprint is 8 GB — for the exact same model.

Worse: a large model loaded in the previous measurement left a large warm cache. That cache can suppress the trough in the current measurement, making the current model look bigger than it is. The readings are contaminated across restarts.

What this looked like in practice

Running the same SDXL model three consecutive times on a fresh boot:

run 1: 15.6 GB
run 2: 18.6 GB
run 3: 15.8 GB

We assumed this was a real signal — maybe ComfyUI was occasionally offloading part of the model to CPU? The 3 GB gap looked deliberate. It wasn't. It was the page cache doing whatever it felt like between restarts, the delta absorbing all of it.

The right frame

The problem isn't the tool — psutil is doing exactly what it says it does. The problem is using a system-wide metric as a proxy for a GPU-specific allocation. On unified memory, that proxy holds on a quiet machine and breaks on a busy one.

The fix wasn't to run the machine quieter. It was to use the right signal entirely: the Metal driver's own accounting of what it has allocated. That's in the next post.
