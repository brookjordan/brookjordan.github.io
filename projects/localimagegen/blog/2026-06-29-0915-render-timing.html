Where did the time go? (per-phase render timing)

2026-06-29 09:15 · milestone rendering tooling

Something didn't add up. The undistilled heavyweights — chroma especially — climb to high step counts (knowing when to stop), and I'd lazily assumed "more steps" meant "proportionally slower." But the numbers refused to scale the way a naive seconds ∝ steps model predicts: a 30-step chroma cell was nowhere near 30/4 ≈ 7.5× its 4-step sibling.

The reason is obvious once you say it out loud. A render isn't all sampling. It's fixed overhead — load the checkpoint, encode the prompt, VAE-decode, save the PNG — plus a variable part, the sampling loop, which is the only piece that grows with steps. Double the steps and you double that slice only; the overhead is the overhead.

The trouble was I couldn't prove it. ComfyUI's /history hands back one number per render — the total wall-clock — and says nothing about where it went. We already stamp that total into every master filename as _t<dur>s_ and onto CellMeta (see everything gets a timestamp — but that post is about recording when something happened; this one is about how long each phase takes, which is a different question a single total can't answer).

The cheap win: timestamp ComfyUI's stdout

Before building anything, the five-second version. ComfyUI already narrates itself to stdout — "Requested to load…", the sampler progress bar, "Prompt executed in N seconds." Pipe it through moreutils' ts and every line gets a wall-clock stamp:

comfy-listen 2>&1 | ts '[%H:%M:%.S]'

Now the gap between the "loading" line and the first sampler step is the load time, by subtraction, right there in the terminal:

[09:14:02.402] model_type FLUX
[09:14:48.911] Requested to load AutoencoderKL    # ~46s of load before a single step
[09:15:08.044] 100%|██████████| 30/30 [00:19<00:00]
[09:15:31.677] Prompt executed in 89.21 seconds

Two shell gotchas cost me a couple of minutes, so they go here:

  • Quote the format. The [...] must be quoted, or the shell reads [%H:%M:%.S] as a glob bracket-expression and mangles it before ts ever sees it. Single quotes fix it.
  • Don't double-escape it inside an alias. Folding this into an alias whose body is double-quoted tempts you to escape the brackets — '\[%H…\]'. Don't: the single quotes already make the brackets literal, so the backslashes survive into ts, which then prints a literal \[ on the front of every line.

This is a human-eyeball tool — perfect for a spot check, useless for answering "across a thousand renders, where does chroma actually spend its time?" For that, lig has to record it.

The real fix: per-phase timing over the WebSocket

ComfyUI emits executing events on its WebSocket as it walks the graph — one per node, the moment that node starts. That's the hook. lig now:

  1. Submits every prompt with a stable clientId (a UUID) and opens one persistent WS (/ws?clientId=…), so ComfyUI routes those events back to us.
  2. For each prompt, trackPhases(promptId, graph) maps every node id → its class_type → a phase bucket: loaders → load, CLIPTextEncode → encode, the samplers → sample, VAEDecode → decode, SaveImage → save.
  3. On each executing transition it stamps the wall-clock and adds the elapsed time to whichever bucket just finished, resolving on execution_success (or the null-node "all done" signal).

The result — { load, encode, sample, decode, save } in seconds — is persisted on CellMeta.phases, right next to the total. It rides along with the live render in reconcile.ts: trackPhases fires in parallel the instant a rung is enqueued, the done-loop collects it (with a 5 s grace window in case the WS lags the HTTP /history entry), and closeWs() between models keeps it tidy.

HTTP stays the fallback — by design

The WebSocket is the enhancement, never a dependency. Two deliberate properties:

  • Graceful degradation. If the WS won't connect, drops, or times out, trackPhases returns null, phases is simply absent, and everything behaves exactly as before — the total still comes from HTTP /history, the master still gets stamped. No WS, no regression. This also covers the ugly case where lig was killed mid-pass but ComfyUI kept rendering: the next refreshData re-reads /history with no WS data and falls back cleanly.
  • HTTP fills what the WS can't. /history carries the authoritative total and the cold flag — execution_cached tells us ComfyUI reused a resident checkpoint (a warm load), which is exactly what explains a suspiciously tiny load number. stampItem merges the two: WS phases + the HTTP cold flag.

So the timing is layered: HTTP alone always gives total + cold; the WS adds the per-phase split when it's there. You can lose the top layer entirely and never see a difference in the output.

The payoff

"Where did the time go?" is now answerable per cell and per model. The early data confirms the hypothesis: load / encode / decode / save are roughly constant for a given model, and sample is the only part that tracks step count. Which is precisely why a 30-step chroma render isn't 7.5× its 4-step self — most of a short render is fixed cost, and only the sampling slice grows.

It also sharpens the frontier scheduler: it spaces rungs by total render duration, but a slab of that duration is overhead paid once per cell no matter the step count. Seeing the split is the first move toward planning against the part that actually scales — and toward an honest sequel to the step-count reckoning, where "slow" finally separates into "slow to load" and "slow to sample."
