Lesson: `workflows export` round-trips — delete the JSON to regenerate

2026-07-02 12:55 · lesson architecture

While moving the anime models to native builders I edited three builders in src/graphs.ts, ran lig workflows export, and expected fresh workflows/*.t2i.json. Nothing changed. The committed graphs still carried the old Lightning LoRA and the old prompts.

Why: export prefers the committed JSON

exportWorkflows doesn't call the builder directly — it calls buildGraph, and buildGraph's first move is:

if (fs.existsSync(jsonPath)) { load JSON, apply {{prompt}}/{{steps}}/{{cellbase}} placeholders, return }

So when a workflows/<model>.t2i.json already exists, export round-trips it — reads the committed file, re-applies the placeholder substitution, writes it back essentially unchanged. The programmatic builder is only the fallback, used when the JSON is absent (you can see it in the log: [graphs] no workflow JSON for <model>, using builder). Editing a builder and re-running export is therefore a no-op until the file is gone.

The fix, and why it's designed this way

Delete the stale template(s) first, then export falls through to the builder:

rm workflows/noobai.t2i.json workflows/noobai.t2i.high.json   # and illustrious, noobaivpred…
node src/cli.ts workflows export

This isn't a bug — it's the committed JSON being treated as the source of truth at run time. A human can hand-tune a graph in the ComfyUI UI and commit it; export must not silently clobber that from a builder it doesn't know is stale. The builder is scaffolding for bootstrapping a workflow, not an authoritative rebuild. The safe mental model: the JSON wins; to make the builder win, remove the JSON.

(Related trap for the SDXL family: sdxl/pony also emit a second <model>.t2i.high.json for the 8-step Lightning LoRA. Moving a model off the sdxl builder orphans that file — delete it too, or it lingers unused. That's why the eps anime models lost their .high.json in the same change.)

Guardrails added so the next person doesn't relearn this: the note now lives in config/workflows.ts (the file: comment) and in the exportWorkflows doc comment, right where you'd reach for the command.
