The error was the lock working perfectly

Run 2415 was refused because ComfyUI already belonged to run 2414. Read it quickly and it looks like a lock failure. It was a lock success, and we were the ones who had failed to queue politely.

Run 2415 was refused because ComfyUI already belonged to run 2414. That sounds like a lock failure if we read it quickly. It was the opposite. The lock had prevented a second workflow from interrupting the first one, which is precisely why it existed. Our mistake was treating refusal as the diagnosis rather than as the beginning of one.

What happened

The failing execution stopped at Assert normal ComfyUI ready. The recorded message identified the owner and the refused run: ComfyUI is locked by run=2414; refusing to interrupt it for run=2415 [line 3]. A later retry, 2417, met the same kind of boundary and produced the evidence used to verify the alert path.

The owner number mattered. Without 2414, we would know only that something held the lock. With it, we could compare executions and ask whether the owner was active, finishing, or abandoned. Another run being refused did not prove that the owner was stale. It proved that the protection had noticed an existing owner.

What the evidence changed

We kept three facts separate. First, a lock owner was recorded. Second, the new run was refused rather than allowed to interrupt it. Third, the alert eventually preserved those facts. None of those facts, alone, proves why the owner held the lock or whether it would later release it.

That is a useful distinction for an operational guard. A lock is a small piece of shared state that stops two jobs from changing the same service at once. Its refusal message is a safety result, not an invitation to delete the lock. The correct next step was to inspect the owning run and its lifecycle, not to erase the evidence so the next attempt could proceed.

The alert formatter initially made this harder by replacing the original error payload with the output from Release failed ComfyUI lock. Once it read the Error Trigger object directly, the notification retained the owner, run, node and full error. The mechanism and the reporting path were then both visible.

Where we left it

Execution 2415 demonstrates a real refusal and identifies run 2414 as the owner. Execution 2417 demonstrates that the alert could report the refusal accurately after the formatter change. The records do not, by themselves, establish whether 2414 was healthy, delayed or abandoned, and we do not call it stale merely because 2415 was refused.

The dry lesson is that a lock can look like an obstacle while doing the least surprising thing in the system. We wanted a new run. It wanted not to corrupt the run already inside the door. On this occasion, the lock won the argument and the evidence agreed with it.
