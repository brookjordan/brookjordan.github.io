The publisher that un-rejected a render

We rejected a banner, reset the entry, and the pipeline put the rejected image back and marked the work done. Two components, both behaving correctly, both describing the same file. A lifecycle fact needs exactly one owner.

We rejected a banner and replaced it. The pipeline then put the rejected one back, marked the work done, and moved on. Nothing errored. That is the part worth writing down.

What happened

P36's first render came from wan, a video model aimed at a still image, and it showed.

The rejected P36 render, preserved on the share as p36-banner.legacy-001.webp.

We rejected it, reset the entry, and left the corrected render to the next pass. That decision lived in render-state.json, which is the render controller's record of what it has built.

The publisher had its own idea. publish-staged.mjs had staged that file earlier, and when it next ran it found a staged file it had already seen, marked it published, and wrote the entry back to done. The reset disappeared. The rejected wan render was live again, and the record now claimed the corrected version had shipped.

That is worth sitting with: the reset and the resurrection were both correct behaviour for their own component. The renderer reset an entry it no longer trusted. The publisher published a staged file it had been given. Neither was confused about anything. They simply both believed the same file was theirs to describe.

What the evidence changed

We had built a publisher that owned lifecycle state, which is the actual mistake. Publishing is a fact about the world outside the pipeline: this image is now on the share and returns 200. Whether an entry is approved, rejected or awaiting a re-render is a different kind of fact, and it belongs to the plan and the render controller. When one file carries both, the last writer wins and the last writer is whichever process happened to run.

The publisher now publishes a staged file only when its state agrees with the plan. Model, step count and prompt hash all have to match, and a mismatch is skipped with a message rather than promoted to done. In parallel, render-banners.mjs --reconcile re-renders any done entry whose recorded model or steps disagree with the plan.

The prompt hash turned out to matter as much as the model, for a reason we had not thought through. Editing a prompt after a render leaves an image that no longer illustrates the text the manifest publishes. Both the publisher and reconcile compare sha256(prompt) against the recorded value, so a prompt edit now forces a re-render instead of quietly producing a provenance lie.

One exception is deliberate. A done entry with no recorded hash, which is only P47, adopted by hand from an interrupted run, is treated as unverifiable rather than stale. Re-rendering it would spend GPU time to prove a maybe, so it is left alone and build-manifest.mjs records promptHash: null for it. The gap is visible in the manifest rather than papered over.

Where we left it

The rejected render is still on the share, renamed rather than deleted, per the convention that a superseded banner stays as <id>-banner.legacy-NNN.webp. That keeps the failure linkable from prose, which is why the grey rectangle and this one can both appear in this blog at all.

The lesson generalises past this pipeline. A lifecycle fact needs exactly one owning file, and a component that writes a fact it does not own will eventually overwrite someone who does. Two processes agreeing about a file is not the same as two processes agreeing about its state.
