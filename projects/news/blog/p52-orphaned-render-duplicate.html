Killing the renderer orphaned its job, then queued a duplicate

The controller stopped. The render it had already handed to ComfyUI did not, because ComfyUI does not cancel work when the client walks away. The client can know what it asked for; only the server knows what is still queued.

We stopped the render controller to change its prompts. The controller stopped. The render it had already handed to ComfyUI did not, because ComfyUI does not cancel work when the client that submitted it walks away.

What happened

The controller submits a prompt to ComfyUI and then waits for the queue to drain. Kill the controller and the prompt stays in that queue, still holding a GPU slot, still going to finish. Restart the controller and it does what it is designed to do: it reads the plan, sees an entry that has not produced a master, and submits it again. Two identical prompts for P34's banner landed in one queue, one running and one pending.

The controller was not wrong, and ComfyUI was not wrong. The controller derives missing work from the plan, which is exactly the converge-from-disk design we want everywhere else. ComfyUI keeps running what it was told to run, which is what a render server should do. The gap is between them: the controller assumed that submitting work was the same as owning it.

What the evidence changed

The queue is the durable source of truth for what is actually pending, and the renderer is disposable. Once you write that down, the fix is small: the controller takes --clear-queue on start, which drops ComfyUI's pending work before it submits anything new, so a restart cannot stack duplicates. The orphaned render is discarded rather than adopted, which is the right call here because it was rendered from the prompt set we had just replaced.

The duplicate's raw PNG was pruned from the inbox rather than promoted to a master, so the evidence of the mistake does not become a candidate for the gallery. That matters: a duplicate that looks like a finished render is the kind of thing that gets adopted by a later pass that has no memory of the restart.

Where we left it

Stopping a long run is normal, and it should never be expensive. The rule worth keeping is that restart hygiene is a first-class part of the run, not an operator's private knowledge. The controller now carries it: a restart clears pending work before it adds any.

There is a broader version of this that turns up whenever a client submits work to a server and then decides when the work is done. The client can know what it asked for. Only the server knows what is still queued. If the client is going to derive its next move from what it asked for, it has to reconcile with the server first, or it will ask twice.
