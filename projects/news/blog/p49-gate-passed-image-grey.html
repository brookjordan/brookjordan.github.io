Forty-seven banners went up. The completion gate reported all clear, which was true, and two of the banners were a flat grey field reading "Image blocked by safety filter", which was also true. Both things passed every check we had. Only one of them was the thing we wanted.

What happened

The banner pipeline ends with a gate. It loops over the plan, finds each expected file, decodes it, and checks the canvas is the 1280 by 720 we asked for. All 47 decoded. All 47 were the right shape. The gate said so, and it was not lying. A safety-filter placeholder is a perfectly valid WebP at exactly the requested size. It is a grey rectangle of the correct dimensions, which is what a structural check is equipped to admire.

We found the grey one afternoon during a spot check, which is to say by looking at the images. P02 and P09 had both been sent to Ideogram 4 as ordinary prose. P02 came back as 6,582 bytes of grey with the filter message across the middle. P09 did the same thing at 6,094 bytes, a slightly different encode of the same nothing.

The file size should have given it away from the start. A real 1280 by 720 render in this corpus runs to hundreds of kilobytes. Six kilobytes is a postcard reading "wish you were here".

The P02 banner as it was served. A valid 1280 by 720 WebP, 6,582 bytes, and entirely grey.

What the evidence changed

We had been sending prose to a model that does not accept prose. The vendor's prompting guide states that Ideogram 4 "is trained exclusively on structured JSON captions", that passing plain text "will not work and will likely trigger a safety warning", and that "false positive rates for safety is high for non-json prompts". The prose prompt was not unlucky. It was invalid input being handled exactly as documented.

The guide also documents something we had not been using. A magic prompt converts ordinary prose into a valid JSON caption, and it ships as the default in the vendor's own inference script. Our engine called the raw model instead, so the escape hatch that exists for precisely this situation sat one layer above where our prompt was assembled. That is a live option for any future Ideogram work and it is worth reading before assuming the model is at fault.

The fix was the JSON caption set plus a detector that reads pixels. A validator that only asks whether a file exists at the right size cannot see a content failure, because a content failure can satisfy both. A prompt dialect belongs to a model's contract, not to taste. Sending prose to a JSON-only model is a schema violation wearing a prompt's clothes.

Both facts sat in the same vendor guide. Neither made it into the plan notes.

Where we left it

The rerun of P02 with a JSON caption produced a real banner. The detector catches the grey field. The pass finished 47 of 47 with no placeholders. We are keeping the grey one, shown above, because a failure that passes your tests is more instructive than the fixed render, and because "our validation said 47 green and two images were grey" is a sentence worth being able to point at.

Two lessons, then. Validate the pixels, not just the file. And a model's input format is part of its interface, so read it before blaming the seed.
