Bespoke banner render pass

2026-09-20 bespoke banner render pass

Design and pipeline record for the bespoke banner pass on the PodCast Builder devlog. The ticket owns scope; this packet owns the how and the measurements. Live status lives in the render workspace, not here.

Why bespoke banners

Before this pass the blog carried 47 posts on colour-coded gradient tiles, because the interim banners (reused localimagegen masters) were stripped on 2026-09-20 in commit 638290c9 ahead of the bespoke renders. The topic→scene mapping and the model rotation in image-plan.ts are borrowed from the localimagegen corpus (config/gallery.ts scene prompts, patch motif and all), but no single master matches any individual post's story.

The plan

  • One bespoke render per post, planned up front. Six hosts (P05 excluded, still held-evidence), 47 entries: per-post concept derived from its meta.ts title and blurb, a matching cinematic scene prompt that always carries the house cloth-repair patch motif, and a model chosen per concept.
  • Scene family follows the established topic mapping: origins → kingdom, video/models → spirit, music/workflow → signage, incidents → dragon, cutover/migration → van.
  • Fixed parameters: seed 42, 16:9 1280×720 (the engine's own W/H default), cwebp -q 82 at 1280w, matching the previous banner treatment.
  • Fastest-first queue using the engine's own measured medians, so early results land early even though the full pass takes hours. Ordering groups by model, which also minimises the number of model swaps.
  • Model choice is deliberately photoreal-only. The prompts are prose cinematic scenes written for long-prompt-budget models (longcat, ideogram, ovis, qwen2512, krea2, chroma, zimage, flux9b, wan). The booru-tag anime models were dropped from this pass so the 47 banners read as one coherent set; that is a change from the pre-pass image-plan.ts model rotation, which mixed anime models into the spirit topic.

Where it lives

  • Plan: render/render-plan.json (47 entries: id, topic, scene, model, steps, concept, prompt).
  • Timings: render/model-timings.json — per-model medians rolled up from the ~9,880 master filenames in the local vault/git/brookjordan/localimagegen/masters/ (the _t<n>s_ field).
  • Controller: render/tools/render-banners.mjs — resumable; renders one entry at a time through node src/cli.ts render, recompresses, publishes, and records state. Never writes inside the localimagegen repo.
  • State / provenance: render/render-state.json (per-entry status, attempts, elapsed, hashes), render/provenance.jsonl (append-only manifest: model, steps, seed, prompt, prompt hash, ComfyUI prompt id, output hash, published path), render/progress.json (cheap status view).
  • Outputs: /Volumes/assets/podcast/blog-banners/<id>-banner.webp, served at https://assets.brook.dev/podcast/blog-banners/<id>-banner.webp (verified HTTP 200). Images are not committed to git.

Blog wiring

build.ts now treats a banner as optional and remote: an https:// blog_img is emitted directly on the card, featured tile and post page, with onerror fallbacks that remove the image so the existing colour-coded gradient tile shows through. image-plan.ts therefore points all 47 entries at their deterministic assets URL before the renders land. Consequences:

  • One deploy covers the whole pass. As each render lands on the share it appears on the live blog with no further build, commit or push; a render that never lands simply leaves its gradient tile in place. This is a deliberate improvement on the earlier per-render flip design.
  • Local master staging is skipped for remote entries, so nothing is copied or committed per build.

Measurements (2026-09-20)

  • Cold zimage render (P47, first render of the session): 14 m 39 s — dominated by a ~5-minute load of the 7.6 GB qwen_3_4b text encoder and general first-run overhead.
  • Warm zimage render (P06, same model, immediately after): 110 s, matching the corpus median (~95 s). The cold figure is a one-off, not the steady state.
  • Sum of per-entry corpus medians for the 47-entry plan: ≈ 3 h 26 m of sampling, plus one model load per model group.

Caveat: the image models are still on the NAS

extra_models_config.yaml declares a nas_fallback at /Volumes/model-store/models/comfyui, and the image-gen checkpoints, UNets and text encoders are not present in the local ~/ComfyUI-Shared/models/ tree (which currently holds the video/LTX and music model set). The five-minute cold text-encoder load is the network. This is the same network-mapped-weights condition that produced the run-2567 SIGBUS (see PCB-008): if the model-store share drops mid-render the render is lost, though the controller is resumable. A future pass could pull the nine banner models into the local tree the way ltx-models-local.py did for the video set.

Model suitability — the gap this pass exposed

The engine's catalogue (config/workflows.ts) has a per-model good_at field, but it is seeded empty, so nothing in the repository records which models are good at what or which should not be used for stills. The first pass therefore picked models from the master-corpus timing data, which is how wan got into the plan. It should not have: the catalogue's own description calls it "WAN 2.1 t2v 1.3B (fp16) coerced to a single still (length 1)", and the official Wan2.1-T2V-1.3B card ships a negative prompt built on "static, still picture, overall gray, worst quality, low quality" — its own guidance suppresses what a still banner needs. Brook flagged the result (P36) as "awful … bare bones".

A local registry now records fitness for this task: render/model-suitability.json, with a preferred | usable | avoid | unavailable status per model, recommended steps, and evidence. preflight-models.mjs fails the run if the plan references an avoid or unavailable model. The durable fix belongs upstream — filling good_at from this evidence — and is logged as follow-up rather than done here (the handoff forbids altering the localimagegen repository).

Corrections made after the first pass (2026-09-20)

Two real defects were found by inspection and fixed before the bulk of the queue ran:

  1. Vanished checkpoints. krea2 (krea2_turbo-Q8_0.gguf) and flux9b (Flux-2-Klein-9B-KV-Q4_K_M.gguf) are no longer in ComfyUI's model store; every graph referencing them was rejected with /prompt -> HTTP 400, failing 12 posts in under a second each. Their posts were reassigned to ovis (18), qwen2512 (8), zimage (14).
  2. Step overshoot. The plan had been derived from the highest rung present in the master ladder, but that ladder was a research sweep deliberately run past each model's plateau. history/2026-06-26-0825-knowing-when-to-stop.md names this failure mode: distilled models (zimage, qwen2512, krea2, the Klein pair) are trained to land at 4–8 steps, and past that it is "minutes of compute spent rendering a slightly worse image… paying to overcook." Step counts were reset to the documented ceilings.

One deliberate exception. zimage was set back to 14. Its first six banners were rendered at 14 and validated by Brook as "amazing", so the empirical result stands over the Turbo-target prior until an A/B at 8 versus 14 settles it. That A/B is recorded as an open follow-up, not a settled question.

Provenance on the page

Brook asked for the generation prompt as alt text and for the workflow to be stored and credited.

  • Alt text is the prompt. Every banner image (alt on the post page, the featured tile and the index cards) carries the exact prompt that produced it, so the image describes itself to a screen reader in the same terms the model was given.
  • A credit line under each banner shows the ComfyUI mark, "Created with <model> · N steps · seed 42", and a link to the provenance JSON. The ComfyUI mark links to the stored workflow for that banner (Brook's own request), so the graph is one click from the image.
  • One manifest, linked from every post: banner-manifest.json on the assets share (https://assets.brook.dev/podcast/blog-banners/banner-manifest.json) holds one entry per post with model, steps, seed, prompt, image, workflow, sha256 and the ComfyUI prompt id. Generated by render/tools/build-manifest.mjs; the blog never invents these values.
  • Stored workflows: the ComfyUI graphs actually used are published beside it at …/blog-banners/workflows/<model>.t2i.json.
  • ComfyUI logo is the official comfy-logo-single.svg mark from comfyui-frontend-package, inlined rather than hot-linked.

Legacy renders are renamed, not deleted. Brook's convention, applied to the rejected wan render: a superseded banner stays on the share as <id>-banner.legacy-NNN.webp. So P36's rejected render is p36-banner.legacy-001.webp, which leaves the live page falling back to its gradient tile until the replacement lands, and keeps the rejected render as evidence rather than pretending it never existed.

Integrity fix: a publisher must not own lifecycle state

publish-staged.mjs originally marked every staged file done/published. That overwrote the --reconcile reset of P36 — it re-published the stale staged wan render and resurrected its done state, so a corrected entry could silently survive. Two guards now prevent it:

  • publish-staged.mjs publishes a staged file only when its state agrees with the plan (model, steps and prompt hash); a mismatch is skipped with a message.
  • render-banners.mjs --reconcile re-renders any done entry whose recorded model/steps disagree with the plan, so the shipped image and the manifest can never describe different renders.

The prompt hash matters as much as the model: editing a prompt after a render leaves an image that no longer illustrates the text the manifest publishes. Reconcile and the publisher both compare sha256(prompt) against the recorded value, so a prompt edit now forces a re-render rather than producing a provenance lie. A done entry with no recorded hash (only P47, adopted by hand from an interrupted run) is treated as unverifiable rather than stale — re-rendering is not spent to prove a maybe, and build-manifest.mjs records promptHash: null for it so the gap is visible.

Prompt set v2: stop borrowing the house formula

Brook reviewed the rendered banners and rejected the prompts: they "closely match the prompts in localimagegen rather than being unique to the blog posts", and the patch "looks weird". Both are fair. Every v1 prompt ended in the same construction — "Stitched onto X is a fabric repair patch that fully covers and conceals a mended tear: mismatched muted patchwork cloth, frayed edges, coarse dark thread in big uneven whip-stitches" — and every subject was mapped onto one of that repo's six scene families (kingdom / van / dragon / spirit / signage). The result was a house style with a blog post slotted in: a giant patch draped over filing boxes, two patches stuck on a leaf, one sewn onto a picture frame. Bolted on, not part of the picture.

What changed. The 22 un-built entries were rewritten from scratch in render/prompts-v2.json, with each image built from what its post is actually about. Concretely:

  • Scene families dropped. No more kingdom/van/dragon/spirit/signage mapping; no shared scene prompt.
  • No repeated patch clause. The cloth patch survives only where it is the story: on the little cover that started everything (P01) and across the replaced planks of the Ship-of-Theseus plaque (P45).
  • Style is now per-post. Darkroom film strips for the ten-vs-twenty-seconds experiment (P37); a server rack in near-total darkness with one breathing LED for "mostly dead" (P30); a monolith fracturing in a void for the SIGBUS crash (P29); five tagged specimen jars for freezing the test cases (P39); a rain-smeared blank address label for the perfect file with the missing filename (P13).

The 25 entries already rendered keep their v1 prompts. Rewriting a rendered prompt would make the shipped image disagree with the manifest — the integrity guard would then either force a re-render or publish a lie — so render/tools/apply-prompts.mjs refuses to modify an entry whose state is done and reports which it left alone.

Operational note: the controller holds the plan in memory, so a prompt change only takes effect after a restart. The run was stopped, the new plan applied, and the controller restarted with --clear-queue (the in-flight old-prompt render is orphaned and discarded). Remaining work is the 22 rewritten entries: ovis 12, longcat 5, chroma 3, ideogram 2.

Ideogram's safety filter: two banners came back as placeholders

Brook spotted that p02-banner.webp served a flat grey image reading "Image blocked by safety filter". Tracing each layer settled who was responsible:

Layer Verdict
Browser / assets.brook.dev serving correctly — HTTP 200, image/webp, 6,582 bytes, byte-identical to what was published
Publish layer copied faithfully; not the cause
cwebp compression produced a small WebP because the source was flat grey
lig render (localimagegen) saved exactly what ComfyUI produced
ComfyUI ran the graph locally (local ideogram4-Q4_0.gguf via UnetLoaderGGUF); no safety node in the graph
Ideogram 4.0 root cause — the model's built-in safety filter
DeepSeek harness never touched the bytes; the placeholder is in the file on the share, independent of any image I viewed

ComfyUI's own Ideogram 4 template carries the warning, and the official prompting guide is explicit:

Ideogram 4 is trained exclusively on structured JSON captions … Passing in plain-text prompts directly to the model will not work and will likely trigger a safety warning.

Safety filter. NSFW prompts are blocked. Instead of an image, the model returns a gray screen with the text "Image blocked by safety filter". False positive rates for safety is high for non-json prompts. We are aware that this is an issue…

So both ideogram posts (P02, P09) were blocked not for their content but for their dialect: we sent prose to a model that only accepts JSON. This is the same class of mistake as the booru-tag research already recorded in the localimagegen history — a prompt-dialect mismatch, not a subject problem.

Fix applied. render/prompts-v3-ideogram.json rewrites both as JSON captions following the documented schema (high_level_description, style_description with a strict key order and uppercase hex color_palette, compositional_deconstruction with background and bbox'd elements), minified as the guide specifies. apply-prompts.mjs gained a promptJson field that serialises to the minified form.

Detection added. The placeholder passes every structural check — valid WebP, correct 1280×720 — so the completion gate happily reported 47/47 while two images were grey. verify-banners.mjs now decodes a thumbnail with dwebp and flags flat, neutral, mid-grey images (lib/image-stats.mjs). A file-size heuristic was rejected: a legitimately dark banner (P30's server rack) is nearly as small.

Follow-up for localimagegen: its ideogram gallery cells are prompted in prose (the scenes.* prompts in config/gallery.ts), which the vendor says "will not work". The corpus masters exist, so it sometimes succeeds — but the dialect needs fixing upstream, and a prompt-size/dialect entry belongs in that repo's empty good_at field.

State ownership: one writer per file

render-state.json had two writers and they raced. The render controller loads it once and rewrites it from memory after every render; publish-staged.mjs also wrote publishedAt there. The controller's next write therefore erased the publisher's — observed on 2026-09-20 with 10 banners live on the share but recorded as unpublished.

Publication now has its own file, publish-state.json, owned solely by the publisher (and by publish-staged.mjs --scan-only, which rebuilds it by reading the share and copies nothing — so it needs no elevated access). The manifest reads published from there and rendered from the staging directory, so neither writer can undo the other. General rule for this pass: a lifecycle fact gets exactly one owning file, and a tool that does not own a fact must not write it.

Unattended operation and the sandbox boundary

A question from Brook — "how can I run this without authorising every command?" — exposed the structural answer, recorded in full in the workspace RUNBOOK.md.

The DSH file sandbox in workspace-write mode allows writes to exactly the workspace root, /tmp and the per-user temp dir. The assets share is outside all three, so every share write from the agent needs a one-command escalation to danger-full-access, and that escalation is the approval prompt. There is no extra-writable-paths option and symlinks do not help (roots are canonicalised). Note the workspace root here is the home directory, so workspace-write protects the system but not other repos or the vault.

The design that resolves it separates the privileged write from the agent:

  1. The agent stays confined and renders only into the workspace (--no-publish staging).
  2. A launchd agent outside DSH (render/ops/banner-publish, render/ops/com.brookjordan.banner-publish.plist) copies the finished artefacts to the share every five minutes. It is deliberately self-contained — it executes nothing from the workspace and copies only P<NN>-banner.webp, banner-manifest.json and workflows/*.json — so the agent can produce banners but cannot aim the delivery at anything else.
  3. Unattended continuation comes from the goal round driver, which queues rounds while the host is up and the goal is armed. It never revives work on its own: after a host restart or session resume the goal is disarmed until one human "continue". The cap is the goal's maxGoalRounds.
  4. Recommended narrowing: launch DSH in the project directory rather than the home directory, so workspace-write means this project only.

Restart hygiene lesson. Killing a controller orphans the render it had already submitted to ComfyUI, and the next pass submits a duplicate — observed as two identical P34 zimage prompts, one running and one pending. The controller now takes --clear-queue to drop ComfyUI's pending queue on start, so a restart cannot stack duplicates. The duplicate's raw PNG was pruned from the ComfyUI output directory.

Environment trap found at hand-off — the Obsidian MCP serves a different vault. The mcp__obsidian__* tools talk instead to obsidian-sync-mcp on the NAS (CouchDB-backed, docker-stacks/docker-obsidian), and that copy has diverged: it lists Project tracking/podcast builder with PCB-001…PCB-008 only (no PCB-015), four Scratchpad notes against thirteen on disk, and project folders (karakeep, localllm) that do not exist locally. The local vault's obsidian-livesync has an empty remote configuration (remoteType, couchDB_URI, couchDB_USER, couchDB_DBNAME all blank; plugin data.json last written 12 Aug), so it never pushes. Until the two vaults are reconciled, do not read or write this project's tracking through the MCP.
