Project Tracking

This folder is the backing store for the obsidian-project-tracking adapter. The portable planning and execution workflow belongs to project-tracking; this index records only how that state is represented through the Obsidian MCP.

Obsidian adapter contract

  • Each project has a README.md map and one child note per ticket.
  • Ticket files use <PROJECT>-<number> <title>.md, for example FSM-001 Audit live mail baseline.md.
  • Every ticket has frontmatter: status, wayfinder_type, assignee, blocked_by, and map.
  • Portable lifecycle labels are To do, In progress, Blocked, Done, or Out of scope; adapters own their stored values.
  • TaskNotes-identified tickets use the type/project-work-item tag and store the corresponding native values as todo, in-progress, done, out-of-scope, or (only for external holds) blocked.
  • blocked_by is a list of wikilinks. A dependency is the source of truth: TaskNotes derives whether todo or in-progress work is actionable in its Not Blocked view.
  • Not Blocked is not quite the adapter's frontier. Its filter is status != "done" plus every blocker resolved, so an out-of-scope ticket stays in the view while the frontier excludes it as non-actionable. The two agree everywhere in the vault today, and the gap is worth re-checking if out-of-scope tickets become common.
  • Verify a project's tickets, frontier, blockers and scratchpad metadata with ~/.bin/scripts/obsidian-frontier-audit.py "Project tracking/<project>" --packets. It reproduces the Not Blocked filter from TaskNotes/Views/tasks-default.base rather than approximating it, and reports map-link, blocker, duplicate-title and packet-indexing defects.
  • map frontmatter uses a one-item list containing the full vault-relative map path, for example README, so TaskNotes can map it to Projects and Obsidian resolves backlinks to the canonical map.
  • The assignee is the claim. Claim a ticket through the Obsidian MCP before working on it.
  • Ticket bodies contain the question or executable scope. When resolved, append a ## Resolution section, set status: Done, and add a one-line linked result to the map's Decisions so far.
  • A Wayfinder project may explicitly carry approved execution through completion in its map Notes. Otherwise Wayfinder remains planning-only.
  • Use the local vault for list, read, write, and edit operations — see Vault architecture and the MCP trap below before using any Obsidian tooling. Return the note deep link whenever creating or updating a map or ticket.
  • Record every finding — positive, negative, or inconclusive — in the project's Scratchpad and index it with a semantic link and one-line gist. The Scratchpad index is the first place an agent checks found and tested outcomes, before searching elsewhere or re-running an experiment; a tested-and-rejected approach must be indexed exactly like a win.

Vault architecture — local vault plus a synced NAS replica

Discovered 2026-09-20, resolved the same day. Read this before using any Obsidian tooling: two copies exist, and the MCP serves the replica, not the vault Obsidian has open.

The local vault is authoritative

  • Path: the local vault/Documents/Obsidian Vault
  • It is the only vault registered in ~/Library/Application Support/obsidian/obsidian.json, and Obsidian has it open. Confirmed by inspecting that file.
  • It is where this project-tracking contract lives and where current work is written.

The MCP serves a replica over the sync

  • mcp__obsidian__* talks to obsidian-sync-mcp running on the NAS, defined in git/brookjordan/docker-stacks/docker-obsidian/docker-compose.yaml, backed by CouchDB (vault name obsidian).
  • It is a replica, so it lags the local vault slightly. Usually harmless; do not reason over a replica you are mid-edit on.
  • It was badly stale before the fix — it had drifted to PCB-001…PCB-008 with four Scratchpad notes, while the local vault held PCB-015 and thirteen.

Why it had diverged (historical)

The local vault's obsidian-livesync plugin was installed and enabled but had no remote configured — remoteType, couchDB_URI, couchDB_USER and couchDB_DBNAME were all empty in .obsidian/plugins/obsidian-livesync/data.json. The local vault therefore never pushed. That was a configuration gap, not a version mismatch: the NAS image being current was irrelevant while no remote was set. Reconnecting the remote fixed it — see the bring-up section below.

What to use instead

  1. ~/.local/bin/obsidian-rest — talks to Obsidian's Local REST API on https://127.0.0.1:27124 (running; the insecure 27123 port is disabled). It reads the API key from the plugin's data.json and never prints it. Commands: status, get <path>, list <dir>, put <path> --file <local>. This is the correct interface — it goes through Obsidian rather than around it.
  2. Direct filesystem access to the vault path above.

mcp__obsidian__* is usable again now that sync is live, but it reads a replica: prefer the two local routes above for anything you are about to act on, and remember a write through the MCP lands in CouchDB and reaches this vault a moment later.

Two things to know:

  • The dangerous wizard choice: always pick connect to the existing remote. "Overwrite remote" and "Rebuild" destroy one side. With sync now established this only matters if it is ever reset.
  • LiveSync stores its settings encrypted. isConfigured: true, encryptedPassphrase set, and the plaintext couchDB_* fields all blank. Do not "repair" the blank fields.

Checking sync health

~/.local/bin/obsidian-vault-diff reports the same table. A rising only local / only remote count means sync has stopped; ~/.local/bin/obsidian-sync-check verifies the CouchDB target.

Verified healthy before setup: CouchDB 3.5.1 reachable, database obsidian present with doc_count=37473 (LiveSync chunks documents, so this far exceeds the ~1,205 note count).

The one choice that matters: in the LiveSync wizard pick the option that connects to the existing remote — not "Overwrite remote" and not "Rebuild". The remote holds notes this vault does not, so those options destroy data on one side.

Scale of the merge, measured before starting: local 1,176 notes; remote 1,205; 1,151 on both; 25 only local (would push); 54 only remote (would pull — these include the karakeep, localllm and most of hear transcription app projects, so they matter).

Helper: ~/.local/bin/obsidian-sync-check re-verifies the target and prints no secrets.

Unresolved

  • Whether the local vault or the NAS copy should be canonical after the merge — LiveSync will union them, but any note edited differently on both sides becomes a conflict to resolve by hand.
  • The local REST API plugin's self-signed TLS keypair was exposed in an agent transcript on 2026-09-20 and should be regenerated; note its bindingHost is 0.0.0.0, not loopback-only.

Tailnet name resolution

If ug-nas-x4800.tail4148b0.ts.net resolves to public addresses (103.84.155.x) rather than 100.84.158.31, MagicDNS is not installed in the Mac's resolver chain — the public answers are the Tailscale Funnel ingress, so services on 5984/8787 "resolve but never answer". Fix and evidence are recorded in the vault's AGENTS.md. Workaround that always works: use the IP.
