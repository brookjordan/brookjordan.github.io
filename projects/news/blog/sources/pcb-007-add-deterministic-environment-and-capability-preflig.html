Route and capability preflight verification

PCB-007 Add deterministic environment and capability preflight

Question

Can the podcast workflow determine, at the beginning of a run, which network routes, storage sources, models, custom nodes, and service endpoints are actually usable instead of relying on a fixed home-network assumption?

Scope

Add a preflight phase to the n8n podcast workflow that runs before expensive generation:

  • identify the MacBook's usable Ethernet, Wi-Fi, and Tailscale paths;
  • distinguish the NAS route available to the MacBook (LAN, Tailscale, or unavailable);
  • verify SMB share discovery and whether the expected model share is authenticated and mounted;
  • inspect local and NAS-backed ComfyUI model and custom-node paths;
  • start or query the exact ComfyUI profile that will process the run;
  • query ComfyUI's advertised loader models and record exact capabilities;
  • check the selected Ollama endpoint;
  • produce one capability manifest consumed by later branches;
  • fail early with checked paths and a precise reason when a required asset is unavailable.

The manifest must distinguish a file existing on disk from a model being registered by the active ComfyUI profile. It must not silently substitute another model or profile.

Current evidence

  • n8n runs on the NAS at 100.84.158.31, in the news-podcast-system Docker stack on a bridge network (app-network), with DNS pinned to the Tailscale resolver 100.100.100.100. Route probes therefore run from inside the container, which is the vantage point that actually makes the requests.
  • ComfyUI and Ollama run on the MacBook at 100.98.203.89.
  • SSH to the NAS is refused from the MacBook, but the MacBook runs sshd and the workflow drives it through a "MacBook SSH" credential, so MacBook-side checks are reachable from n8n.
  • The MacBook currently has no 10.10.10.x interface: it is on wireless LAN at 192.168.0.25, and its own 10/8 route points into a VPN, so the direct-Ethernet tier is both absent and mis-routed while unplugged.

Superseded claims (corrected 2026-09-16)

These earlier findings were wrong or are no longer true, and must not be relied on:

  • /Volumes/model-store is mounted. The exact LTX-2.5-Distilled-Q3_K_M.gguf is present at .../comfyui/unet/, with the matching gemma4-12b-with-proj-ltx-2.5 text encoder and both LTX VAEs.
  • The active ComfyUI profile does advertise the exact LTX GGUF. The earlier probe queried /models/diffusion_models, which filters .gguf files out; the correct check is the loader's option list, and UnetLoaderGGUF lists LTX-2.5-Distilled-Q3_K_M.gguf among 10 options.
  • Execution 2524's ECONNREFUSED on port 8087 was not a host-role mistake: nothing was listening, because yue-server was not running. Port 8087 is simply yue-server's default port (tools/yue-server.cpp:601), not a legacy artefact.
  • The workflow's YuE2 stage is still MiniMax: TEST — YuE2 synth is a ComfyUI node running minimax_music3_dit_fp16 with the "ComfyUI - music" credential. The migration was never completed.
  • The MiniMax-era lifecycle was not fully removed: the music profile switch is gone, but nine ComfyUI profile lifecycle nodes remain (normal start/assert/release, isolated LTX start/assert, and three restores).

Measured route reachability (2026-09-16, probed from the n8n container)

Role Ethernet 10.10.10.1 Wireless LAN 192.168.0.25 Tailscale 100.98.203.89
ComfyUI 8188 timeout (route) 200, 21 ms 200, 27 ms
YuE 8087 timeout (route) ECONNREFUSED (service) ECONNREFUSED (service)

The failure kind separates the two problems cleanly: a timeout means the route is unusable, while ECONNREFUSED means the route is fine and the service is down. Wireless LAN is the best available tier and is marginally faster than Tailscale.

Proposed decision

Use a route-and-capability manifest rather than hard-coded serviceHost, comfyHost, or llmHost assumptions. The preflight may use SSH to inspect the MacBook because that is where ComfyUI runs, while n8n-local checks inspect NAS-side paths separately. SMB reachability, authentication, mount visibility, and ComfyUI registration remain separate checks.

Completion criteria

  • A run at home Ethernet, Tailscale-only, and NAS-unavailable conditions selects or rejects routes deterministically.
  • Required assets report their source (local, nas, or unavailable) and exact checked locations.
  • LTX preflight remains fail-closed for LTX-2.5-Distilled-Q3_K_M.gguf.
  • The first failure message identifies whether the cause is network routing, SMB authentication, missing mount, missing file, missing custom node, or ComfyUI registration.
  • A real manual execution records the manifest before media generation begins.

Parser trap worth remembering

TEST — YuE2 materialise audio never worked: it called String(...) at the top level of an n8n expression and aborted with ExpressionExtensionError: invalid syntax before running. Nodes that call String(...) inside an IIFE are fine, and || is fine (it is used in Add iso date, which earlier executions passed). The rule is that top-level function calls on non-$ globals break the expression syntax extension. The command is now plain concatenation, proven end to end.

Decided: keep the ComfyUI profile lifecycle

The nine residual lifecycle nodes stay. They are not MiniMax-era cruft. The isolated LTX profile is deliberate and self-verifying: Assert isolated LTX ComfyUI ready pins ComfyUI 0.35.0, asserts the running argv contains --disable-all-custom-nodes, ComfyUI-GGUF and the /comfyui-ltx.db database, and checks that UnetLoaderGGUF, CLIPLoader and VAELoader advertise the exact LTX GGUF, text encoder and VAE, plus the native LTXVCropGuides and SaveVideo nodes. That is a stronger capability gate than the manifest's own LTX check, and it is the mechanism that keeps the LTX profile isolated from every other custom node. The MiniMax-era music profile switch, which was the aggressive behaviour Brook objected to, is already gone — as is the port 8189 it depended on.

Blocker found 2026-09-16: container DNS, and it is breaking production

The test run of 2k7x4U8GgLeSFpRE (execution 2543) cleared ComfyUI restart, Start YuE2 server and the endpoint manifest, then failed at the first external call, Fetch Repo Folders, after 25 s with The DNS server returned an error, perhaps the server is offline.

Diagnosis, using Execute Command inside the n8n container:

  • The container's only resolver is Docker's 127.0.0.11, which forwards to 100.100.100.100 (Tailscale MagicDNS), because that is the sole entry in the dns: list of both the n8n and n8n-worker services.
  • nslookup api.github.com 100.100.100.100 returns SERVFAIL from inside the container, but the same query succeeds from the MacBook (20.205.243.168). The tailnet DNS configuration is therefore fine; the NAS Tailscale container's forwarding is broken.
  • 1.1.1.1, 8.8.8.8 and the home gateway 192.168.0.1 all resolve public names from inside the container, so outbound DNS is not blocked — only the configured resolver is broken.
  • IP-based calls are unaffected, which is why the ComfyUI, Ollama and YuE2 path worked throughout and the fault looked selective.

Consequences, verified from execution history:

  • Production S9v0UpCVYcrtVJH4 has been failing since 2026-09-14. Last success was execution 2493 (2026-09-14T20:30). Executions 2526, 2529, 2531 and 2549 all errored, and 2549 failed at Fetch Repo Folders with the identical DNS error and the same ~25 s delay.
  • The failure alerts are down too. The alert workflow kyZcvt1CxQq8FQ0j fails in Send failure alert with the same DNS error, because api.telegram.org also needs public DNS. It last succeeded at 2530 (2026-09-15T20:34); 2532 and 2550 errored. The outage is silent: broken runs and broken notifications share one cause.

The container cannot repair itself: it runs as uid 1013, so /etc/resolv.conf is not writable, and NODE_FUNCTION_ALLOW_BUILTIN is unset, so a Code node cannot call dns.setServers.

Fix prepared, not yet applied

/Volumes/docker/n8n/docker-compose.yaml now lists a public fallback second for both services (backup at the local vault/tmp/docker-compose.n8n.backup.yaml):

    dns:
      - "${TAILSCALE_DNS_SERVER:-100.100.100.100}"
      - "${PUBLIC_DNS_SERVER:-1.1.1.1}"

The YAML parses and both services carry both resolvers, but the change needs a stack redeploy to take effect. Faster alternative: restart the NAS tailscale container, which should restore MagicDNS forwarding by itself and unblock everything without touching n8n.

Services to restart after changing DNS: n8n and n8n-worker. Worth confirming afterwards that Docker's embedded resolver really does fall through to the second server on SERVFAIL; if it does not, swap the order so the public resolver is first.

Root cause: Mullvad retired its public DNS, and the NAS was pointed at it

Mullvad shut down its public encrypted DNS service. Announced 3 September 2026, with manual users given until 2 November 2026 to migrate; Mullvad is redirecting those resources into sponsoring the Quad9 Foundation. Its resolvers 194.242.2.2 and 194.242.2.3 now return REFUSED.

Verified from both sides:

Query api.github.com via MacBook NAS container
194.242.2.2 (Mullvad) REFUSED REFUSED
194.242.2.3 (Mullvad) — REFUSED
192.168.0.169 (LAN) resolves resolves
192.168.0.1 (gateway) resolves resolves
9.9.9.9 / 149.112.112.112 (Quad9) resolves —
100.100.100.100 (MagicDNS) resolves SERVFAIL

The breakage window matches the shutdown: production 2529 (15 Sep 20:30) still got through every network call and failed on an unrelated Ollama timeout; by 2531 (16 Sep 04:10) both the run and its alert were DNS-failing.

The tailnet's own DNS config is empty — nameservers: {"dns": []}, split-dns: {}, searchPaths: [], magicDNS: true — so MagicDNS has no configured upstream and falls back to each host's own resolvers. The MacBook has working DHCP resolvers to catch it; the NAS has only the dead Mullvad addresses, so it SERVFAILs. Executing Command inside the n8n container confirmed all of the above from the NAS side.

Changing the address shown under "Local DNS settings" in the Tailscale DNS console to 192.168.0.169 did not fix it: MagicDNS still SERVFAILs and the API still reports zero configured nameservers, so that field is not the upstream MagicDNS uses. The dead address must be configured in the NAS host's own network settings (UGOS network DNS), which is what MagicDNS forwards to.

Fixes, in order of preference:

  1. Replace the Mullvad addresses in the NAS's own DNS configuration with Quad9 (9.9.9.9, 149.112.112.112) — Mullvad's own recommendation, and verified resolving from this network — or the LAN resolver 192.168.0.169.
  2. Redeploy the n8n stack so it carries its own resolver (already written into the compose, see below) and stops depending on MagicDNS entirely.
  3. Restart the NAS tailscale container if its daemon has stopped applying control-plane DNS updates.

Attempting to set it via the API returned HTTP 403 calling actor does not have enough permissions, so the OAuth client used here is read-only; the change needs the admin console or a client with DNS write scope. The compose fallback above remains worth doing as defence in depth, so that n8n does not depend on MagicDNS health at all.
