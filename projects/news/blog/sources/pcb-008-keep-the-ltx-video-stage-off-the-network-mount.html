LTX mount incident and cleanup reference

PCB-008 Keep the LTX video stage off the network mount

Question

Can the podcast workflow make the video stage depend only on local disk, so that a 26.8 GB read over SMB/Tailscale — the condition that crashed ComfyUI with SIGBUS when the share dropped — is no longer on the critical path?

Scope

  • Fetch the four-file LTX model set to ~/ComfyUI-Shared/models as a first-class workflow step, overlapping script, TTS and image generation rather than blocking on it.
  • Make the transfer resumable, so a dropped SMB session continues instead of restarting 26.8 GB.
  • Run the transfer detached from the workflow run, so it survives a failed or cancelled execution.
  • Verify the finished files against the content-addressed model store, not just against their size.
  • Gate the video stage on that verification: fail closed with a precise reason rather than silently reading from the NAS.

Design decisions

Detached sync with a status file, not a blocking node. The handoff proposed an SSH node that starts the copy and returns. That is necessary but not sufficient: the copy must also outlive the run that started it, and be resumable across runs. ltx-models-local.py start launches a detached process and writes JSON status to ~/.local/state/ltx-models-local/status.json; gate blocks until the set is local. This also means the gate is idempotent — a completed set makes it a no-op.

Verification is free, because the store is content-addressed. Every model in models/comfyui/... is a symlink into objects/sha256/<aa>/<sha256>, so the object path is the expected digest. The sync copies the object and names the destination after its own digest, then verifies; a half-written file can never be mistaken for a complete model. This removes the need for a separate checksum manifest.

Local precedence is confirmed by reading the code, not assumed. folder_paths.get_full_path iterates folders[0] in insertion order and returns the first os.path.isfile hit. extra_models_config.yaml declares comfyui_desktop (with is_default: "true"), then nas_fallback, so local is inserted first and wins. A missing base_path is simply not scanned. This supersedes the earlier unverified claim in the map that "ComfyUI already prefers the local model directories, so no configuration change is needed".

NAS SSH is not an alternative. Port 22 on 100.84.158.31 is filtered from the MacBook, so rsync-over-SSH to the NAS is unavailable and SMB remains the only bulk path.

Why the transfer keeps failing — evidence, not the inherited hypothesis

The handoff's leading hypothesis is that a sustained multi-gigabyte read destabilises the NAS. The client-side evidence gathered on 2026-09-17 does not clearly support that, and points instead at the network path as the first thing to fail:

  • The writer's errors are [Errno 9] Bad file descriptor followed by [Errno 60] Operation timed out. A NAS going away does not normally hand the client EBADF mid-read; that is the SMB client's socket being torn down under it.
  • During the observed failure, tailscale status still listed the NAS as active with a direct path (101.100.161.237:41641), which is the control plane's view and is not conclusive on its own, but it is inconsistent with a node that has just died.
  • The NAS became reachable again within roughly two minutes, with no evidence of a reboot cycle.

Network conditions on the MacBook's current network that plausibly explain it:

  • tailscale netcheck reports MappingVariesByDestIP: true. That means a symmetric NAT: the apparent source IP changes per destination. Symmetric NAT destabilises Tailscale's UDP hole punching, so a direct path can be established and then quietly break under sustained load.
  • The direct endpoint is a public address (101.100.161.237), and the nearest DERP is Singapore, so all of this is real internet transit from a corporate network, not the home LAN.
  • The failure occurred around 10.7 GB into a transfer at roughly 15–25 MB/s. That is the classic shape of a middlebox deciding a long-lived high-throughput flow has had enough, rather than a storage node falling over.

Not yet proven either way. Confirming a path failure needs the NAS reachable from another tailnet node at the moment the MacBook cannot reach it. ~/tmp/watch-nas-path.sh samples tailscale status path type, tailscale ping, and TCP to 445/9443, and records whether the peer flips from direct to relay — a flip would be strong evidence for the path. NAS-side evidence (uptime, OOM, SMB daemon restarts) would settle it from the other direction, but SSH to the NAS is filtered, so it has to come from the NAS itself.

This matters for the fix: if the path is the fault, throttling may not be enough and the answer is a resumable transfer plus retry (which is now built), whereas if the NAS is the fault, the answer is NAS-side.

Resume behaviour

The transfer is resumable and supervised:

  • sync copies into a content-addressed object file and resumes from a 16 MiB-aligned offset, re-reading a 256 KiB overlap on both sides to reject a corrupted prefix before appending.
  • A file is only promoted to its destination name after its SHA-256 matches the digest encoded in the store's own symlink path, so a torn copy can never be mistaken for a complete model.
  • Each file gets four in-attempt retries with a remount between them.
  • start --supervise wraps that in a supervisor that keeps re-running sync with exponential backoff (30 s doubling to 900 s), because one sync giving up after four attempts is not enough when the path drops every few gigabytes. A six-hour budget and 40 attempts are the defaults used by the workflow kickoff.
  • The gate restarts an interrupted sync in supervised mode, so a run that begins while the transfer is stalled revives it rather than failing immediately.
