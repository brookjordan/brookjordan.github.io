Song path control surface

What the song path can actually control

The podcast song generator renders through a local C++ port of YuE2, a text-to-song model, and reaches it from an n8n workflow. Four nodes matter: Generate song spec asks a language model for a JSON brief, Parse song spec clamps that brief, YuE2 synth POSTs a request to the renderer, YuE2 materialise audio polls the job and writes a file.

The headline is that the generator's control surface is far narrower than its vocabulary suggests, and that the error runs the opposite way from the usual intuition. The renderer accepts a score and honours its key, metre and tempo exactly. The workflow neither sends a score nor persists one. Everything the pipeline appears to fix about key, metre and tempo travels as prose inside a single comma-separated style string, and the renderer's own symbolic planner overwrites it.

1. The channels

Five channels exist. Naming them precisely is most of the audit, because several of the axes below are only distinguishable by which one carries them.

Channel What it is Field
Style string Comma-separated descriptors under [Tags], reaching the model verbatim style
Lyrics string The words to sing, with structural tags, verbatim under [Lyrics] lyrics
ABC score A symbolic plan tokenized into the prompt as-is, replacing the planning stage abc
Dedicated field Typed request parameters the pipeline reads directly duration, steps, seed, lm_seed, cot, cfg_scale, output_format, peak_clip, mp3_bitrate, semantic_tokens, lm_batch_size, synth_batch_size, abc_sampling, semantic_sampling
Nothing No channel exists —

The renderer's request schema is authoritative in src/request.h and src/request.cpp of the port, and documented in its architecture document. That document states the whole contract plainly: "Every field has a default. Omitting a field is strictly equivalent to sending it with its default value. Only style or lyrics is required" — see yue2.cpp docs/ARCHITECTURE.md.

Two details of prompt assembly decide which axes are hard. First, style and lyrics reach the model verbatim: "The style and lyrics text reaches the model verbatim: the protocol defines no caption cleaning and no lyrics normalization." Second, the score slot is a real slot, and supplying it removes a whole generation stage: a non-empty abc "replaces the planning stage: the score is tokenized into the prefix as is."

2. Axis by channel by strength

Strength is graded as the brief defines it. Hard means a typed field the renderer parses and acts on, or a score the semantic stage reads directly. Soft means prose the model may or may not act on. Unavailable means no channel reaches it. Unknown means the evidence does not settle it.

The pattern is consistent: everything that is a name is soft, and everything that is a number or a score is hard. Style, mood, instrumentation and production are names. Key, metre, tempo and register become numbers only inside an ABC score.

3. The ABC round trip

This is the only hard channel for key, metre and tempo, so it deserves precision.

Step Mechanism Evidence
Produce The autoregressive stage writes the score when the abc slot is open. cot: "full" asks for a chord-annotated transcription, "melody" for melody only, "off" closes the slot immediately src/prompt.h instruction table
Obtain The score travels with the track. yue-plan --out score.abc writes it standalone; GET /job?id=N&result=1 returns multipart/mixed with "one application/json replay request part (the request carrying the semantic stream, the score and the seeds of that track)" docs/ARCHITECTURE.md, README
Edit Plain text. The port's own tooling transposes whole octaves, "the only hard lever on the sung register, because the semantic stage takes its pitches from this melody" port tooling header comment
Send back Put the edited text in the abc field. A helper reads a base request, attaches the score, and reports the score's own M: and Q: — "Keeps the score's tempo and meter, so only the audio stage is re-conditioned" port tooling header comment

What survives a round trip. Everything the ABC parser reads. In the observed scores the header is:

X:1
T:
M:2/4
L:1/32
Q:1/4=107
V: Vocal clef=treble name="Vocal Melody" snm="Vocal"
V: Ins clef=treble name="Ins Melody" snm="Inst."
K:D

Meter, tempo, key, note lengths, rests, ties, dotted values, octave markers and chord symbols all survive, because the score is tokenized into the prefix as-is and the model consumes it as text. The score is also the only place where an explicit mode can be written: ABC K: accepts a mode suffix, so K:DDorian names a scale rather than a key signature.

What is ignored. X:, T:, the V: voice declarations and % comments are decorative — they are carried but not parsed by the renderer, which has no ABC grammar at all. It tokenizes. The port contains no tempo, meter or key handling anywhere in its source; those live entirely in the model's reading of the text.

Which fields the score can authoritatively set. M: sets metre and Q: sets tempo, both hard, both confirmed by the planner-skip path. K: sets key and, in practice, mode. L:, note values and octave markers set the melodic rhythm and register. The empirical support is that a re-submitted score renders deterministically from its own codes, so the score's tempo is the code timing, not a request.

4. The clamps, one at a time

Each clamp lives in the Parse song spec Code node. The verdicts are as follows.

Clamp Value Verdict Evidence
Two-section maximum MAX_SECTIONS = 2, .slice(0, MAX_SECTIONS) Self-imposed The renderer accepts a free-text lyrics string with no section limit. Upstream examples show longer forms
Four lines per section MAX_LINES_PER_SECTION = 4, .slice(0, MAX_LINES_PER_SECTION) Self-imposed Same; nothing in the request schema counts lines
Verse-and-chorus only if (name === 'verse' || name === 'chorus') Self-imposed, but built on a real narrowness Upstream documents [Verse]/[Chorus] as examples and gives no closed list. The comment claims "the only tags it understands are [verse] and [chorus]" — a stronger claim than the upstream docs support
Twelve-key list literal array of 12 Self-imposed The renderer has no key field; any key is expressible in style or in abc K:
{4,3,6} time signature ['4','3','6'] Self-imposed No time-signature field. A planned score wrote M:2/4, which the clamp can never produce
90–140 BPM clamp bpm < 90 || bpm > 140 → 120 Self-imposed No tempo field. Scores observed at 70, 77 and 186
Lyric length limit .slice(0, 1600) Self-imposed, with a real ceiling behind it The 4096-token planning budget and 9000-frame (6 min) semantic budget are real; 1600 characters is far below them
Duration choice vocals ? 360 : 12 Real field, self-imposed value duration is a typed field, but its "preset of the semantic stage caps it, so the shorter of the two wins", and 9000 frames at 25 fps = 360 s

The {4,3,6} and 90–140 verdicts are not inferences. Across 95 renders spanning five quantisation levels, planned scores carry metres including 2/4, 3/4 and 4/4, and tempi of 70, 73, 77, 95, 107, 114, 120, 124, 128, 155, 160, 165, 170, 175, 176, 178 and 186 BPM. A clamp to {4,3,6} and 90–140 cannot express the renderer's own output. The clamp constrains the workflow, not the model.

The comment above the section-tag code, quoted

YuE's input contract is narrow: the lyrics must contain verse and chorus sections and the only tags it understands are [verse] and [chorus]. Anything else reaches the model verbatim, so an [Intro - pulsing synth bass ...] tag makes it perform that direction and spend the song's opening on an instrumental intro -- which is how a 40 s cap ended up consuming itself before any vocal arrived. Keeping two short canonical sections is what makes the finished song short, so no duration cap is needed to bound it.

Is it still justified? Half of it is, and the half that matters is the weaker half. The observation is sound: a descriptive tag does reach the model verbatim and does steer it, which is exactly why the channel is useful rather than dangerous. The conclusion drawn from it — that only two tags are understood — overstates what is documented. Upstream says "Put the words to sing in lyrics, with section tags such as [Verse] and [Chorus]." That is an example list, not a closed set, and no closed list is documented anywhere. The two-section rule is a self-imposed clamp justified by an undocumented claim about the model's tag vocabulary.

The second half is obsolete on its own terms. The comment says the short lyric is what bounds length so "no duration cap is needed", and the code below it then sets yueDuration = 360 — the maximum the semantic stage will produce. The cap was not removed; it was moved to the model's context budget.

5. Seed, steps, cfg_scale, duration

Field Workflow sends Default What it does in practice
seed not sent -1 → random mt19937 seed for the acoustic noise. Does not affect the score or the length. Splitting it from lm_seed is the port's own addition; the release runs both from one
lm_seed not sent -1 → random Philox key for the token draw: "the score, the melody and the length come from this one." The only way to reproduce a composition
steps 32 32 Midpoint steps of the flow-matching ODE, minimum 1. Affects acoustic fidelity only. 32 is the checkpoint value
cfg_scale not sent -1 → protocol Guidance on the semantic stage. Negative resolves to 1.0 in full/melody and 1.01 in off; "Exactly 1.0 keeps a single branch and halves the decode cost." So the pipeline runs unguided: the style string is a suggestion the sampler is not pushed toward
duration 360 (vocals), 12 (bumper) 360.0 "Target length. The preset of the semantic stage caps it, so the shorter of the two wins and the model can still end the song earlier on its own." 360 s matches the 9000-frame cap at 25 fps — the pipeline asks for the maximum

The consequence of the cfg_scale default is the single most important thing on this page. A workflow that never sets it gets no classifier-free guidance on the semantic stage, which means style adherence rests entirely on the model's own prior. Every soft channel above is softer than it looks.

6. What this means for the catalogue waves

Wave A, music styles. Worth building, and the only wave that is unambiguously safe. Style and sub-genre ride the style string, which reaches the model verbatim. The catalogue should describe features rather than name genres: "a named style alone is not an instruction." Expect soft adherence, because guidance is off.

Wave B, stanza and line structure. The most wasted wave if built against the current pipeline. Two sections of four lines is the whole reachable space. The catalogue work is still correct as research, but it cannot be used until the MAX_SECTIONS and MAX_LINES_PER_SECTION clamps are lifted, and it should be written against the renderer's real capacity, not the clamp.

Wave C, instruments and production. Build it, but grade it honestly. Instrument names, production adjectives and arrangement vocabulary are all soft-only, all in the same style string, competing for the model's attention with genre and mood. Density is the one axis with a hard back door: event density is legible in an ABC score even though timbral density is not.

Wave D, scales, melody and metre. The highest-value wave, because it is the only one with a hard channel. Key, mode, scale, metre, tempo and register all land hard through abc. A scale catalogue is worth much more than a tempo table, since tempo is already a single number.

Soft-only axes. Style, sub-genre, instrumentation, production texture, mood, era, vocal type, vocal delivery, language, structure as prose, section tags beyond verse/chorus, line length, and arrangement density. A catalogue of values for these axes reaches the model as one undifferentiated comma-separated string with no guidance applied. That is not a reason to skip the catalogues; it is a reason to keep the entries described and specific, since specificity is the only lever a soft channel offers.

Unavailable. Microtonal and non-12-TET tuning. ABC is a 12-tone notation and nothing in the request schema reaches pitch representation. Any catalogue of non-Western tuning is unusable against this renderer as it stands.
