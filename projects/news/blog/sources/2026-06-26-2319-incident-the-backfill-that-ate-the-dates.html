Date backfill incident

We wanted blog posts to sort by time, not just date. Two posts written hours apart on the same day were tied, and the tie-break (alphabetical filename) put the wrong one on top. Easy fix: give each post a full timestamp. So I wrote a backfill script to stamp every post's date: frontmatter with a real time — and reached for the obvious source: git.

// the mistake
git log --follow --diff-filter=A --format="%aI" -- "$file"  // first commit that ADDED the file

"When was this file first committed?" feels like "when was it written." It is not.

What broke

Twenty-one posts came out stamped with the exact same timestamp: 2026-06-25T21:36:56. They'd all been imported in one big commit (docs: … import the devlog), so git honestly reported the only time it knew — the commit's — for every one of them. The tie we were trying to break got worse: now 21 posts were tied.

Worse still, the backfill overwrote the whole date: field, including the date. Posts that were deliberately backdated — the-spark is dated 2026-06-22 — got rewritten to the import commit's date, 2026-06-25. The spark jumped three days into the future. I'd corrupted the publication dates while trying to add times.

The hunt

Brook caught it immediately ("too many 2026-06-25-2136-…") and pointed at the right question: if commit time is fatally broken, what else knows when these files were born? We checked the candidates:

  • git commit time — the culprit; one timestamp per commit, not per file.
  • git reflog — local op history, still not per-file authoring.
  • mtime — useless now: my own scripts (backfill, rename, link-fix) had just rewritten every file, so every modification time was today.
  • birth time (stat -f %SB) — intact. Renaming with git mv and editing in place both preserve the inode on APFS, so the original creation moment survived everything I'd done to the files. And it was distinct for every post: 17:22:41, 17:23:01, 17:23:08, … a believable authoring sequence, not a wall of identical stamps.

The fix

Two sources, each for the half it actually knows:

  • date ← the filename's YYYY-MM-DD prefix (the intended publication date — authoritative, and untouched by the import).
  • time ← the file's birth time (distinct per post; correct relative order).
const datePrefix = file.slice(0, 10);                         // 2026-06-22  (publication date)
const hms = stat('%SB', '%H:%M:%S', file);                    // 18:14:07    (when it was born)
const iso = `${datePrefix}T${hms}+08:00`;                     // 2026-06-22T18:14:07+08:00

Re-ran backfill → re-derived the HHMM filenames → repaired the cross-links (slug-based this time, so it's robust to whatever the HHMM happens to be). Zero duplicate timestamps, every backdated post back under its real date header.

The lessons

  1. "First commit" is not "authored." Commit time answers when did this enter version control, in whatever batch it rode in on. For per-item authoring time it's worse than nothing — it actively lies, and it lies identically for everything in the same commit.
  2. Don't widen a field you mean to narrow. I only needed the time. By rewriting the whole date: line I let the bad source clobber a good value (the date) that was never in question. Touch the smallest thing.
  3. Birth time is a quiet hero — and a fragile one. It survived here because every edit was in-place or a rename. A cp, a fresh git clone, or a checkout onto a new filesystem would have reset it to "now" and this signal would be gone. We got lucky; the real fix is to record the time when the post is written (the timestamp-everything rule), not to reconstruct it forensically later.
  4. A second pair of eyes beats a clever script. The bug was obvious the instant someone looked at the filenames — "too many 2136" — even though every individual step had looked fine. Surface your derived data somewhere a human will glance at it.

The irony isn't lost on me: the post right next door is What time did that happen? (Everything gets a timestamp). We had the rule. The blog just wasn't living by it yet.
