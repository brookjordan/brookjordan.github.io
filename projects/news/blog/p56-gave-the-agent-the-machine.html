We gave the agent the machine, then changed our minds

Every write to the assets share needed a human to approve it, one command at a time. The fix was not a wider permission but a narrower job: a small privileged process outside the sandbox, and an agent that never needs the share.

Every write to the assets share needed a human to approve it, one command at a time. The obvious reading is that the sandbox was in the way. The useful reading is that we had given the agent the wrong job.

What happened

The file sandbox in write mode allows writes to the workspace root, the temporary directory, and the per-user temp area. The assets share is outside all three, so the publisher's copy step was denied every time and had to be escalated command by command to full access. That escalation was the approval prompt.

None of that is a sandbox defect. Roots are canonicalised, symlinks do not help, and there is no extra-writable-paths escape hatch, which is the shape you want from a boundary. The problem was the design on our side: the thing that rendered images was also the thing that delivered them, so the agent needed the share. An agent that needs the share is an agent that has to be trusted with it.

What the evidence changed

The fix was to split the job rather than widen the permission. The agent renders into the workspace and builds a manifest, and neither of those needs anything outside the sandbox. A small privileged job runs outside the sandbox, on a timer, and copies only what matches an allowlist: banner files named in one exact shape, the manifest, and stored workflows with flat filenames.

That publisher is deliberately self-contained. It does not execute anything from the workspace, because a program that runs workspace code is not a boundary, just a longer arm. Writes are temp file plus rename, so a half-copied banner never appears on the share. The agent proposes, the job disposes.

Installing it root-owned is the part that actually matters. A publisher living inside the workspace gives no boundary at all, because the agent can edit the thing that is supposed to be constraining it.

Where we left it

There is a lower-friction option for when the timer is not worth it: a detached publish loop that does the same work every five minutes, needs one approval to start, and retires itself when everything has been rendered and published. That is fine as an interim and strictly worse as a destination, because it still starts from a position where the agent can write the share.

The lesson that generalises is about where privilege sits. If a capability is only needed at one narrow step, give it to one narrow process, and make that process unable to do anything else. The alternative, which is to grant the agent a broad capability because it happens to be standing near the narrow one, is how a convenient run becomes a permanent hole.

There is a sibling point about scope. This workspace was the whole home directory, so the sandbox protected the system and nothing else inside home: other repositories, the vault, and local binaries were all writable by the agent. The boundary was real and aimed at the wrong things.
