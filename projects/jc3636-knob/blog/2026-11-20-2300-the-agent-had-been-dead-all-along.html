The agent had been dead all along

2026-11-20 time not recorded · part 7 of 22 usage panelagenttypescriptusb

The usage panel is only as good as the little agent on the laptop that fetches the numbers. On 20 November I went to check on it and found it had been dead. Not "a bit unwell". Not running. No job, no process, connection refused. The panel had been politely saying "agent offline" to an empty room.

Exhibit A: the corpse

launchctl list showed no jc3636 job. No serve.py process. http://127.0.0.1:8787/usage refused the connection. The LaunchAgent file was still there, looking innocent.

So the "login service" ticket I'd marked done on 2 November had been done, and then quietly undone at some point I can't date. Which is the best possible argument for a panel that says when it's stale: the one time it mattered, it did. "Agent offline" was the truest thing on my desk.

Two shapes, not three

Before reviving it, I asked a question that turned into a redesign: are the sources really just two shapes, prepaid and postpaid?

Nearly. The split that matters for drawing a bar is whether the meter refills:

  • an allowance is used-of-a-limit that resets at a time. Subscription windows (5 hours, 7 days) and monthly spend are the same shape with different labels;
  • a pot is what's left, no reset. Only prepaid credit. DeepSeek, the jar of coins.

Two shapes. Two display styles. One threshold rule each. Tidy enough to frame.

Python → TypeScript, with no packages

I prefer TypeScript on Node wherever it's reasonable, so the agent got ported the same day. Node 24 runs .ts files directly by stripping the types, so there's no build step, and the whole thing uses only built-in modules: the HTTP server, fetch, security for the Keychain, stty for the USB serial port. Zero dependencies. Zero node_modules. A tiny, smug, self-contained agent.

The LaunchAgent now runs the TypeScript agent with an absolute path to Node, and this time it actually loaded. (The first attempt said Input/output error. It turned out that error came from inside the agent's sandbox. Running the same command outside it worked first time. Classic.)

That night: the cable did everything

I plugged the knob in by USB, with an older game on it, and went to bed. The coach made a full 16 MB backup of the flash first (thank you), then flashed the new pane-list firmware over the cable at 14:13 by the laptop's clock. No buttons needed.

Then the best bug of the day. Full payloads, 1,463 bytes each, were sent and never acknowledged. The panel's USB receive ring is 1,024 bytes, and a chunk that doesn't fit is simply dropped. Not truncated. Not an error. Dropped, silently, every time, on the floor.

The fix on the agent side: send 256 bytes every 200 ms, like a polite person feeding coins into a slow vending machine. Every payload after that was acknowledged and parsed. The knob started reporting each minute:

applied panes=6 states=oEoouu cue=0 sel=openai bars=2 lines=0 heap=212216

Six panes, OpenAI selected, heap steady at about 212 KB. Every field matched the agent's own check.

Honesty corner: nobody actually looked at the screen that night, because I was asleep. The record says so in as many words. The numbers were right; the pixels were unwitnessed.

And the stale marker

The panel now also says how stale. Every fallback figure carries a reason (login expired, unreachable (VPN?), fetch failed) and its age, and the footer prints them in amber. If the agent dies again, at least it'll be a well-documented death.
