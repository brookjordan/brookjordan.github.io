The board was plugged in, just not here

2026-11-28 11:12 (+0800) · part 29 of 57 labhardwareflashingotaarchitecture

"It never seems to do real tests. The board is always plugged in."

That was a very reasonable question at 10:08. Seven piano apps had just flown through the Mac simulator with green checkmarks, and not a single one had touched the actual ESP32-S3 sitting right there on the desk.

So we went looking. And we found two completely different reasons, stacked neatly one on top of the other like a comedy routine.

The measurements before the theory

Check What we expected What we actually observed
tools/pi-run.py prompt (NEW) Flash if a board is attached Hardcoded: "There is no board attached: do not flash."
ls -la /dev/cu.* /dev/cu.usbmodem* Only Bluetooth-Incoming-Port and debug-console
system_profiler SPUSBDataType Espressif USB device Nothing on the USB bus
ping -c 1 192.168.0.120 Maybe offline? 62.0 ms reply, ESPHome usage panel happily alive on Wi-Fi
projects/game-template/partitions.csv Dual OTA slots? One 9 MB factory partition, no ota_0/ota_1, no Wi-Fi stack

The board was plugged in. Just into power, not into a Mac USB data port. And even if it had been plugged into USB data, our own runner was telling pi not to touch it!

Two worlds fighting over one flash chip

Every flashing headache we have paid for this week comes from the same root cause: the knob lives a double life as two incompatible firmware worlds.

  • World 1: The daily-driver LLM usage panel (ESPHome, reachable on Wi-Fi at 192.168.0.120, freshly stabilised in the panel that stopped forgetting). Its TinyUSB CDC driver claims GPIO19/20, which locks out the ESP32-S3's built-in USB-Serial-JTAG auto-reset until a human taps RESET or BOOT+RESET.
  • World 2: The ESP-IDF games and piano apps. Fast direct-framebuffer C, single factory partition, zero Wi-Fi, zero OTA. Once an ESP-IDF game is on the chip, USB-Serial-JTAG stays wide open for button-free flashing, bidirectional console commands (idf.py monitor), and built-in hardware JTAG debugging (idf.py openocd + idf.py gdb on :3333) with no external probe.

Flashing an ESP-IDF game over ESPHome's Wi-Fi OTA would be a one-way trip: the game boots, Wi-Fi OTA vanishes, and the knob becomes an island until you plug in a USB data cable.

The fix today, and the first-principles destination

First, we fixed the immediate offline bugs so pi can actually use hardware the moment a USB data cable is plugged in:

  1. tools/pi-run.py (5d7e858) now inspects /dev/cu.usbmodem* at launch instead of hardcoding no-flash: a short-named game/bootloader port tells pi to run tools/build.sh <name> flash and tools/build.sh <name> log after check.sh passes; a long-named TinyUSB port warns that one manual BOOT+RESET is needed first.
  2. .agents/skills/knob-flash/SKILL.md (0d0d6b8) now documents every verified ESP-IDF 5.5 connection path: USB-Serial-JTAG auto-reset, bidirectional console commands, built-in OpenOCD/GDB debugging, and the Wi-Fi OTA boundary.

Then we stepped back and asked: if we designed this knob from day one knowing it is both a daily LLM desk panel and an autonomous pi hardware testbed, what would we build?

One ESP-IDF Knob OS with two OTA slots:

  • Slot A (ota_0, the Knob Shell): boots straight into the LLM usage gauges plus an app launcher, and exposes a tiny OTA + control endpoint over Wi-Fi and USB-Serial-JTAG.
  • Slot B (ota_1, pi's Hardware Test Sandbox): pi still writes tiny single-file apps against game-template, while the template quietly carries ESP-IDF automatic rollback (CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE) plus a thin remote input/log shim speaking the exact same knob/tap/drag script language as tools/sim.sh. If a pi build panics or hangs, the bootloader rolls straight back to your LLM gauges. Unbrickable, even over Wi-Fi!

Alternatives rejected

  • Porting the entire ESPHome usage panel to ESP-IDF before doing any hardware tests. Next! Dropping TinyUSB CDC (or adding a reboot-to-bootloader trigger) in ESPHome gives button-free USB flashing in minutes while the two-slot OS is built incrementally.
  • Leaving Wi-Fi on during BLE MIDI performance. Next! Wi-Fi and BLE 5.0 share one 2.4 GHz antenna on the ESP32-S3, so the Wi-Fi debug shim must stay off whenever a BLE MIDI app is active.

What still hurts

We still have not plugged a single MIDI cable into the knob! Next up is a deep-research pass on left-handed piano geometry, Launchkey 49 MK4 + M-VAVE FM-1 / SMK-37 Pro MIDI quirks, and ESP32-S3 USB Host + BLE MIDI coexistence, followed by the physical bench tests as soon as the USB-C data cable, powered USB 2.0 hub and OTG adapter hit the desk. See the morning's coaching post and the seven piano apps post for the builds waiting to be flashed.
