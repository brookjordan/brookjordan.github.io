Half a radio, and a cable that turned out to be the network

2026-11-03 12:20 · part 5 of 21 networkingusbarchitecture

The panel stopped showing new numbers when I moved to a different network. Not loudly. The panes just kept their last values and quietly stopped updating, which is exactly what a working device looks like if you don't look closely.

The explanation took me longer than it should have. The fix turned out to be the cable that had been plugged in the whole time. Of course it was.

The radio hears half the room

The ESP32-S3 has a 2.4GHz radio. Not a radio that prefers 2.4GHz, or one that falls back to it: a radio that cannot see a 5GHz network at all. A scan from the device returns nothing, no association is attempted, and the fallback access point comes up as if the house were empty.

That is a datasheet fact, and it is worth stating plainly because it is easy to misread the symptom. A device that cannot join a 5GHz-only network does not report that it cannot join it. It reports the same "disconnected" it reports for a wrong password, a mistyped SSID, or a router that is off.

I had been treating the panel's connectivity as a firmware concern for a whole day before checking what band the network was even on. A day! Of firmware! For a radio that literally could not see the network. Magnificent.

The cable does not make a network by itself

The obvious next thought is that the USB cable should carry the laptop's connection. It is plugged in, the laptop has internet, so surely the device does too.

It does not. A USB cable to this board gives three things: power, a way to flash it, and a serial channel. None of those is a network. It was, for networking purposes, a very expensive phone charger. The device was never reading from that channel, so "tethered" meant nothing beyond charging.

What made the confusion worse is that I had said something close to the opposite earlier, in the context of a design that was not built yet. The transport independence I described was the thing I was planning, not the thing that existed. That is a distinction worth keeping straight when a device is misbehaving at seven in the evening.

Data over the wire, deliberately

The fix is the old idea finally built: give the device a data path on the cable.

On the device, tinyusb and usb_cdc_acm expose a single CDC interface. The fetch script now asks for data over WiFi when WiFi is connected, and otherwise writes R\n to the cable. The main loop drains that channel line by line, and a line beginning with { goes into the same parser the HTTP response used, because the payload is identical either way.

On the laptop, a bridge watches the USB serial ports, and answers R with one JSON line from the agent. It runs as a thread inside the usage agent rather than as its own service, which is a decision born of an hour of confusion: as a separate LaunchAgent it started, ran, and produced no output whatsoever, because the service's standard output was never connected. The agent already owned the token and the log, so the bridge belonged there from the start.

The result is a device that does not care what band anything is on. It asks, something answers, the panes update. It just works, over the cable that was there all along, and I am unreasonably pleased about it. Frequency, SSIDs and DHCP stop being part of the problem.

The cost, which is not obvious until it bites

TinyUSB takes the USB peripheral for itself. On this board, before that change, the USB port presented the ESP32-S3's built-in USB-Serial-JTAG interface, which is what esptool uses to reset the chip into its bootloader.

With the CDC firmware running, that interface is gone. esphome upload over USB fails mid-handshake, and the failure reads like a permissions problem or a bad cable rather than a consequence of the firmware that is already on the device.

Recovery is physical: hold BOOT, tap RESET, release BOOT, and the bootloader appears. Then flashing works again. The alternative is WiFi, which is the thing that was broken in the first place, so on a 5GHz-only network the buttons are the only way to deploy a new build.

That is a real operational cost, and I wrote it into the notes rather than discovering it again the next time I flash from across the room.

What actually travels on the wire

The protocol is deliberately trivial, because the value here is the path, not the framing.

The device writes three bytes, R\n, when it wants data. The bridge reads lines, and answers R or the boot greeting KNOB-DATA with exactly one JSON line from the agent. The device accumulates bytes until a newline, caps the buffer at 1900 so a malformed stream cannot exhaust memory, and hands anything that starts with { to the parser.

Two consequences fall out of using the same payload shape as HTTP. The parser is shared, unchanged from the version that read HTTP responses, so the new transport could not introduce a parsing difference. And the device does not know or care whether the JSON arrived over a socket or a serial cable, which is exactly the property that made the change a small one rather than a second implementation.

What is missing is an acknowledgement. The device parses, then says nothing, so the laptop can only prove that bytes were served. Adding an OK line back is three lines of code, and it is written but not flashed, because of the trap below.

The service that ran and said nothing

The bridge began life as its own LaunchAgent, which is the obvious way to keep something running across logins. It started, stayed running, and produced an empty log file. Not an error, not a crash: nothing.

launchctl reported it running with a pid. lsof on that pid showed standard input attached to /dev/null and no standard output at all, so every line the script wrote went nowhere. Reproducing the same command with a minimal environment by hand worked immediately and printed opened /dev/cu.usbmodem..., which ruled out the script, the port and the token.

Rather than debug launchd's plumbing, the bridge moved into the agent service, which already had a working log, a running process, and the bearer token in hand. That is one fewer service to supervise, and the failure mode of a missing log disappears because there is only one log.

The lesson is not about launchd specifically. A second service for a second channel looked tidy and cost an hour; the thing that already worked was the better host. An hour of a service running perfectly, saying nothing, to nobody. Very zen.

What the transport does not prove

Serving the payload is not the same as displaying it. For twenty minutes the log showed a request and a 623-byte answer every sixty seconds, with no reconnect and no reboot, which proves the device is alive, asking, and receiving. It does not prove a single number on the glass is correct.

There is a temptation to call that success because the traffic looks right. The honest summary is narrower: the transport works, the firmware is stable enough not to restart while idle, and the rendering is unverified until somebody looks at it. Building in an acknowledgement was the next step, and it is exactly the step the flashing trap then made awkward.

Two layers, two kinds of evidence. Network traffic is cheap to observe and easy to mistake for the whole story. The bytes arrived. Whether the pixels were right was, at that point, anyone's guess.
