The knob that knows when the tokens run out

2026-11-02 11:06 · part 3 of 17 buildhardware

I bought a round screen with a knob on it and then spent two days learning everything it refuses to tell you. This is the record of that: partly so the next person saves the two days, and mostly because half the fun was in the things that lied.

The board gave nothing away

The listing said 320x320. The panel is 360x360. The listing did not mention that the touch controller and a haptic driver share one I2C bus, or that the haptic driver has no enable pin, because the schematic ties it high and expects you to discover it.

Over USB it introduced itself as an ESP32-S3 with 16MB of flash and 8MB of PSRAM, and the vendor's starter pack did the rest, once I stopped trusting the shop page and read the schematic instead. The definition of the device is in that PDF, not in the marketing copy.

The serial console was a trap

Everything I knew about reading firmware output was wrong here. The device enumerates as a USB serial port, opens, accepts writes, and returns nothing. Three firmwares, including a probe whose only job was to print a number every second, were silent. A firmware with one job. Failing it. Three times.

The board was sitting in its ROM download mode, and flashing does not take it out of that mode. Only a physical power cycle does. Worse, merely opening the port reset the chip, so every attempt to listen restarted the thing I was listening to. The panel eventually reported its own reset reason as USB peripheral, which is the peripheral admitting, sheepishly, that it had been reset by the host. Every time I listened, I killed it. Very Schrödinger.

The fix was to stop using the cable. Flashing and logs both go over WiFi now, and the only reason to touch USB again is a board that will not boot.

Picking a toolchain by reading, not by habit

Arduino CLI got pixels on the screen, but its libraries live in a global folder with no lockfile. Before migrating, the useful question was not which framework is fashionable but which one already knows this panel.

ESPHome added the ST77916 as a stock mipi_spi model in its October release, and its initialisation sequence is the vendor's own, command for command. That is the whole argument: the custom driver I would have written was already upstream, tested against this panel family.

The giveaway that the migration was right is how little firmware there is. Four panes, a knob, a touchscreen and a haptic sequencer fit in 1.05MB, and every dependency is pinned in one file. One file! I could cry.

Two panes nobody documents

Subscription usage is not an API feature. It is a thing the vendor's own console knows and your key does not.

Z.AI exposes it on an endpoint its console calls, not in its reference documentation. Claude Code has one behind an OAuth login, and the endpoint needs a scope that a setup-token does not carry, which is why the token I minted first was useless. Beautifully, completely useless. ChatGPT's usage sits on a web backend that answers a browser and refuses a script.

That last one matters for anyone building this: the reliable credential was not a copied cookie. It was the OAuth session that a tool on the same machine already keeps refreshed. The lesson generalises. Before inventing an auth flow, look for the one already working on the machine.

The keys moved off the device

The first version put the API key in the firmware, which is to say it put an account-wide secret in flash that anyone with a cable could read.

Now a small agent on the laptop owns every credential, and the panel holds only a token that proves it is allowed to ask. The agent serves one normalised payload; the panel renders it. Two consequences fall out of that shape. The device has nothing worth stealing, and the transport stops mattering, because swapping WiFi for a cable or Bluetooth is a change at the agent end.

One detail worth stealing: ESPHome substitutes secrets literally, so a secret that has to be a header value must contain the whole header. The first build sent a bare token and the agent answered 401. Fair, honestly.

The motor would not buzz

The unknown I2C device at address 0x5A turned out to be a DRV2605L, a haptic driver, which the schematic names and the vendor's demos never mention.

It took four configurations, offered on the four corners of the screen and judged by feel, to learn that real-time playback produces nothing on this motor while the ROM effect library clicks. I had built every announcement on the one mode that does not work, which is why a whole feature looked broken when one setting was wrong. Four configurations, judged by poking the corners of a screen and feeling for a buzz. Science!

The datasheet explains why the clicks are faint: the level scaler has no reference until auto-calibration runs. It also explains why calibrating at boot is a bad idea on this board, because doing it there pulled the rail down and the panel stopped fetching. Calibration now lives behind a knob press, where a failure costs one reboot.

Timing was never the haptics

Rotating the knob clicked in a burst after the rotation stopped. The obvious suspect was the haptic code. The actual cause was the display: it pushed a full 360x360 frame after every detent, and each push blocked the loop long enough to delay the next click.

Drawing on demand fixed it, and the knob now clicks with the notch. Click. Notch. Click. Notch. Bliss. The sequencer also stopped counting ticks and started reading the clock, so a busy moment skips a cue rather than replaying it late.

The panel lied once, convincingly

Every pane started reporting the agent offline, while the agent logged a successful request every minute. The device had one global flag for "the agent answered", and it cleared that flag whenever the payload happened to lack one provider's data. One upstream blip blanked all four panes. One! Blip! All four!

A heartbeat in the log settled it in one line: at boot the flags were zero and a minute later they were all one. The flag now starts true, WiFi association triggers a fetch, one failure is tolerated, and a provider with a bad minute keeps its last good number instead of vanishing.

What is still open

The touch screen has no ambient light sensor, which the schematic confirms and my eyes had already guessed. Brightness is set by dragging a finger along the diagonal, and the attempt to set a dim default at boot took the board down, so that is unfinished.

Pentatonic touch tones remain unbuilt, the threshold haptics at 90 and 80 percent remain specified but not wired, and the panel currently shows about nine dollars of DeepSeek credit because I spent the rest of it writing this.

The full record, including the failures I would rather not have had, is in the project notes. That is the useful part anyway. A devlog that only shows the version that worked is a brochure, and this is very much not a brochure.
