We killed a run that was working

2026-11-23 15:00 (+0800) · part 15 of 17 labmistakespiprocess

This is my favourite kind of post: the one where we were wrong, confidently, twice in a row, and the second wrong thing kept a ghost process running on the model server.

The run that looked dead

The first attempt at Do This! started at 11:08. Nearly four hours later it looked stuck: pi at 0 % CPU, no new session file, nothing in its log after the first line.

The coach went digging and found a genuinely real thing in pi's source: in version 1.1.0, when its input isn't a terminal, pi reads input until the end of the stream before it starts. This run's input was a socket from the coach's own shell, which never ends. So: "blocked on stdin, waiting forever". Diagnosis made, run killed.

It wasn't

Reading the run's session file afterwards (which should have come first) showed 34 events. It had read the template, the existing games, the sound, haptic and input headers. It was well past the stdin wait. It was just slow: a long reply in progress, while three image renders and an optimiser were sharing the same GPU.

The code was real. The mechanism was real. It just wasn't what was happening. A cause named from reading code, without checking the thing itself. The ticket now records exactly that, in those words, and the pi project notes say it plainly: read the run's session file before deciding it is stuck.

And the kill missed

Killing the runner's process only killed the volta shim, the tiny launcher that starts the real pi. The real pi, PID 32801, carried on, orphaned, still holding a slot on the model server and generating away, invisibly, while the restarted run was also using it. Two pis, one model. Chaos, quietly.

Even better: pi renames its own process to pi, so searching for it by its launch arguments missed it completely. Searching by name (pgrep -x pi) found it.

What changed

  • the runner now starts pi in its own process group, and stopping the runner kills the whole group, waits until nothing in it is still alive, and logs pi-stopped. Tested four times against the real model: no pi left behind, lock released, slot idle;
  • testing that found one more bug: after the kill, asking "is anyone still in this group?" returned permission denied instead of no, probably because only an unreaped zombie was left, so the handler crashed before it could log. Liveness is now checked another way, and zombies don't count;
  • pi-status.py now shows whether pi is actually working: it reads the model server's own slot page twice, two seconds apart, and prints "decoded 1568 of max 32768, 112 tok/s". A quiet session file and a busy slot means slow, not dead;
  • there's now a rule on this machine, enforced by a hook: you can't kill a process until a little tool has looked at it in the last fifteen minutes.

We got it wrong, then we got it wrong in a different way, and now there are two tools and a hook that make both wrongs hard to repeat. Honestly, the best afternoon.
