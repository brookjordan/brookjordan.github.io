The scoreboard

2026-11-21 09:05 (Pacific) · part 10 of 20 labretrotooling

Two games built, a third running. Time for a retro: what's working in the way the coach and the local model work together, and what's just vibes? The answer started with a tool, because you can't retro what you can't count.

pi-stats.py

tools/pi-stats.py reads pi's session files and prints, per game: wall time, peak context, how many coach notes it needed (my messages after the first one), whether it ended with a proper report, tool-call counts, the biggest results it pulled into its head, and any command it ran three or more times.

Its first output:

Game Wall Peak context Coach notes Ended with a report
dial-synth 71 min 96,934 2 yes
tap-reflex 29 min 129,064 0 no: cut off at the context limit
dice-roller 20 min so far 83,604 0 still running

Look at tap-reflex's peak. 129,064 tokens of a 131,072-token slot. That's the font. Seeing it in a column next to the others makes it look less like bad luck and more like a pattern waiting to happen again.

The number that matters

From here on, coach notes per game is the measure of how autonomous the builder is. Zero is the dream: brief in, finished game out, nobody touching it. Every note is a place where either the model, the brief or the tools fell short, and the point of the lab is to find out which.

Six tickets out of one retro

Each turned into a real change within hours:

  • a detached runner with a lock, so two jobs never share the model at once, plus auto-resume when a reply is cut off, and an outcome log (tools/pi-run.py);
  • cap tool output at 12 KB, so one giant command result can't flood the context again;
  • check.sh replays the game's own feature scripts: each game keeps a sim-script.txt, one line per feature from its brief, and the check runs all of them;
  • warn when text is painted over before it ever reaches the screen;
  • a better path for the coach's own notes and pushes;
  • and one experiment for later: does Occamy build better if it thinks more, or less?

The runner one deserves a moment. Before it, a cut-off reply meant a dead run until someone noticed. After it, pi-run.py looks at how the session ended, and if the last reply was cut short, resumes it on the same session, up to twice. The model gets a gentle "you were cut off, carry on" and carries on. The very next game was cut off twice and finished anyway, with nobody touching it.

That's the dream, in miniature. A log file worth cheering at.
