The silent arcade

2026-11-23 17:29 (+0800) · part 18 of 26 labsimulatorsoundmistakes

The arcade had six games ready. Then we discovered that five of them would have been completely silent on the actual board, and the simulator had been cheerfully logging every beep they never made.

Muted, since day one

Back in the folder for a flight, sound was set to start muted, with BOOT cycling it on. A good choice for a demo on a quiet desk! A terrible surprise for any game that never turns it on.

Only two of the games called sfx_output(). pocket-pet, metronome, dice-roller, tap-reflex and the arcade's own menu never did. On the board: silence. In the simulator's event log: every sound, listed faithfully, because the simulator didn't model the mute.

So now it does. Sounds played while muted are marked in the log, and at the end of a run the simulator says:

the game played 12 sounds but never called sfx_output(): sound starts muted, so on the board they are silent.

It fired on exactly the five silent ones and nothing else. Each got one line after setup (sfx_output(SFX_OUT_ALL)), and the template's demo now says on purpose that it starts muted, so the warning knows the difference between a choice and an accident.

A metronome that drew "(40)"

metronome had passed every check. Turn the tempo from 220 down to 40 and the screen said (40): the edges of the wider "220" were never erased. Start it, and the status line drew "1 / 4" straight over "tap to start": tap1/4tart.

Left: metronome as first committed, rebuilt in the simulator. Right: after one coach note, fixed by Occamy in three minutes.

That's the same bug pocket-pet had with its age text, and both had passed the check, so the simulator learned to catch it: when text is drawn where other text was, and pixels of the old text still show outside the new one, it warns and names the fix. Replayed against every game: metronome failed, twice, on its two real bugs, and the others passed clean. Then it caught one more, in the arcade menu itself: with six games, the first row was drawn on top of the "ARCADE" title. Spaced out, fixed.

And now, the coach's mistake

While checking metronome, the simulator's text listing seemed to say "tap to start" on a screenshot that clearly showed "1 / 4". A simulator bug! In code the coach had just changed! It swapped the old simulator back in: correct. Swapped the new one back: wrong. Proof, surely.

Four debug runs later, with traces on every text record, everything inside the simulator was right. The problem was grep. The coach had asked it to print matching lines from two files without filenames, and the version on this machine printed them in whatever order it finished, not the order it was given. "stopped" had been read as "started", and vice versa. The simulator was right the whole time, and the "proof" was most likely the same grep, happening to print in order that once.

I adore this. A careful, methodical, swap-one-thing-and-watch investigation, executed beautifully, of the wrong suspect. grep -H, with filenames, is now everyone's new best friend.

The arcade, now

Six games: dial-synth, tap-reflex, dice-roller, kitchen-timer, metronome, pocket-pet. Sound on. The menu puts the backlight back to 80 % when you return (pocket-pet dims it to 30 % when the pet falls asleep). Every game passes its own check, and the arcade passes its eight feature scripts.

Not flashed yet; that needs a human hand on BOOT and RESET. But it's ready. And it'll make noise.
