Shokz Auto-Fill/FAQ

Questions

Including the ones you are right to ask before typing your password into a script somebody put on the internet.

The basics

What is a .command file, really?

A plain text file full of shell commands that macOS runs in Terminal when you double-click it. That is the entire meaning of the extension: .command is what tells Finder "hand this to Terminal" instead of "open this in a text editor".

It is not an app bundle, not a package, not a compiled binary, and not an installer framework. Right-click install.command, choose Open With → TextEdit, and you can read every line that is about to execute. It is about 700 lines with comments, including the one you are reading about.

It is also why macOS is suspicious. A .command file has no developer certificate to check against, so Gatekeeper falls back to "I have not seen this before, ask the human." Hence the right-click-and-Open dance on the first run, which is you answering that question. See the install page.

Do I need Navidrome? What even is it?

Yes. Navidrome is a free, open-source music server: you point it at a folder of your own music files and it serves them over HTTP with a Subsonic-compatible API. It runs happily on a Mac, a NAS, a Raspberry Pi or a small VPS.

This tool is a client for that API. It asks Navidrome for random songs and downloads them. It does not do any music management of its own — no library scanning, no metadata, no playlists. If you already have Navidrome, this fits straight on top. If you do not, setting it up is a separate job and probably the bigger half of the work.

Which players does it work with?

Any player that mounts as a USB mass-storage volume under /Volumes and is formatted FAT32 or exFAT. It was written for a Shokz OpenSwim, and it works with the OpenSwim Pro, older Aftershokz players, most clip-on MP3 players, and anything else that shows up in Finder as a removable drive with a name.

It does not work with phones, with iPods stuck in their default iTunes-managed mode, or with anything that needs a proprietary app to transfer music. The test is simple: if you can drag an MP3 onto it in Finder and have the player see it, this tool can fill it.

Will it work with Spotify, Apple Music or YouTube Music?

No. Those are streaming services with DRM and no download-to-a-folder API, and this tool has nothing to say about them. It moves files from a server you run, containing music you own or have the right to keep, onto a drive you own.

If your library lives in one of those services, this is not the tool for you — and the Subsonic API gives no legitimate route around that.

Windows? Linux? iOS?

macOS only, and genuinely so — not "not ported yet". The reason the project exists is a macOS-specific privacy mechanism (see below) and the launchd agent that watches /Volumes. On Linux, the equivalent is a udev rule and a five-line shell script; on Windows it would be a different program. Run it on the Mac you actually plug the player into.

Do I have to install Homebrew?

Only if you do not already have jq and a non-Apple bash. The installer checks both and will not touch Homebrew if they are present.

If they are missing it runs brew install jq and brew install bash — two ordinary packages, no taps, no third-party formulae. If Homebrew itself is missing, the installer stops and tells you to install it first from brew.sh rather than installing a package manager for you.

Trust and privacy

Why should I trust you with my password?

You should not, on the strength of a web page — mine or anyone's. You should trust it because you read it, and here is what you will find when you do.

It is small. Four files do all the work: install.command, uninstall.command, lib/common.sh and bin/auto_fill_shokz.sh. Together, about 1,500 lines of commented shell. There is no compiled code, nothing minified, no vendored dependency, and no download step during install.

You can see every network call. Search the repository for curl and you will find calls to exactly two kinds of destination: the Navidrome URL you typed yourself, and nothing else. There is no analytics endpoint, no crash reporter, no update check, no paste service, no IP echo.

It only ever writes to paths it names. Your home folder, two files under /tmp, and the volume you chose. No sudo anywhere. Nothing system-wide, no kernel extension, no daemon.

You do not have to give it your real password. Navidrome supports multiple accounts, so make a second one for this tool and use that. It only ever needs to read your library. That is a genuinely good idea and it costs nothing.

If after reading it you find something wrong, open an issue — that is what the repository is for.

Does anything leave my computer?

Two things are contacted during normal operation:

  • Your Navidrome server. To check it is alive, to ask for random song IDs, and to download those songs. You configured the address yourself.
  • The USB volume in front of you. To write the files.

That is the complete list. There is no telemetry, no analytics, no usage reporting, no crash reporting, no update check, no license server, and no third party anywhere in the path. The tool has never had a network destination other than the server you name.

The one external thing that happens at any point is during install: brew install bash or brew install jq, if you are missing them. That is Homebrew talking to Homebrew, before any of your credentials have been asked for.

Where exactly does my password end up?

One file: ~/.config/shokz-auto-fill/config, written with mode 600 — readable only by your user account, not by other accounts on the Mac.

It is a plain shell file, so you can read it yourself. It looks like this:

DEVICE_NAME="MY_PLAYER"
ND_URLS="http://navidrome.local:4533"
ND_USER="youruser"
ND_PASS="••••••••••"
SONG_COUNT=50
CONNECT_TIMEOUT=8

It is not in the repository, and config/config is git-ignored as a backstop in case anyone ever puts a config in the wrong place. It is never printed, never logged, and never included in the Done summary.

If you are migrating from an older setup that kept the password in plain text inside a script that got committed to git, treat it as exposed: rotate it on the server, then re-run the installer to store the new one.

Is my password sent over the network?

Not as such. The Subsonic API this tool speaks uses a token scheme: each request sends md5(password + salt) with a fresh random salt, and never the password itself. Navidrome accepts that in place of the plaintext.

Which is worth understanding precisely, because it is a real improvement and not a magic trick: a token with its salt is a working credential for that request. It cannot be replayed without the salt, and the salt is new every time, so it is much better than sending the password over plain HTTP. It is not a substitute for HTTPS, though. If your server is reachable over the open internet, put it behind TLS.

This is also why the installer's log redacts tokens and salts as well as passwords. A log file full of replayable tokens would be a credential store with extra steps.

Why does it need Homebrew bash? That seems excessive.

It does seem excessive, right up until you have spent an evening on the alternative. Here is the whole mechanism.

macOS gates removable volumes behind a privacy service called kTCCServiceSystemPolicyRemovableVolumes. When a background job tries to write to a USB drive, macOS asks one process in that job for permission — the responsible process.

Run the job under /bin/bash and bash is the responsible process. But /bin/bash is an Apple platform binary:

$ codesign -dvvv /bin/bash | grep Platform
Platform identifier=26

macOS refuses to grant TCC permissions to a platform binary, and it cannot even raise the prompt to ask:

Platform binary prompting is 'Deny' because: is Platform Binary

So the answer is no — permanently, silently, with no dialog and no error of its own. All you see, much later, is this, once per file, with no explanation:

mkdir: /Volumes/MY_PLAYER/auto-list/1: Operation not permitted

And here is the part that makes it maddening: run the identical commands by hand in Terminal and they work perfectly. Because then the responsible process is Terminal, which macOS is perfectly willing to ask. The same script, the same files, the same drive — works interactively, fails from the agent, with no difference you can see.

Running the job under a non-Apple bash changes the responsible process to something macOS can prompt for. That is why the installer goes to the trouble, and why the shebang must stay pointed at /opt/homebrew/bin/bash rather than /bin/bash. The full trace is in the walkthrough.

What is this "Full Disk Access" thing the warning mentions?

A fallback, not the normal path. The normal path is the Allow dialog during install, which grants access to removable volumes as a category.

If that dialog was missed, denied, or never appeared, the alternative is to add the Homebrew bash to Full Disk Access in System Settings → Privacy & Security. It is broader than the tool needs — but it is the permission macOS reliably honours for a background job, and the installer prints the exact path to use:

/opt/homebrew/bin/bash          # Apple Silicon
/usr/local/bin/bash             # Intel

Not /bin/bash. Adding the Apple one will do nothing at all, for the reason immediately above.

Is it signed or notarised?

No. Signing and notarising require a paid Apple Developer account, and this is a personal open-source tool. That is the entire reason you meet Gatekeeper on the first run.

Which is a fair reason to be more careful, not less. Read the file before you run it. Everything it does is in the repository, in shell, in plain text.

Setting it up

I upgraded bash with Homebrew and now it has stopped working.

Expected, and annoying, and fixable in ten seconds. The permission grant is keyed by path — and because Homebrew bash is unsigned, macOS resolves symlinks and records the versioned Cellar path, /opt/homebrew/Cellar/bash/5.3.20/bin/bash. Upgrade bash and the path becomes 5.3.21. The grant does not follow it.

Fix: re-run install.command. It repeats the permission probe, so the dialog comes back and the grant is re-created against the new path. Ten seconds, and you keep receiving bash updates.

Or prevent it: brew pin bash stops its path ever moving again. Durable, at the cost of no further bash security updates — a real trade-off, and yours to make.

The symptom to recognise: the job stops filling for no visible reason, and the log is full of Operation not permitted.

Can I install without the player plugged in?

Yes, but plug it in if you can. Two reasons, and the second one matters more.

The installer lists what is currently mounted so you can pick your player by number rather than typing its volume name from memory — which is not as easy as it sounds when macOS decides to call it MY PLAYER 1 because an old mount never cleared.

More importantly, it can only test the removable-volume permission against a drive that is actually there. Install without the player and the test is skipped, so you meet the Allow dialog for the first time on a future plug-in, with a job running in the background that you cannot see. It works; it is just a worse first experience. What the installer says when it skips it →

Can I use a separate Navidrome account for this?

Please do. Create a second Navidrome user, give it a different password, and enter that in the installer. The tool only ever needs to read your library — it makes no changes to the server at all.

The benefit is that the credential sitting in a file on your Mac is not the same credential you use everywhere else, so losing it costs you nothing. This is the single cheapest security improvement available here, and it takes about a minute.

Can I use it with more than one player?

Not with a single installation — the config holds one device name. There is one LaunchAgent watching /Volumes, and when anything mounts it looks for /Volumes/<the name in the config>. If that is not what just appeared, it does nothing.

Two players is genuinely a different feature (which drive, which settings, what if both are plugged in at once), and it is not built. If you want it, an issue describing your setup is the right way to ask.

My player's name has a space in it. Is that a problem?

No, and it is specifically handled. An earlier version word-split the volume list, which turned one player called MY PLAYER into two menu entries — MY and PLAYER — neither of which existed. The current code reads the list line by line, and the device name is quoted everywhere it is used.

It is one of the defects the installer test suite covers, so it cannot come back unnoticed.

Using it

How much space does it use on the player?

Fifty songs is roughly 200 MB at typical bitrates, and two lists are kept, so budget about half a gigabyte. The old lists beyond the newest two are deleted on each fill, so that figure does not grow over time.

If your player is small, drop the song count — that is installer option 1 on a re-run, and it takes effect on the very next fill.

How do I change the number of songs?

Run install.command again, choose option 1, enter the new number. Done — no reload, no restart, no need to touch the drive. The script and the agent read the config at run time, so the next fill uses the new value.

You could also edit SONG_COUNT in ~/.config/shokz-auto-fill/config by hand. The installer route is better, because it validates the number and leaves the file with the right permissions.

Will it delete my music?

It will delete the numbered folders it created itself, inside auto-list/, and only the ones older than the newest two. That is the whole of its deletion behaviour.

Everything else on the player is untouched — other folders, files you put there yourself, anything at all outside auto-list/. And a fill that cannot download anything aborts before the cleanup step, so a failed run never removes a list.

The uninstaller does not delete anything from the player either. If you want the auto-list folders gone, remove them yourself.

What order do the songs play in?

The order they were downloaded in. Every file is prefixed with a four-digit number — 0001 - Artist - Title.mp3 — so a player that sorts by filename plays the list in the sequence it was built rather than alphabetically by artist.

Which means: shuffle on the player is still worth using, and the list is a genuinely random draw from your library rather than a curated sequence. That is the point — plug in tomorrow and you get a different fifty.

Does it work while my Mac is asleep?

No — and it does not need to. The job fires when a volume appears under /Volumes, which requires the Mac to be awake and for you to have physically plugged the player in.

So the realistic pattern is: you plug the player into the Mac, the fill runs in under a minute, the drive ejects itself, and you unplug it. If the Mac is shut, nothing happens until you open it and the volume mounts — at which point the job fires as normal.

If the Mac goes to sleep during a fill, the run is interrupted and may leave a partial list. Cleaning that up is easy, and the next fill is unaffected.

Can I just run it by hand when I feel like it?

Yes. With the player already mounted:

$ launchctl kickstart -k gui/$(id -u)/local.shokz-auto-fill
$ tail -f /tmp/shokz-auto-fill.log

Useful for testing after a settings change, and it is exactly what the agent runs — so if this works, plug-in will too.

What if two fills try to run at once?

Only one can. A lock file is taken atomically — with set -o noclobber, so the test and the create are a single step — before the log is even trimmed. A second run finds the lock, logs that another fill is in progress with the pid holding it, and exits without touching anything.

Without that, two /Volumes events arriving together could both number a folder and each delete the other's work. It is a defect that shipped once and is now covered by a test that extracts the lock code straight out of the shipping script, so the test cannot drift from what actually runs.

If a run is killed hard, the lock is left behind — here is the one-line fix.

Will I get the same song twice?

Not within one list — Navidrome returns a set of distinct random songs for each request. Across lists, entirely possible, and expected: the lists are independent random draws from the same library. With a small library you will notice repeats; with a large one you will not.

Can I use a playlist, or a genre, instead of random songs?

Not currently. It asks for getRandomSongs and nothing else. The Subsonic API supports plenty of alternatives — getStarred, getPlaylist, getSongsByGenre — so this is a genuinely small change to the script, but it is not built and not configurable today.

An issue saying which one you want is the way to get it considered.

Won't the log file grow forever?

No. /tmp/shokz-auto-fill.log is trimmed to its last 1000 lines at the start of every run, so it stays small by construction. Being under /tmp also means macOS clears it periodically on its own.

The install logs are a separate thing: one file per install run, under ~/Library/Application Support/ShokzAutoFill/logs/. They are small and they accumulate only as often as you run the installer.

Not answered here?

The edge-case page covers things going wrong, and the walkthrough covers things going right. If neither has it, open an issue — and include the conclusion lines from ~/Library/Application Support/ShokzAutoFill/logs/latest.log, which will usually answer it before anyone has to ask.
