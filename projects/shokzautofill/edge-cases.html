When it goes sideways

Mistyped a URL, want to change your mind, or the server said no. Every path through the installer that is not the happy one — and the promise that holds on all of them: nothing is written until the last step.

The rule that covers everything on this page

The installer collects every answer into a variable and writes nothing — no config, no script, no LaunchAgent, nothing on your player — until all the questions are done and the URL check has passed. Back out at any point, by any means, and your machine is exactly as it was.

The keys, in full

The installer does not use the normal terminal line editor. It reads your keystrokes itself, for a specific reason: bash's own editor treats a bare Esc as the start of an escape sequence and swallows it, which is exactly how "Escape goes back a step" got lost in an earlier version. Reading the bytes directly is what makes the navigation work — and it is also what keeps an arrow key from landing in your URL as literal ^[[A characters.

KeyWhat it doesAt the password prompt?
Esc or ↑ or back or < Go back one questionYes — Esc and < only
↓ or next or > Move forward to a question you have already answered> only
ReturnAccept the answer, or keep the default in [brackets]Submits the password
BackspaceDelete one characterYes, invisibly
Ctrl+UClear the whole line and start againYes, invisibly
← →Ignored. Answers are typed at the end.Ignored
Ctrl+C or Ctrl+DCancel the whole installCancels

Two files define all of this and they are short: lib/common.sh holds the reader, install.command holds the questions. Both are in the repository.

Going back a question

Press Esc. The line you are on is abandoned, the previous question is asked again with your earlier answer already in the brackets, and you can edit it:

install.command 
--- Navidrome username ---
Your Navidrome account, which need not match your macOS account.
Username: youruser
                        ← press Escape here

--- Navidrome URL(s) ---
Space-separated, tried in order. Put the fastest first, then a remote one.
URL(s) [http://navidrome.local:4533 https://music.example.com]:

Your previous answer is shown in square brackets and is the default — press return to keep it unchanged, or type over it. A bare prompt with no brackets means you have not answered that question yet.

At the very first question

There is nowhere to go, and it says so rather than doing something odd:

  this is the first question, so there is nothing to go back to

Escape at the password prompt goes to the username

Not back to some earlier question, and not out. Esc at Password for youruser returns you to the username line, because that is the most likely thing you got wrong. Fix it, press return, and you are at the password prompt again.

What going back does to your answers

Nothing. This is worth stating plainly because it is the thing that most often goes wrong in installers: every answer is held in its own variable, and stepping backwards never discards an answer you gave later.

Concretely — imagine you have answered all five questions and are looking at the URL report, when you realise the username is wrong. Press Esc through the intervening questions and back to Username, fix it, and then answer forward. Your device, your song count and your URL list are all still there. You re-answer only the username and the password.

The same holds for the URL prompt itself: the previous list appears in brackets, so correcting one entry in a list of three is an edit, not a retype.

Going forward again

↓ moves forward — but only over questions you have already answered. It will not skip a question that still needs an answer, and it will not jump you past the password prompt into an empty config.

If there is nothing ahead of you yet, it says so:

  no later question has been answered yet

Once you have answered forward, ↓ becomes a fast way back to where you were. Practically: Esc back to fix something, then ↓ forward through the questions you already answered until you reach the one you were on.

You can also type the words back and next, or < and >. Those exist so a script can drive the installer — the test suite uses them — but they work identically by hand.

The password prompt on a re-run

This is the one prompt whose behaviour changes between a first install and a re-run, and it catches people out. On a re-run, where a password is already stored, you do not get the hidden prompt at all — you get a question about the stored one:

install.command — a re-run 
--- Navidrome password ---
Keep the password already set? [Y/n]:

Press return and the stored password is kept, unchanged and never shown. Type n and it is cleared, after which you get the usual hidden Password for youruser (not echoed, will be checked): prompt to enter a new one.

A password is never displayed back to you, not even partially — not on a re-run, not in the summary, not in any log. If you are not sure whether the stored one is right, choose n and retype it; that is the only way to be certain, and it costs ten seconds.

Why this exists

Because re-running the installer to change one setting — the song count, say — should not make you dig out a password you stored six months ago. Keeping it is the default, and the config is untouched unless you say otherwise.

Pasting a URL

Pasting works, and it is safe. This sounds like a trivial thing to promise, and it is not: a pasted URL used to be able to cancel the whole install.

Terminals wrap a paste in invisible marker sequences, and those markers arrive as keystrokes exactly like an arrow key does. An earlier version read the marker as "back" and threw away the run. The current reader tracks escape-sequence state as it goes, steps over bracketed-paste markers, and reads the pasted text between them as ordinary characters.

Belt and braces: every answer is also stripped of terminal escape sequences and control characters before it is stored, so even a sequence that arrives in pieces cannot end up as invisible bytes inside a URL or a volume name. If something did get through, the -> will try: line after the prompt would show it, and Esc takes you back.

The login was rejected

The most common real failure, and the installer distinguishes it from the confusing ones. A server answered at the address you gave, speaking Subsonic — so the address is right — but it refused those credentials:

install.command 
--- Checking every configured URL ---
  rejected  : https://music.example.com (Subsonic status='40')
  0 of 1 authenticated.
WARNING: a server answered, so the addresses are right, but it rejected that login.
Go back and fix the login? [Y/n]:

Press return (or ↑) to accept — you go back and fix it. Type n (or press ↓) to carry on regardless.

Note which keys do what here, because it is a deliberate touch: ↑ means "yes, go back" and ↓ means "no, carry on", which is what those keys do at every other prompt.

What happens when you say yes

The installer walks back to the username, then the password, and then jumps straight back to the check. It does not ask for the URL list, the device or the song count again — you already answered those, and re-asking would just be an opportunity to break something that works.

install.command — after fixing the login 
--- Navidrome username ---
Your Navidrome account, which need not match your macOS account.
Username [youruser]: 

--- Navidrome password ---
Keep the password already set? [Y/n]: 

… straight back to the check, no other questions …

--- Checking every configured URL ---
  ok        : https://music.example.com (authenticated)
  1 of 1 authenticated.

If you answer n instead — carry on with a login that does not work — the install completes and the tool is installed, but every fill will fail until you fix the credentials. Re-running install.command and choosing option 4 is the repair.

Some URLs answered, some did not

You configured a LAN address and a remote fallback. The LAN one works; the remote one is dead. The installer will not let that pass quietly, because a fallback you have never tested is not a fallback — you would find out it was broken on the day the working one went away.

install.command 
--- Checking every configured URL ---
  ok        : http://navidrome.local:4533 (authenticated)
  no answer : https://music.example.com
  1 of 2 authenticated.
WARNING: these URLs did not answer: https://music.example.com
Go back and edit the URL list? [Y/n]:

Press return to go back and edit the list; type n to keep the working URL and move on. Saying yes takes you to the URL prompt with the list already filled in, and then — because the credentials did not change — it goes back to the check rather than re-asking for the username and password.

Fixing a URL does not repeat the login. Fixing the login does not repeat the URL list. Neither repeats the device or the song count.

No URL answered at all

Nothing replied. This is almost always a typo in the host or port, a server that is not running, or a firewall — and the installer offers the URL list first, because that is the usual culprit:

install.command 
--- Checking every configured URL ---
  no answer : http://navidrome.local:4533
  0 of 1 authenticated.
WARNING: no configured URL answered: http://navidrome.local:4533
Go back and edit the URL list? [Y/n]: n

Install anyway, to fix it later? [y/N]:

If you decline to go back, you get a second, blunter question. The default is N — press return and the install is abandoned cleanly.

Answer y and you get a working installation pointed at a server that does not answer. That is sometimes what you want: you are setting this up before the server exists, or you are on a different network today and know the address is right. The fill will simply abort each time until a server replies, leaving the music already on the player in place.

The twenty-round guard

There is a hard limit on the fix-and-retry loop. After twenty rounds of edits without a single working URL, the installer stops:

WARNING: 20 rounds without a working URL. Stopping so this cannot loop forever.

Aborted at your request. Nothing was changed.

The wording says "at your request" because that is the same exit path as a deliberate abandon — a small inaccuracy in the message, kept rather than papered over, since the alternative is a second exit path to maintain. An issue is welcome.

In practice you will never see it. It exists so that an unattended or mis-scripted run cannot spin forever, and it is the reason the installer suite can be run under a timeout: a prompt loop fails the test instead of hanging it.

Cancelling

Ctrl+C at any prompt, or Ctrl+D:

Cancelled. Nothing was changed.

Press return to close this window...

Nothing has been written at this point — that is the design — so there is nothing to undo. The installer also restores the terminal on the way out: it explicitly puts the terminal back into normal echo mode, so a run you cancelled at the password prompt cannot leave your shell with invisible typing. That cleanup also runs if you close the window mid-prompt.

Cancelling from a plain terminal — not a double-clicked window — exits with status 130, the conventional code for an interrupted program.

Re-running the installer

Running install.command again when something is already installed gives you a menu instead of the questions. This is also how you change any setting later.

install.command — second run 
An existing installation was found.
  config : /Users/you/.config/shokz-auto-fill/config
  script : present  (/Users/you/Library/Application Support/ShokzAutoFill/bin/auto_fill_shokz.sh)
  agent  : loaded  (local.shokz-auto-fill)

Current settings:
  device     : MY_PLAYER
  url(s)     : http://navidrome.local:4533 https://music.example.com
  login      : youruser   password: stored
  songs/fill : 50

What would you like to update?  (one number, several separated by spaces, or 'a')
  1) song count          (now 50)
  2) Navidrome URL(s)
  3) device              (now MY_PLAYER)
  4) login               (now youruser)
  5) reinstall script + LaunchAgent, and re-request volume permission
  a) all of the above
  q) quit without changing anything
Choice [a]:

Enter one number, or several separated by spaces — 1 3 — or a for everything, or q to leave it all alone. Press return and you get a, the everything option.

Only what you pick is asked. Choose 1 and you get one question, about the song count. The config, the script and the agent are left alone, and because the script and the agent read the config at run time, the change takes effect on the very next fill with no reload.

The odds and ends of this menu

  • An unrecognised entry is reported and skipped: WARNING: ignoring unrecognised choice: 'x'. The rest of your selection still applies.
  • Nothing selected — because every entry was unrecognised — gives Nothing selected - no changes made. and exits.
  • A missing stored password forces the login questions back in: WARNING: no stored password found, so the login will be asked for as well. This happens if the config was edited by hand or the password line was blanked.
  • Changing only the device or the song count prints Settings changed only - no server check needed (credentials unchanged). and skips the URL check entirely. There is no point testing a login you did not change.
  • Option 5 is the one that reinstalls the script and the agent and repeats the permission probe. That is the repair for a lost permission grant.

The player was not mounted

Perfectly fine, and the installer says exactly what it is skipping:

  device not mounted, so permission cannot be probed now.
  It will be requested the first time the device is plugged in - allow it.

The consequence is deferred, not avoided: the first time you plug the player in, macOS will put up the removable-volume dialog, and it will be the job asking rather than the installer. Click Allow then, and everything proceeds normally. If you miss it, the fill fails with Operation not permitted and the fix below applies.

The device question also behaves differently without a player attached — there is no list of mounted volumes to show, so you type the volume name from memory. If you are not certain how macOS spells it, plug the player in first; it is worth the extra ten seconds.

Permission denied

You clicked Don't Allow, or the dialog timed out. The installer says so and tells you the exact path it needs:

WARNING: permission DENIED. Allow the dialog, or add to System Settings >
Privacy & Security > Full Disk Access:  /opt/homebrew/bin/bash
then re-run this installer.

Three ways forward, in order of preference:

  1. Re-run install.command and watch for the dialog. It often appears behind the Terminal window, or on another Space. This is the normal fix.
  2. Add bash to Full Disk Access yourself, at System Settings → Privacy & Security → Full Disk Access, using the + button and ⌘+⇧+G to type the path. Note it is the Homebrew bash — /opt/homebrew/bin/bash on Apple Silicon, /usr/local/bin/bash on Intel — not /bin/bash.
  3. If it still fails, check the log for the exact interpreter and whether macOS considers it a platform binary. The install log records both:
interpreter     : /opt/homebrew/bin/bash
  platform binary: no, so macOS can prompt for it

If that line ever reads yes, something has pointed the job at /bin/bash, and no amount of clicking Allow will help — which is the whole story here.

After a Homebrew bash upgrade

This is the one failure that appears out of nowhere, weeks later, with nothing having changed on your side. The job simply stops filling, and the log fills with Operation not permitted.

The cause is in how macOS records the grant. For an unsigned binary it keys the permission by path, and it resolves symlinks — so the grant is bound to a versioned Cellar path like /opt/homebrew/Cellar/bash/5.3.20/bin/bash. Run brew upgrade bash and that path moves to 5.3.21. macOS does not follow it, and the permission is silently gone.

Re-run the installer

The default. It repeats the permission probe, so the dialog comes back and the grant is re-created against the new path. Ten seconds, and you keep receiving bash updates.

Or pin bash

brew pin bash stops its path ever moving, so the grant survives forever. Durable, at the cost of no more bash security updates.

The rule to remember: if the job stops filling for no visible reason, look for Operation not permitted in the log and re-run the installer. It is almost always this.

A stale lock file

Only one fill runs at a time. A lock file at /tmp/shokz-auto-fill.state is taken atomically before anything on the device is touched — set -o noclobber makes the test and the create a single step, so two /Volumes events arriving together cannot both get through and start deleting each other's work.

The lock records the pid that owns it, and only that run clears it. If a run is killed hard — a force-quit, a power cut, a kernel panic — the lock is left behind. The next plug-in says so, and names the culprit:

--- Tue Oct 14 07:44:10 BST 2026 --- another fill is running; skipping. The lock records pid 48213.
That process is gone, so the lock is stale: delete /tmp/shokz-auto-fill.state and replug.

The fix is one line:

$ rm /tmp/shokz-auto-fill.state

…then unplug and replug the player.

Why it is not automatic

Deciding that a lock is stale means reading it, checking whether the pid is alive, and then deleting it — and another run can take the lock between that read and that deletion, which is precisely the race the lock exists to prevent. So it reports instead of guessing, and leaves the judgement with you. If the pid it names is still alive, a fill genuinely is running; wait for it.

The server is down at fill time

You plug in, and nothing seems to happen. The log tells the story, and — importantly — tells you that nothing was damaged:

Probing http://navidrome.local:4533...
FAILED http://navidrome.local:4533: curl error 7 (unreachable / timed out).
Probing https://music.example.com...
FAILED https://music.example.com: curl error 28 (unreachable / timed out).
ABORT: None of the configured Navidrome URLs answered: http://navidrome.local:4533 https://music.example.com. Leaving existing music on MY_PLAYER untouched.
Short-circuiting: no new auto-list folder, no cleanup, no eject.

Two things to note about that:

  • "No cleanup" is deliberate. The old-list pruning happens after a successful download, so a failed run cannot delete your existing music. The player is left exactly as it was.
  • "No eject" means the drive stays mounted. That is your signal something went wrong — on a successful fill the volume disappears on its own.

The same short-circuit applies if the server answers but returns nothing usable. Zero songs is treated as failure, not as an empty playlist:

ABORT: getRandomSongs returned zero songs from http://navidrome.local:4533. Refusing to create an empty auto-list folder.

And if every individual download fails partway through, the half-built folder is removed and the run aborts, leaving the older lists intact:

Removing empty folder /Volumes/MY_PLAYER/auto-list/7
ABORT: All downloads failed against http://navidrome.local:4533. Existing auto-list folders left intact.

Nothing happens when I plug in

Three checks, in order. The first one answers the question ninety per cent of the time.

CheckCommandIf it looks wrong
Is the agent loaded? launchctl list | grep shokz No output means it is not loaded. Re-run install.command and choose option 5.
Does the volume name match? ls /Volumes Compare against DEVICE_NAME in ~/.config/shokz-auto-fill/config. A player that mounted as MY_PLAYER 1 because an older mount never cleared will not match MY_PLAYER. Eject, unplug, replug, and re-run the installer if the name has genuinely changed.
What does the job say? tail -30 /tmp/shokz-auto-fill.log The log names the failure. Operation not permitted is permission; ABORT is the server.

A related trap: launchctl list local.shokz-auto-fill saying "could not find service" is not a fault. The correct label is local.shokz-auto-fill, and it must be passed to launchctl list exactly — no domain prefix. If it is genuinely missing from launchctl list with no argument, the agent is not loaded.

A half-written folder

If a fill is interrupted — you unplug mid-download, the Mac sleeps, the server drops — you can be left with a numbered folder holding fewer tracks than it should. auto-list/7 with nineteen songs in it, say.

Nothing breaks. The next fill takes the next number and works normally, and the partial folder is just an unusually short playlist until the pruning catches up with it. If it bothers you:

# with the player mounted — delete only the numbered folder you want gone
$ rm -rf "/Volumes/MY_PLAYER/auto-list/7"
Be precise with that path

That command deletes a folder. Check the number against what is actually on the player first — ls /Volumes/MY_PLAYER/auto-list — and delete exactly one numbered folder. Do not run it against auto-list itself, and do not run it when the drive is not mounted: without the volume, the path resolves to a folder on your own disk, or to nothing at all.

There is no need to clean up before the next fill. The script numbers folders by looking at what is already there, so gaps and partials do not confuse it.

Reading the logs

When something is wrong, these two files answer almost every question.

FileRead it when
/tmp/shokz-auto-fill.log The fills themselves. One block per plug-in, newest at the bottom. Trimmed to the last 1000 lines automatically.
…/ShokzAutoFill/logs/latest.log The installer. Full network diagnosis for every URL, the config it wrote, the plist it generated, the script hash, and the permission probe.

The thing to look for first is the conclusion line, because it is written to tell apart the failures that look identical from outside:

  conclusion       : authenticated
  conclusion       : reachable, and it rejected the credentials
  conclusion       : the TCP connection opened and the server never replied
  conclusion       : TLS completed and then nothing came back. A proxy is waiting on an upstream that never answers
  conclusion       : headers arrived but the body never finished, so the upstream stalled mid-response
  conclusion       : no reply before the deadline. The port is filtered, or the host is down
  conclusion       : nothing is listening on that port
  conclusion       : the hostname did not resolve
  conclusion       : the TLS handshake or the certificate failed

“The connection opened and nobody answered” and “the port is filtered” are the same experience and completely different problems — a hung Navidrome versus a firewall rule. Everything else in the log, the timings and headers and body excerpt, is there to settle that question.

The log is written for the question you ask after something breaks, so it records the reasoning rather than just the outcome. It is also mode 600, and it contains no credential: the password is substituted out, and so is any Subsonic token or salt, because a token with its salt is a working credential.

Uninstalling

Double-click uninstall.command. It unloads and removes the LaunchAgent and the installed script, and then asks separately about the config — because that file holds your password, and you might be about to reinstall.

Say no to the config question and the credentials survive for a future reinstall. Say yes and everything is gone.

Music already on the player is never touched, by the uninstaller or by anything else here. If you want the auto-list folders off the player, delete them yourself — the tool will not do it for you, on the principle that a cleanup routine that can be pointed at your files is a cleanup routine that can be pointed at the wrong ones.
