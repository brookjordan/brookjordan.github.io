Before you start

You need four things:

  • A Mac. This is macOS-only. It relies on launchd and on a quirk of macOS privacy that has no equivalent elsewhere.
  • A Navidrome server — navidrome.org — with your music on it, and an account on that server. This can be on the same Mac, on a NAS in the house, or on a VPS somewhere. It just has to answer HTTP.
  • The player, formatted as FAT32 or exFAT, so that it mounts as a folder under /Volumes.
  • Homebrew — brew.sh — but only if you don't already have jq and a non-Apple bash. The installer checks first and will not touch Homebrew if it doesn't need to.
Plug the player in first

You can install without the player attached, and the installer will still set everything up — but it will not be able to run its permission test, and you will meet the Allow dialog for the first time on your next plug-in instead, with no context for what just asked you for access to your drive. It is a much calmer experience to have the player mounted while you install. It also gives the device question a menu to show you rather than a blank line.

The short version

If you read nothing else, this is the whole thing.

1

Get the files

Clone the repository, or download the ZIP from GitHub and unpack it. Anywhere is fine — your home folder, your Desktop, a projects directory. The installer copies what it needs into place; the folder you run it from is not where it lives afterwards.

$ git clone https://github.com/brookjordan/shokz-auto-fill.git
$ cd shokz-auto-fill
2

Plug your player in, then double-click install.command

In Finder, that is two clicks. From a terminal, it is ./install.command. Either way you get the same thing: a Terminal window opens and starts asking questions.

macOS will probably block it once

The first time, you may get "install.command cannot be opened because it is from an unidentified developer", or a dialog offering to move it to the Bin. That is Gatekeeper doing its job on an unsigned script. Do not double-click again — right-click the file, choose Open, then click Open in the dialog. macOS remembers, and every later run is a normal double-click.

If there is no Open option, the file has lost its execute permission — usually because it came out of a ZIP. Fix it once with chmod +x install.command.

3

Answer five questions

They are asked in a deliberate order, and you can go back and change any answer before anything is written. Full detail on the five answers below.

4

Click Allow when macOS asks

Once, near the end. The dialog is macOS asking whether the job may write to removable volumes. Click Allow. If you click Don't Allow, the installer tells you and you can re-run it — nothing is broken, and nothing is written to the drive until this is granted.

5

Done

The installer prints a summary and waits for you to press return before closing the window. That is the whole installation. To test it right away:

$ launchctl kickstart -k gui/$(id -u)/local.shokz-auto-fill
$ tail -f /tmp/shokz-auto-fill.log

The five answers

Asked in this order, on purpose. The server and the login come first so that the connection check they make possible can run in the background while you answer the remaining questions. By the time you finish, the answer is usually already waiting.

QuestionWhat to putWhy it is asked this way
Navidrome URL(s) One or more base URLs, separated by spaces or commas. e.g. http://navidrome.local:4533 https://music.example.com Every URL is checked during install. A dead fallback is worth discovering now, rather than on the day the working one goes away.
Username Your Navidrome account name. It does not have to match your macOS account. Asked separately from the password so that a typo you notice at the password prompt is one Esc away from being fixed.
Password Your Navidrome password. Nothing appears as you type. Not echoed. Pressing return keeps a password already stored from a previous install.
Device The volume name — the folder name under /Volumes. You can type it, or type the number from the list the installer prints. Currently mounted volumes are listed with a filesystem and free-space hint, so you can tell your player from a mounted disk image.
Songs per fill A whole number. Default 50. You can change it later without reinstalling.

The bits nobody tells you

A .command file is just a text file

It is not an app, not a package, and not a binary. It is a shell script with a .command extension, which is the one thing that makes Finder hand it to Terminal instead of opening it in TextEdit. Right-click it and choose Open With → TextEdit and you will read exactly what is about to run — no compiled code, no installer payload, no hidden download step.

That is also why Gatekeeper complains. There is no developer certificate to check, so macOS falls back to "I have never seen this, ask a human." The right-click-and-Open dance is you answering that question once.

Don't worry — your password will not appear on screen

When you reach the password prompt, typing produces nothing at all. No characters, no asterisks, no dots, no cursor movement. That is not a broken prompt; it is the point. The installer puts the terminal into no-echo mode itself and reads your keystrokes one at a time, precisely so the password cannot be shoulder-surfed or caught by a screen recording.

From there the password goes to exactly one place: ~/.config/shokz-auto-fill/config, written with mode 600 — readable only by your user account. It is never printed, never written to the installer's log (which redacts it even if it somehow appeared), and never sent anywhere except your own Navidrome server.

What actually goes over the wire

Not the password. Every request to Navidrome uses a Subsonic token: md5(password + salt), with a fresh random salt each time. Even on the wire, your password itself never travels.

If you would still rather not, make a second Navidrome account for this tool and use that. It only ever needs to read your library.

Why we ask for the fastest server first

You can give it several URLs, and they are tried in the order you write them, with the first one that answers winning. The order matters more than it looks:

  • Put your LAN address first. If your Navidrome is on the same network, http://navidrome.local:4533 will beat a remote URL every time — often by two orders of magnitude. Fifty songs off a local server is seconds; fifty songs over the internet from a coffee shop is minutes, and every one of those minutes is a drive sitting there half-written.
  • Put a remote URL second. That is the fallback for when you are away from home. This is exactly the entry that rots quietly — a dynamic DNS name that stopped updating, a certificate that expired, a port forward someone closed. Which is why the installer checks every URL, not just the first one. A fallback you have never tested is not a fallback.

At fill time, "reachable" is enough to win. A URL that answers but rejects the login is still the right service on the right host, so the job stays with it rather than skipping ahead to a URL that might do the same thing more slowly.

Have the drive attached so we can find it

Two reasons, and the second is the one that bites.

One: the installer lists what is currently mounted under /Volumes — with the filesystem and free space next to each entry — so the device question becomes "type 2" instead of "remember exactly how macOS spelled your player's volume name." A player named MY PLAYER with a space in it is a perfectly normal thing to get wrong.

Two: the removable-volume permission can only be tested against a drive that is actually there. macOS grants access to removable volumes as a category, so in principle one grant covers everything — but the installer would rather prove it now, on a drive it can write to and clean up after, than leave you to discover a denial at 6am on your way out of the door.

Why it installs Homebrew bash

This is the one genuinely surprising requirement, and it has a real reason. macOS will not grant removable-volume access to an Apple platform binary, and /bin/bash is one. The refusal is silent and permanent, and it arrives as Operation not permitted on every write — the single most confusing failure this project has. The long version, with the actual log lines, is in the walkthrough and the FAQ.

What lands where

Six things, all of them listed here so there are no surprises later.

PathWhat it is
~/Library/Application Support/ShokzAutoFill/bin/auto_fill_shokz.sh The fill script itself.
~/.config/shokz-auto-fill/config Device, URLs and credentials. Mode 600. This is the only file with your password in it.
~/Library/LaunchAgents/local.shokz-auto-fill.plist The LaunchAgent that runs the script whenever /Volumes changes.
/tmp/shokz-auto-fill.log The job's own log. Trimmed to the last 1000 lines on every run.
~/Library/Application Support/ShokzAutoFill/logs/ One install log per run, mode 600, credentials redacted, with latest.log pointing at the newest.
/Volumes/<PLAYER>/auto-list/<n>/ The music. Numbered folders, two newest kept.

Nothing is installed system-wide. There is no sudo anywhere in the installer, no daemon, no kernel extension, and nothing written outside your home folder except the two logs under /tmp.

After the install

Changing a setting later

Just run install.command again. It notices the existing installation, shows you what is configured, and asks what to change. Enter one number, or several like 1 3, or a for everything, or q to leave it alone. Because the script and the agent read the config at run time, a settings change takes effect on the very next fill — no reload, no restart.

Choose 5 when you want to reinstall the script and agent themselves — for example to re-request the removable-volume permission after a Homebrew bash upgrade, which the FAQ covers.

Removing it

Double-click uninstall.command. It unloads and deletes the LaunchAgent and the installed script, then asks separately before deleting the config — because that file holds your password, and you might be reinstalling in a minute. Music already on the player is never touched.

Stuck?

The installer writes an unusually detailed log on purpose — every URL it tried, the DNS answer, whether the port was open, the TLS timing, the Subsonic status, and a plain-English conclusion. Open ~/Library/Application Support/ShokzAutoFill/logs/latest.log before assuming anything. The log section shows you what to look for.
