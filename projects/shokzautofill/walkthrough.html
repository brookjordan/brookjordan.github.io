Shokz Auto-Fill/Install/Walkthrough

The walkthrough

The happy path, in full. Every prompt in the order you will meet it, the exact text on screen, what to type, and — just as usefully — the two moments where the installer goes quiet on purpose and you should sit on your hands.

Read this first

Nothing in the installer is written until the very end. No config, no script, no LaunchAgent, and nothing at all on your player. You can press Ctrl+C at any prompt and the answer is always the same: “Cancelled. Nothing was changed.” That means you can walk through the whole thing just to see it, and back out at the last question, without a trace.

Step 0

Before you double-click

Have three things to hand, because they are all asked in the first ninety seconds:

  • The URL of your Navidrome server — including the port. It looks like http://navidrome.local:4533 or https://music.example.com. No trailing path, no /app, no /rest — just the base.
  • Your Navidrome username and password, not your macOS ones.
  • The player, already plugged in. Not strictly required, but it turns the device question into a menu and lets the installer test the permission now rather than at 6am tomorrow.

Then, in Finder: double-click install.command.

The one Gatekeeper interruption

First run only, if the file was downloaded rather than cloned: right-click → Open → Open. A plain double-click gives you “cannot be opened because it is from an unidentified developer” and no way forward. See what a .command file is for why.

Step 1

The window opens

A Terminal window appears and prints this. It is the same for a first install and a re-run; everything below happens inside this one window.

install.command — bash — 80×24 
=== Shokz Auto-Fill installer ===

Escape or Up goes back a question, Down moves forward to one you have already
answered, and Ctrl-C cancels. Backspace works, and a URL can be pasted.

The Navidrome server and login come first, so the connection can be checked
while the remaining questions are asked.

What to do: nothing yet. This paragraph is the whole keyboard contract, and it is worth the ten seconds it takes to read — the arrow keys do something specific here, and it is not what you might guess. The full key reference is here.

Step 2

Navidrome URL(s)

install.command 
--- Navidrome URL(s) ---
Space-separated, tried in order. Put the fastest first, then a remote one.
URL(s):

Type: one or more URLs, separated by spaces or commas. Press return. For example:

http://navidrome.local:4533, https://music.example.com

Commas are converted to spaces for you, so pasting a comma-separated list from your notes works fine.

Then you will see:

  -> will try: http://navidrome.local:4533 https://music.example.com

That is your confirmation the list parsed the way you meant it. If a URL has been mangled — split in the wrong place, or trailing punctuation absorbed into it — this is where you find out, and Esc takes you straight back to fix it.

Order matters, here and later

First URL that answers wins, at every fill, forever. LAN address first, remote second — the reasoning is on the install page.

Step 3

Username

install.command 
--- Navidrome username ---
Your Navidrome account, which need not match your macOS account.
Username:

Type: your Navidrome account name. It is echoed as you type, which is deliberate — a typo here would otherwise only surface as “rejected” two questions later, with no way to see what you actually sent. You will see no -> confirmation line here; the value is shown back to you in the Done summary instead.

This is separated from the password on purpose. If you notice at the password prompt that the username was wrong, one Esc puts you back on this line.

Step 4

Password — and why nothing appears

install.command 
--- Navidrome password ---
Password for youruser (not echoed, will be checked):

Type your password and press return. You will see absolutely nothing — no characters, no dots, no asterisks, and the cursor will not move. This is the single most alarming part of the install and it is entirely intentional.

The installer takes the terminal out of its normal line-editing mode and reads your keystrokes itself. That is what stops the password reaching the screen, the scrollback buffer, or a screen recording. Backspace still deletes, the same as anywhere else — you just cannot see it happen. If you lose track, press Ctrl+U to clear the line and start again.

A word of caution that only applies here

Everywhere else in the installer, typing back goes to the previous question. Not at this prompt. A password can be any string at all, so reserving a word here would make that password untypeable. Only Esc, < and > navigate from the password prompt.

The moment you press return, the connection check starts in the background. It runs while you answer the next two questions, which is the reason the server and login were asked for first.

Step 5

Two more questions, while the check runs behind you

These two appear immediately. Meanwhile, in the background, the installer is already talking to your Navidrome server. On a slow or remote server it may still be going when you finish — that is fine, and it will say so in the next step.

Device

install.command 
--- Which device should be filled? ---
The name the player mounts as, the folder under /Volumes.
Currently mounted volumes:
  1) MY_PLAYER  (MS-DOS FAT32, 27.9 GB free)
  2) Backup  (Mac OS Extended (Journaled), 412 GB free)

Volume name (or a number from the list):

Type: the number next to your player — 1 — or the volume name itself, MY_PLAYER. Both work. The list is built live from /Volumes at the moment the question is asked, so it reflects what is actually plugged in right now.

Each entry carries a hint: the filesystem and the free space. That is there to tell a real player from a mounted disk image, which macOS also reports as removable. If your player is not in the list, it is not mounted — check the cable, and check the player is not sitting in a charging-only state.

Then you will see:

  -> /Volumes/MY_PLAYER

If you typed a number that is not in the list, you get WARNING: there is no volume numbered 9 and the question is asked again rather than accepting something that does not exist.

Songs per fill

install.command 
--- Songs per fill ---
How many songs per fill [50]:

Type: a whole number, or just press return for 50. The value in square brackets is the default, and on a first run that is always 50.

Then you will see:

  -> 50 songs per fill

Anything that is not a positive whole number gets WARNING: enter a whole number. or WARNING: enter a number greater than zero. and the question comes back. Nothing is accepted silently.

Fifty songs at roughly 4 MB each is about 200 MB per list, and you keep two — so budget around half a gigabyte of the player. On a 32 GB OpenSwim that is comfortably nothing; on a small clip-on player, check the free space in the device list above.

Step 6

The URL report

Now the background check is collected and reported. Every URL you gave gets one line.

install.command 
--- Checking every configured URL ---
  ok        : http://navidrome.local:4533 (authenticated)
  ok        : https://music.example.com (authenticated)
  2 of 2 authenticated.

This is the good outcome and it needs nothing from you. Both URLs answered and both accepted the login, so the installer carries straight on to writing the config.

Three verdicts are possible, and only the first one is silent about it:

LineMeaning
ok : … (authenticated) The server answered and accepted your login. This is the one you want.
rejected : … (Subsonic status='40') A server answered, at the right address, speaking Subsonic — but it refused those credentials. The host is right; the login is wrong.
no answer : … Nothing replied at all: wrong host, wrong port, a firewall, or the server is down.

If everything is green there is nothing to do. If it is not, the edge-case page walks through exactly what the installer offers you and how to retry — including the fact that fixing a URL does not make you re-answer the login, the device or the song count.

If it says it is still waiting

On a slow server you may see the background check has not finished; waiting for it instead. That is the installer telling you why the window has paused rather than sitting there looking frozen. Let it finish — it is bounded, and it will not hang indefinitely. The timeout is eight seconds to connect and sixteen seconds in total, per URL.

Step 7

The config is written, then the script and agent

install.command 
config written: /Users/you/.config/shokz-auto-fill/config (mode 600)

--- Shell for the background job ---
  using /opt/homebrew/bin/bash (not a platform binary, so macOS can grant it access)
  installed script: /Users/you/Library/Application Support/ShokzAutoFill/bin/auto_fill_shokz.sh
  wrote /Users/you/Library/LaunchAgents/local.shokz-auto-fill.plist
  agent loaded: local.shokz-auto-fill

Four things just happened. The config was written with your credentials at mode 600. The fill script was copied into ~/Library/Application Support/ShokzAutoFill/ with its shebang pointed at the Homebrew bash resolved on this machine. The LaunchAgent was written and checked with plutil. And the agent was loaded into launchd.

If you see Installing bash via Homebrew above the first line, that is expected on a Mac without Homebrew bash — it is a normal brew install, and the only package this tool ever installs. Here is the long answer for why it is necessary.

Step 8

The Allow dialog — the important one

This is the moment the whole project exists to get right.

install.command 
--- Removable-volume permission ---
macOS may ask once to allow access to removable volumes; click Allow.
  permission OK - the job can write to the device

Look away from Terminal. A macOS dialog appears — usually behind the Terminal window, or as a notification in the top-right — naming bash and asking whether it may access files on a removable volume. Click Allow.

The installer waits for that answer, up to sixty seconds, then prints one of three lines:

LineWhat it means
permission OK - the job can write to the device Done. Everything works from here.
WARNING: permission DENIED… The dialog was declined. It tells you the exact path to add under System Settings → Privacy & Security → Full Disk Access, and asks you to re-run. Nothing is broken.
WARNING: no answer within 60s… Most likely the dialog is still sitting there unanswered, possibly on another Space or behind a full-screen window.
device not mounted, so permission cannot be probed now. You installed without the player attached. The permission is requested the first time you plug it in — allow it then.

Why a permission dialog at all

Because macOS will not let a background job write to a removable volume without one, and the refusal is otherwise silent. The mechanics are worth knowing, because they explain the strangest requirement of this whole project — the Homebrew bash.

macOS gates removable volumes behind a privacy service called kTCCServiceSystemPolicyRemovableVolumes. When a LaunchAgent runs a job, one process in that job is designated the responsible process, and that is who macOS asks. Run /bin/bash and bash is the responsible process — but /bin/bash is an Apple platform binary:

$ codesign -dvvv /bin/bash | grep Platform
Platform identifier=26

macOS refuses to grant TCC permissions to a platform binary and cannot even raise the prompt:

Platform binary prompting is 'Deny' because: is Platform Binary

The denial is permanent and it produces no dialog, no error and no log entry of its own. What you get, eventually, is this in the job log — once per file, with no explanation of the cause:

mkdir: /Volumes/MY_PLAYER/auto-list/1: Operation not permitted

Run the same commands in an interactive shell and they work perfectly, because there the responsible process is Terminal rather than bash. That discrepancy — works by hand, fails from the job — is the entire bug this project was built around.

So the job runs under a Homebrew bash, which is not a platform binary. macOS can then ask, and you can then answer:

AUTHREQ_PROMPTING: service=kTCCServiceSystemPolicyRemovableVolumes
                   subject=Sub:{/opt/homebrew/Cellar/bash/5.3.20/bin/bash}
...
Publishing <TCCDEvent: type=Create, service=kTCCServiceSystemPolicyRemovableVolumes,
            identifier_type=Path, identifier=/opt/homebrew/Cellar/bash/5.3.20/bin/bash>
The catch: the grant is keyed by path

Read that second block again — the grant is recorded against a versioned Homebrew path, …/Cellar/bash/5.3.20/bin/bash. Run brew upgrade bash and that path moves. The grant does not follow it.

Two ways to live with it: re-run install.command after a bash upgrade (it repeats the probe, so the dialog comes back and the grant is re-created), or brew pin bash to stop its path ever moving. The full comparison is in the FAQ.

Step 9

Done

install.command 
=== Done ===
Config   : /Users/you/.config/shokz-auto-fill/config
  device     : MY_PLAYER
  url(s)     : http://navidrome.local:4533 https://music.example.com
  login      : youruser
  songs/fill : 50
Agent    : local.shokz-auto-fill
Log      : /Users/you/Library/Application Support/ShokzAutoFill/logs/install-20261014T071203.log
Job log  : /tmp/shokz-auto-fill.log

To test now:  launchctl kickstart -k gui/501/local.shokz-auto-fill

Press return to close this window...

Read the summary back. That is your chance to catch a wrong device name or a mistyped login while it is still cheap to fix — re-running the installer takes ten seconds and changes only what you pick.

Note the password is not in that summary. It never appears anywhere on screen.

Then press return to close the window. That pause only exists because a double-clicked .command would otherwise close its own Terminal window the instant it finished, taking the summary with it.

Step 10

Your first fill

If the player is still plugged in, nothing has been written to it yet — the installer does not fill anything. The job fires when /Volumes changes, so either unplug and replug the player, or kick it off by hand to watch it work:

$ launchctl kickstart -k gui/$(id -u)/local.shokz-auto-fill
$ tail -f /tmp/shokz-auto-fill.log

This is what scrolls past. A full fifty-song fill is typically twenty seconds to a couple of minutes, depending on how far away the server is.

/tmp/shokz-auto-fill.log 
--- Script started at Tue 14 Oct 07:31:52 BST 2026 ---
Probing http://navidrome.local:4533...
OK http://navidrome.local:4533: reachable and authenticated.
Using Navidrome via http://navidrome.local:4533
Fetching 50 random songs from Navidrome...
Got 50 song id(s).
Downloading to /Volumes/MY_PLAYER/auto-list/1...
Downloaded file count in /Volumes/MY_PLAYER/auto-list/1: 50
Cleaning up old lists (keeping 2 newest)...
Syncing and ejecting...
"MY_PLAYER" ejected.

What to do: nothing. The drive is ejected when it finishes, which is your cue — the volume disappears from Finder, and the player is safe to unplug and put on.

On the player you will find the tracks inside auto-list/1/, numbered 0001 - …, 0002 - … and so on, so the player plays them in the order they were fetched rather than alphabetically. Replace one list with a fresh one next time you plug in; the list before that stays until the fill after.

Step 11

Confirming it worked

Three quick checks, in increasing order of effort:

  • The player was ejected. If its volume vanished from Finder on its own, the run completed — that is the last thing the script does.
  • The folder is there. Plug it back in and look for auto-list/1 with fifty tracks in it.
  • The agent is loaded. This should print a line with a PID:
$ launchctl list | grep shokz
-   0   local.shokz-auto-fill

A leading - means it is loaded and idle, which is exactly right — the agent only runs when /Volumes changes. A number there means it is running at this moment. If the command prints nothing at all, the agent is not loaded; re-run install.command and choose option 5.

Step 12

The logs, and why they are worth knowing about now

Two logs, for two different questions.

FileAnswers
/tmp/shokz-auto-fill.log “What has the job been doing?” One entry per fill. Auto-trimmed to the last 1000 lines so it can never grow without bound.
~/Library/Application Support/ShokzAutoFill/logs/latest.log “Why did the installer decide that?” One file per install run, with latest.log always pointing at the newest. Mode 600.

The install log is unusually thorough on purpose. Every URL gets a full trace — DNS, whether the TCP port was open, the curl exit code and what it means in English, timings for DNS, connect, TLS and first byte, the response headers, an excerpt of the body, the Subsonic status, and a plain conclusion:

  url              : http://navidrome.local:4533
  DNS              : address literal, no lookup needed
  TCP 4533         : open
  curl exit        : 28, timed out: no reply before the deadline
  timings          : code=000 connect=0.000232s tls=0.000000s total=16.006105s bytes=0
  conclusion       : the TCP connection opened and the server never replied

That last line is the whole point of the exercise. “The connection opened and nobody answered” and “the port is filtered” look identical from the outside and have completely different fixes — a hung Navidrome versus a firewall. The log tells them apart.

Tokens, salts and your password never appear in it. A Subsonic token with its salt is a working credential, so anything replayable is redacted before it reaches the file.
